## 逐条处置

| 需求 | 处置 | 关键理由 |
| --- | --- | --- |
| 拉黑 3 条 + 删除 3 条 + 重加 + 刷新 | S3-A | 用户最常撞上的缺口；本地策略，不改线格式（除解除拉黑的可验证答复） |
| 通知内容、连接方式、可达性、使用前告知 | S3-B | 给别人用之前必须有；都挂在现有状态上 |
| 全文搜索、十万条 | S3-C | 阻塞于「加密存储怎么搜」的 ADR |
| 恢复短语 5 条 | 延后 | 冲击 ADR-0007 的失败关闭边界，需密钥管理 ADR + 外部评审 |
| 消息删除 5 条 | 延后 | 墓碑与逐设备确认是协议级改动，与 GBNV 耦合 |
| 公开别名头像、公开张贴、渠道身份复用 | 延后 | v1 没有公开面 |
| 联系人分组、引用回复 | 延后 | 价值不足，且要动消息结构/新字段 |
| 大范围重发批准、配额暂停、陌生对端预算、在线状态 | 延后 | 需要新协议状态或新功能面 |
| 解除拉黑的完整不可得状态机 | 延后 | 只取本波用到的可验证答复那一段 |

## 已知约束

- 没有墓碑 → S2b 的扇出会把删过的消息带回；S3 不做消息删除，这是明确约束不是缺陷。
- v1 的 16 条行为契约不变，S3 只新增。
- 生产代码余量 10,386 行；三波估算用 3,800–5,600 行。延后 19 条全做会超 30,000 行上限。
- S3-C 未解 ADR 前不开工；十万条阈值不继承旧项目数字。
