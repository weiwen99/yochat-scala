# 需求分期、矛盾与难点

> 对象：旧实现 `docs/product/` 的 118 条需求；重写侧对照 `docs/adr/0003-v1-scope.md` 与 `0004-test-parity-and-performance-gates.md`。
> 结论先行：**不是所有需求都要在 MVP 做。** 旧计划的「首增量 93 条」是范围声明，不是最小可用集；23 条已明确延后，剩余 95 条可以按 S1 / S2 / S3 分批。
> 本文的分批是**为重写提出的建议**，不是旧项目的声明，也不是已经拍板的 S3 清单。S3 条目必须逐条重新论证。

## 1. 口径

先把三个数对齐：

| 数 | 含义 |
| ---: | --- |
| 118 | `docs/product/` 的全部需求：用户与设备 24、好友与通讯录 24、聊天与会话 35、界面与外壳 4、隐私与防护 8、群聊 8、文件传输 15 |
| 95 | 旧计划列入首个交付增量的需求：93 条原始需求 + 2 条 2026-11-03 的排序/补入增补 |
| 23 | 旧计划逐条声明延后的需求：群聊 8 + 文件传输 15 |

「MVP」在这里有两个含义，必须分开：

- **旧计划的「首个交付增量」**：95 条，覆盖多设备、历史同步、吊销、恢复短语、WCAG、十万条历史、陌生对端预算等发布级要求；首期只先验 macOS。
- **重写的 S1**：两个用户、各一台设备、加好友、单聊、先落盘、重启不丢、断网重连；生产代码 ≤30,000 行，1,000 条端到端 <5 秒。

旧计划把发布级要求和自用场景混在一个增量里，这正是复盘里的范围失控。下面的分批把「自用工具先能用」放在 S1，把多设备放 S2，把发布级要求放 S3。

**批次口径**：

- 批次 = 该需求**首次被实现**的批次；标「子集」的条目在该批次只实现核心部分，完整范围在后续批次。
- S1 / S2 对齐 ADR-0003 的方向；S3 是候选池，不是承诺。
- 一条需求进哪个批次，看它的**依赖与成本**，不看它写在旧文档的哪一篇。

## 2. 分批结果

| 批次 | 条数 | 一句话 | 主要成本 |
| --- | ---: | --- | --- |
| S1 | 40 | 两台设备、各一台；加好友、单聊、落盘、重启、重连 | 一条协议路径 + 本地加密/锁 + 最少的 UI |
| S2 | 20 | 同一用户多设备；仍无群聊/文件 | 设备列表合并、历史同步、吊销、本人同步、常在线 |
| S3 | 35 | 发布级 MVP 候选 | 拉黑/删除/搜索/通知/键盘/十万条/恢复短语/多实例/隐私告知 |
| D | 23 | 群聊 8 + 文件 15 | 旧计划已逐条延后 |
| 合计 | 118 |  |  |

**为什么 S1 还有 40 条？** 因为很多条目是跨切面的不变量（签名、去重、时间不可信、诊断不含内容），不是独立功能。真正的成本轴是：协议状态机、加密、存储、传输、UI/壳五个组件；不是需求条数。若要把 S1 再缩小，只能缩小验收场景（例如先做在线单聊），不能删掉安全不变量。

S1 里需要特别说明的三条：

- `REQ_20260918_2276A5JCK1KGNS1A`：S1 只做**定向邀请**；不定向邀请、公开张贴、渠道身份复用都在 S3。
- `REQ_20260918_R1J6B5CH21YFFP32`：S1 只有一台设备，规则退化为「用户私钥只在这台设备上」；多设备的完整规则在 S2。
- `REQ_20261103_GBNVF8ZY42F1DZX4` 不在 S1：S1 设计只承诺按作者顺序。若要求跨作者最终全序，要么在 S1 加成本，要么明确降级为已知约束；不能既说 S1 等价旧规格，又不实现它。

## 3. 依赖顺序

分批不是按文档切，而是按依赖切。主要依赖链：

```text
用户密钥 / 本地加密 / 应用锁
        │
        ▼
定向邀请 ── 一次性公钥 ── 应答 ── 安全码
        │
        ▼
联系人关系 ── 设备组（S1 只有两台设备）
        │
        ▼
单聊：先落盘 → 发送 → 缺失检测 → 等待 → 重发 / 重建
        │
        ├── S2：设备列表 / 新设备 / 历史同步 / 吊销 / 本人同步
        │
        └── S3：删除 / 搜索 / 拉黑 / 通知 / 十万条 / 恢复短语 / 多实例
```

几条硬依赖：

- 没有定向邀请与一次性公钥，就没有关系；没有关系，就没有消息准入。
- 没有本地落盘与去重，重发/重建会制造重复或丢消息。
- 没有设备列表合并，S2 的历史同步与吊销会在分叉上打架。
- 没有删除墓碑，S3 的多设备同步会把删过的消息又带回来。
- 没有应用锁的会话失效，S1 的「锁定即边界」不成立，S2 的多实例隔离也不成立。

## 4. 表面矛盾与张力

下面 12 条是读旧规格时最容易卡住的地方。多数不是设计错误，而是**两个正确约束的交界**；旧文档大多写明了边界，少数仍需裁决。

| # | 表面矛盾 | 证据 | 实际关系 / 裁决 | 批次 |
| ---: | --- | --- | --- | --- |
| 1 | 用户私钥「只存在于指定设备」 vs 恢复短语是私钥的可写形式 | `REQ_20260918_R1J6B5CH21YFFP32`；`REQ_20260918_T1H63J7F3QD0WBBT`；旧术语「恢复短语」 | 字面绝对化。应改成「YoChat 不在指定设备之外持久保存用户私钥；恢复短语由用户自行保管」。不是设计变更，是措辞修正。 | S1 / S3 |
| 2 | 消息不得因资源上限被放弃 vs 接收/落盘/存储有上限 | `REQ_20260918_537BK4VME23Y2GTW`；`REQ_20260918_0FAYS8R0Z7A9WF3Q` | 上限在**接纳之前**拒绝；已接纳的消息不丢。存储满之后是暂停 + 恢复动作，不是静默丢弃。需要明确「已接纳」的边界。 | S1 / S3 |
| 3 | 严格按序、不得跳过 vs 放行应用游标 | `REQ_20260918_537BK4VME23Y2GTW`；`REQ_20260918_9MKG1QMBXQAG6C12` | 「放行」不是「应用」：它为不可得/等待批准的位置推进游标，带可见原因且可逆。标题比机制更绝对，UI 与测试必须区分 应用 / 放行 / 已决。 | S1 / S3 |
| 4 | 等待只因乱序、会自行结束 vs 暂不可得/不再提供长期存在 | `REQ_20260918_BXC7RNH3YCQZ9BQY`；`REQ_20260918_9MKG1QMBXQAG6C12` | 「等待」只指乱序；「暂不可得」「不再提供」是另外的状态。旧术语表已经区分，界面不能都叫「等待」。 | S1 / S3 |
| 5 | 关系需要双方各自确认 vs 应答方发出应答即完成确认、拒绝不产生信号 | `REQ_20260918_1VXJQ68HXHM0JR0Q`；`REQ_20260918_A1MZYZ7JV43G7EJ3`；`REQ_20260918_KWW858WDBR49C9KS` | 确认是**非对称**的：应答方先认为建立，发起方后确认；拒绝是静默的。有限交换不可能消灭不一致，旧规格要求过期 + 恢复提示。这是协议限制，不是 bug。 | S1 |
| 6 | 常在线设备无人值守 vs 应用锁是安全边界、空闲自动锁定 | `REQ_20260918_GBC9KZAACYZ1RHYZ`；`REQ_20260918_B9Y4E73VMQ8RS99X`；`REQ_20260918_YQW27DXZJSHAR0Z0` | **仍未裁决。** 锁定后的常在线设备是否还能解密，旧规格没有给出策略：若锁定是安全边界，就不应让明文密钥在锁定时可达；若为了常在线保持解锁，锁边界就被削弱。旧计划把无界面/无钥匙串解锁延后，首期只让桌面进程承担。S2 必须给出策略：只存密文后解密，还是专用解锁策略。 | S2 / S3 |
| 7 | 吊销使设备消息被拒绝 vs 持用户私钥的被吊销设备仍可冒充 | `REQ_20260918_9YNQV83FP0G2FV42`；`REQ_20260918_214C96FXNAE7W0G6` | 吊销只对**不持用户私钥**的设备成立；持用户私钥等于身份本身，YoChat 挡不住。旧规格已如实写明，产品文案不能承诺「吊销即安全」。 | S2 |
| 8 | 消息默认永久保存 vs 用户删除/墓碑/多设备历史不同 | `REQ_20260918_C2TDVVB9MGCY30KM`；`REQ_20260918_PE8XM7D0MPZ2XWTV`；`REQ_20260918_F9J932YWK907YPY7`；`REQ_20260918_K54NXXBZW1R6415F` | 永久保存是**默认**，不是保证；删除是显式、逐设备确认、不是远程擦除。不同设备的历史可以不同；验收是「按内容检索不到」，不是「物理不可恢复」。 | S3 |
| 9 | 设备列表对联系人可见 vs 用户层身份/成员名单对中转不可读 | `REQ_20260918_5A7WDB3CTV03FJTW`；`REQ_20260918_P7X1QGZCYA41GAQT` | 观察者不同：中转看设备端点，联系人看设备列表。设备 ≠ 用户；隐私告知必须逐字区分，否则验收对不上。 | S1 / S3 |
| 10 | 所有操作有界结束 vs 消息不因超时放弃等待 | 架构「每次对外操作有固定单调截止」；`REQ_20260918_537BK4VME23Y2GTW` | 截止约束**一次尝试**，不约束逻辑上的消息；重试继续，直到不可得/不再提供。模型要同时表达「尝试有界」与「逻辑等待可持续」。 | 跨批次 |
| 11 | 十万条首屏 500ms vs S1 一千条 <5 秒 | `REQ_20260918_3TK81N30WS2S6JWB`；ADR-0004 | 范围差异，不是矛盾。S1 的 1,000 条与 S3 的 100,000 条是不同验收；T1 不能把 100k 指标塞进 S1。 | S3 |
| 12 | 恢复短语「只在创建时展示」 vs 设置中通过应用锁再次查看 | `REQ_20260918_T1H63J7F3QD0WBBT` 的标题与正文 | 标题比正文窄；正文允许显式请求 + 应用锁校验后再次查看。属文档措辞缺陷，复用该条时要改标题。 | S3 |

还有两条不是矛盾，但容易被误读：

- **「消息默认永久保存」 vs 文件七天有效期**：旧文档已说明对象不同——消息是本地历史，文件是发送方共享位置上的临时可下载物。
- **「关系双方确认」 vs 「不定向邀请可被多人应答」**：一份邀请可以被多人分别应答，发起方分别确认；这不是多方关系，仍是多条一对一关系。

## 5. 难点

| # | 难点 | 为什么难 | 旧项目做到哪 | 建议 |
| ---: | --- | --- | --- | --- |
| 1 | 多设备设备列表合并 | 多台持用户私钥的设备可离线各签一个 `v+1`；只按版本/到达顺序都会分叉。旧设计改成「一组可合并的签名操作」：加入/改名取并集，吊销永久生效，同版本按 `(批次版本, 签名字节)` 确定排序。 | 已写出合并规则与冲突状态；有模型与真实回归。 | S2 先做合并与冲突展示，不做「自动选胜者」。 |
| 2 | 常在线设备 + 应用锁 | 要替离线设备收消息，就要有可用密钥；若锁定是安全边界，锁定时又不能解密。旧计划没有给出常在线设备的解锁策略，只把无界面/无钥匙串解锁延后。 | 首期由长期运行的桌面进程承担；无界面形态仍是占位。 | S2 只做「锁定时代收密文、解锁后解密」，或明确不做常在线；不要偷偷保持解锁。 |
| 3 | 乱序、缺失、重建 | 日志位置用于补齐，消息标识用于呈现；两套数不能混。缺失检测必须按日志位置，解密失败要重建并重传，重建还要限频。 | 两套数、三条补齐路径、墓碑、重建限频都写进了工程契约。 | S1 只保留一条路径；不要先在 S1 引入历史同步/大范围重发。 |
| 4 | 重发 vs 历史同步 vs 删除 | 小范围补齐自动、大范围要批准、历史同步要显式发起；删除要留墓碑、逐设备确认、不能承诺对方收不到。 | 入组基线、滑动窗、256 位置/10 分钟/7 天、批准队列、私有通道转达都已设计。 | S1 不做大范围重发；S2 做基线；S3 做批准与删除。 |

| 6 | 吊销传播 | 联系人可能长期离线；吊销只能随连接传播；判定用本地接收时间；持用户私钥的设备吊销不了。 | 设备列表 + 独立吊销声明 + 本地时间判定 + 如实告知。 | S2 做传播与本地判定；产品文案明确「收到之后才生效」。 |
| 7 | 本地加密与多实例隔离 | SQLCipher、钥匙串、应用锁代数、在途结果失效、每实例独立数据库密钥；同机多用户/多实例是真实使用方式。 | 已写出实例隔离、锁代数、在途结果丢弃、每实例密钥。 | S1 做单实例锁边界；S2 再做多实例，别在 S1 用「目录隔离」冒充安全隔离。 |

## 6. 建议与待裁决

### 6.1 对 S1 的建议

- **保留** 40 条中的安全不变量：签名、端到端加密、去重、时间不可信、诊断不含内容、锁边界。
- **明确降级** `REQ_20261103_GBNVF8ZY42F1DZX4`（跨作者最终全序）：要么在 S1 预算里实现，要么写进已知约束；不要静默忽略。
- **不要** 在 S1 做常在线、历史同步、吊销传播、大范围重发、删除、搜索、通知、十万条。
- **性能门先测** 1,000 条端到端 <5 秒，再谈 100k；不要用旧项目的 300 秒当基线。

### 6.2 进入实现前要拍板的五件事

1. **GBNV**：S1 是否要求跨作者最终全序？如果是，S1 的范围表要加一行成本；如果不是，写进已知约束，并在 T1 里标明不等价。
2. **常在线解锁**：锁定时代收密文，还是允许专用设备保持解锁？后者需要明确的安全告知与评审。
3. **恢复短语**：S3 才做，还是 S1 就给最小恢复？ADR-0003 目前把它列为非目标。
4. **隐私告知**：`Q0MQ` / `386R` 在 S1 做还是 S3 做？如果 S1 面向自用，可以后置；但一旦给别人用，就必须前移。
5. **删除/搜索**：S3 的一次做，还是拆成「本地删除」与「跨设备删除」两批？后者依赖墓碑与设备确认。

### 6.3 不要做的事

- 不要把旧 93 条当成待办清单逐条 burn down；那正是复盘里的范围放大。
- 不要为了「测试等价」移植全部旧测试；T1 只对 KEEP 功能等价，单元测试按新结构重写。
- 不要把旧 170 个模型搬进 S1；S1 只保留 5 个模型，协议定稿后冻结。
- 不要用「任务勾满」「编译通过」「AI 解释」当验收；验收是两台设备 100 条消息、重启不丢、断网重连，加上性能门与测试门。
