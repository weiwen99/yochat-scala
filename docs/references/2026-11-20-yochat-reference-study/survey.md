# 旧实现现状

> 对象：`~/projects/yochat-reference`（2026-11-20 的只读副本）
> 需求快照：本仓 `docs/spec/`
> 方法：读 `docs/product`、`docs/engineering`、主计划与验证摘要；数 Rust / Quint / 测试；不把任务勾选当产品验收。
> 结论：功能停在「加好友、单聊」；约 26.5 万行 Rust、170 个 Quint 模型、205/205 任务；macOS 路径大体可用，但发布级验收没有闭合。

## 1. 一句话定位

YoChat 是一个 serverless、端到端加密的 friend-to-friend IM。旧实现用 Rust + Tauri + Svelte，传输在 iroh 上、消息字节由 p2panda 承载，本地用 SQLCipher。它的能力边界仍是加好友与一对一单聊；多设备、历史同步、吊销、群聊、文件传输都没有成为可日常使用的完整产品。

本仓的重写不是「把 Rust 换成 Scala」，而是把范围从发布级首增量收回到 S1：两个用户、各一台设备、加好友、单聊、先落盘、重启不丢、断网重连。旧需求是后续版本的输入，不是本计划的基线。

## 3. 架构

旧实现的骨架是「纯状态机 + 执行器 + 适配器」：

```text
Svelte UI
   │ Tauri IPC
yochat-app（窗口 / 应用锁 / 钥匙串 / 通知）
   │
yochat-core
   ├─ step(state, event) -> (State, Vector<Effect>)   纯状态机
   ├─ Store（SQLCipher）                              存储适配
   └─ 网络接口
        │
yochat-net（iroh） ── 中转 / 直接连接 ── 对端
```

关键约束：

- 状态与待执行效果在同一个事务里落盘；事务提交后才执行效果；执行完成后再在另一个事务里标记完成。效果必须幂等或可去重。
- 状态只含可序列化纯数据；网络句柄、SQLite 句柄不进入状态。
- 每个聊天会话是一个设备组：参与方全部未吊销设备的并集；关系建立期间例外，只含邀请与应答各自携带的那台设备。
- 每台设备在每个会话维护一条只增日志；日志位置用于补齐，消息标识用于呈现、去重、删除与引用。两者是不同的类型，不能混用。
- 所有对外操作有固定截止；等待、队列、重试、广播都有上限。

## 5. 验收到了哪

主计划验证摘要里能核对到的证据与边界：

| 范围 | 已观察到 | 没有闭合的部分 |
| --- | --- | --- |
| Rust 分批回归 | Core 1119 项、Protocol 251 项、App e2e 430 项、Net lib 56 项 + 集成 61 项通过 | 不是一次完整 workspace 全量；部分历史结果按源码边界复用 |
| 形式检查 | 154 个模型文件、308 个配置、342 项时序性质；303 个条目复用既有完整证明 | 不是整条公共 verify 重新执行；模型与实现仍需对拍 |
| 原生 GUI（macOS） | 15 文件主套件 586.631 秒通过；冷加入、联系人接管等专项通过 | 真实系统通知点击、锁屏、默认五分钟自动锁满值未全部覆盖 |
| 性能 | 千条、万条分层有历史结果；12 次性能样本通过 | 一万条 App 进程重启没有作为当前整批通过；常在线 780 秒批次曾失败 |
| 平台 | macOS 定向验收 | Windows/Linux 实机、打包、通知未验 |
| 交付 | release `.app` 本地 ad-hoc 签名校验 | 不是 Developer ID 或公证；不是发布级安装包矩阵 |

最值得记住的两个数字：

- 2026-11-14 的一万条历史原生批次在 1800 秒截止时退出 124；写入 249.295 秒，最后同步进度 26/1734，尚未进入断网/重启。
- 2026-11-20 仍在开 SQL 查询效率计划，说明性能与索引问题没有在「宣布收工」时结束。

这两个数字不等于「所有功能都坏」，但它们说明：**任务完成、代码能编译、macOS 主路径能跑，与「产品验收完成」不是一回事。**

## 6. 为什么重写

复盘把失败归为四条，按杠杆排序：

1. **范围**：一句话需求被细化成 93 条需求、144 个 Quint 模型（复盘口径；当前目录有 170 个 `.qnt` 文件）、205 个任务、约 25 万行 Rust（当前 26.5 万）；未完成的尾巴几乎全是多设备。
2. **结构**：25 万行超出一人能读懂的范围；模块边界没有按变更频率切。
3. **验收**：三次「搞完了」都基于散文、行数或 AI 解释，而不是固定场景。
4. **目标漂移**：自用工具与 AI 编程练习用同一套产品标准结算。

重写的对策写在 ADR-0003 / ADR-0004：

- S1 只做两个用户、各一台设备、加好友、单聊、先落盘、重启不丢、断网重连。
- 生产代码 ≤30,000 行，模块 ≤8,000 行，文件 ≤2,000 行；每加一个功能删等量死代码。
- 1,000 条端到端 <5 秒；冷启动 p50/p95 ≤2s/≤4s；空闲内存 ≤800MB。
- 测试规格等价 T1：只对 KEEP 功能做等价；每个旧测试在 `test-parity.md` 有一行，不能静默删除或放宽。
- 这是最后一次整体重写；之后只做模块替换。

## 7. 读旧项目时的三个提醒

1. **`proposed` / `draft` 不是冻结规格。** 旧文档里有很多「待确认事项」，数值上限、时限、平台行为都还没有定案。把图或表当成验收证据会读错。
2. **任务勾选不是产品验收。** 205/205 只说明任务图上的工作项被勾掉；验证摘要明确保留了大量未验项。
3. **旧图是阅读辅助，不是规格。** flw 的六张图和术语表由外部模型生成，未经旧项目作者校对；它们帮助建立整体理解，引用前要对照 `docs/spec/` 和代码。
