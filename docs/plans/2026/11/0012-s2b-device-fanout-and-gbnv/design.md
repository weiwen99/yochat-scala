# Plan 0012 design: S2-B 设备列表、扇出与 GBNV

- 状态：design draft（2026-11-26）；尚未写实现代码。
- 范围：S2-B。建立一个主设备 + 至多一个只读伴随设备、联系人可见设备列表、B 直接向 A2 分发、签名吊销传播、两主设备作者的 GBNV。
- 前序：ADR-0003、ADR-0004、ADR-0006、ADR-0007、ADR-0008、ADR-0010；新决策见 ADR-0011。
- 产品依据：`docs/spec/product/users-and-devices.md` 的设备条目/设备列表/吊销条目；`docs/spec/engineering/keys-and-devices.md` 的签名域与合并规则；`docs/spec/engineering/messaging.md` 的最终全序与每设备回执。
- 本文不把旧实现（Rust/p2panda/iroh）作为代码复用对象；只取其已签字的需求与不变量。

## 1. 规模

| 维度 | 需求要什么 | 本计划产出 | 倍率 | 说明 |
| --- | ---: | ---: | ---: | --- |
| 需求条数 | 4 | 3 波 | 3× | 设备列表/吊销、直接扇出、GBNV；设备列表与吊销合在第一波 |
| 新表 | 0（S2-A 可复用设备/同步） | 4 | 不可比 | `peer_device_ops`、`peer_revocations`、`message_order`、`delivery_receipts`；`peer_devices` 作为投影表，合计 5 表但投影不另存原件 |
| 新列 | 0 | 0 | 不可比 | 逻辑消息键复用 `(conversation, authorDevice, authorSeq)`；不改正文、wire 或 AAD |
| 组件 | 1（现有 server/transport 内） | 4 | 4× | 列表合并、设备会话扇出、吊销投影、GBNV 排序；全部现有进程内，不新增服务 |
| 配置 | 0 用户可调 | 5 个内部常量 | 不可比 | 列表批次、吊销保留、乱序窗口、会话重试、依赖上限 |
| 工程师日 | 5–8（S2-A 规模） | 18–25（估算） | 3.1× | 新对端握手、每设备会话、迁移、E2E、S1/S2-A 回归；不含评审 |
| 发布波次 | 1 | 3 | 3× | B1、B2、B3；三波都过门才叫 S2-B |

组件 4× 已到纪律上限。解释：S2-B 需要同时改变成员资格（列表）、接收者（每设备会话）、拒绝规则（吊销）和展示顺序（GBNV）；这四件事不能压成一个职责，但也不新增第五个服务或第二套 runtime。工程师日 3.1× 按一人估算；评审、外部审计、跨主机网络矩阵不计入。

## 2. 范围与非目标

范围内：

- 每个用户：1 台可写主设备（A1/B1）+ 至多 1 台只读伴随设备（A2/B2）。
- 设备条目、设备列表、签名的加入/改名/吊销操作；联系人可见设备列表。
- 主设备到对方主设备/伴随设备的每设备会话；伴随设备只读接收和 ACK，不发送业务消息。
- 用户签名吊销原件向联系人分发；收到后拒绝被吊销设备此后到达的消息，既有历史保留。
- 两个主设备作者的 GBNV：同一条有效消息集合在各设备得到同一全序；因果前驱未到不跳过。
- S2-A 的 device-sync、JoinManifest、1k 同步、本地移除继续保留；S2-B 的设备列表/吊销和直投是增量。

非目标：

- 历史同步、用户私钥同步、恢复短语、群聊、文件传输、移动端、第三台写设备。
- 联系人可见的“所有历史设备”或远程擦除；吊销只影响收到原件后的新消息。
- 让 A2 变成可写设备、持有用户私钥或接管 A1。
- 混合版本下的新保证；S2-B 默认关闭，只在双方声明支持后启用。
- 发布级目录/设备发现服务；设备列表只随已建立关系同步。

## 3. 复用与新增

| 能力 | 复用 | 为什么不另造 |
| --- | --- | --- |
| 用户/设备身份 | `IdentityKeys` v2、`devices`、`DeviceAuthorization` | S2-A 已有设备密钥与授权；只需增加联系人侧投影 |
| 存储/加密 | ADR-0007 的 store key、AAD、锁代际 | 新表沿用同一 store；不新增数据库或第二套密钥 |
| relay | `RelayPayload` opaque kind、`RelayClient` | 不新增 relay 服务；列表/吊销/设备会话是同一设备寻址 |
| 伴随同步 | S2-A `DeviceSyncProtocol` | 继续作为 A1→A2 的展示副本路径；S2-B 增加 B→A2 直投，不删旧路 |
| 顺序等待 | S1 的按作者 gap、重发、通道重建 | GBNV 只增加跨作者前驱边，不重写补齐路径 |
| UI | 现有联系人详情、设备面板 | 设备列表放进详情/设置，不新增第四屏 |

## 4. 数据与锁序

### 4.1 表

| 表 | 内容 | 保护 |
| --- | --- | --- |
| `peer_device_ops` | 每个联系人用户的签名设备操作原件：用户、操作类型、设备、别名、时间、列表版本、签名 | 原件按用户隔离；AAD 绑定用户/操作摘要；不静默删除 |
| `peer_devices` | 从原件合并出的当前设备投影：用户、设备、别名、加入时间、最后版本 | 只读投影；与原件同事务更新；不独立签发 |
| `peer_revocations` | 用户签名吊销原件：用户、设备、时间、列表版本、签名 | 永久保留；同用户/设备唯一；不因旧列表或改名删除 |
| `message_order` | 会话、作者设备、作者序号、逻辑消息键、Lamport、因果前驱摘要 | 与消息/正文同事务写入；有界依赖 |
| `delivery_receipts` | 会话、逻辑消息键、收件设备、状态、时间 | 每设备独立；一个设备 ACK 不替另一个结清 |
| 逻辑消息键 | `(conversation_id, author_device, author_seq)` 的规范编码；不新增列 | 不含正文；不改 wire/AAD |

S2-B 不把 `peer_devices` 当权威：它永远是 `peer_device_ops` 的投影；吊销/旧列表冲突时以原件合并规则为准。

### 4.2 全局锁序

沿用 ADR-0007 的顺序，在 `devices` 后插入联系人设备表：

```text
invitations → contacts → conversations → sessions → messages → message_order
            → devices → peer_device_ops → peer_devices → peer_revocations
            → companion_messages → device_sync → delivery_receipts → meta
```

- 收到设备操作：写 `peer_device_ops`，同事务重算 `peer_devices`；不持有会话/消息锁。
- 收到吊销：写 `peer_revocations`，同事务更新 `peer_devices` 的 revoked 投影；不修改既有消息。
- 追加业务消息：写 `messages` + `message_order` + `delivery_receipts`（待发目标）同事务；然后才发。
- 收 ACK：只写对应 `delivery_receipts`；不重写消息正文，不跨设备结清。
- 每设备会话：`sessions` 已有行；设备会话 ID 绑定双方 device；不新增会话表。

### 4.3 迁移

- 当前 schema 3。升到 4：新增 4 张表；旧消息的逻辑键直接由 `(conversation, author_device, seq)` 构造，`lamport` 初始为 `seq` 的局部单调值，因果前驱为空；仅用于旧消息展示，不伪造跨作者因果。
- v3 夹具必须含 S2-A `devices`/`device_sync`/`companion_messages`/`messages.sync_seq`；迁移后 S1/S2-A E2E、查询计划、锁定行为不变。
- 迁移失败保留旧库并 `UnsupportedSchema` 失败关闭；不自动降级；回退只走备份。
- S2-B 默认关闭：设备/联系人元数据声明 `s2b=1` 才启用；关闭时旧 S2-A 路径继续工作，列表操作不生成、不发送。

## 5. 协议

### 5.1 设备列表控制

新增 `RelayPayload.DeviceList`（opaque、同一 relay 设备寻址）。内容为一条或多条签名设备操作，批次有界；接收方逐条验签、按用户隔离、合并投影。签名域与字段沿用 ADR-0011/产品规格：

```text
device-entry: devicePriv(userPub, devicePub, joinedAt)
device-list:  userPriv(userPub, version, operations, issuedAt)
```

- 联系人只接受对方用户的签名；设备条目自签名只证明设备持有，不证明归属。
- 加入/改名/吊销按操作标识取并集；吊销永久；版本只用于补齐。
- 同一用户同版本不同签名保留冲突并告警，不按到达顺序取一个。
- 列表同步在关系建立、重连、设备变更时触发；设备列表不随每条消息发送。

### 5.2 wire 与能力声明

- S2-B 使用新的 `WireFrame` v2 header：`orderLamport` 与有界因果前驱摘要随消息签名；旧 S1 `WireFrame` 不解析新字段，S2-B 不向未声明能力的对端发送 v2 业务帧。混合版本走 S2-A 路径，不声称 GBNV。
- 设备操作带 `features` 位（至少 `s2b=1`）；双方设备列表都声明后才启用直投/GBNV。未声明时保留 S2-A 路径，不伪造升级。`features` 与列表操作同签名，不单独接受调用方声明。
- 控制帧使用新的 relay opaque kind，复用现有 `RelayClient` 设备寻址；不新增 relay 服务。

### 5.3 设备会话与直投

- 主设备 A1/B1 在收到对方完整设备列表后，为对方的当前设备建立会话；对主设备沿用 S1 S1 会话；对伴随设备建立**只读设备会话**。
- 只读设备会话握手由设备密钥签名，授权依据是对方用户签名的设备列表 + 未吊销；双方各用 X25519 ephemeral 交换并绑定用户、双方 device、设备列表版本与会话用途，派生独立会话密钥。伴随设备只收不发业务数据，只发设备级 ACK/控制确认。握手拒绝错用户、未在列表、已吊销或列表版本落后的设备。
- B1→A2 的消息与 B1→A1 的消息是同一逻辑消息在不同会话的两份密文；A2 直接验证、解密、落盘；A1 的 device-sync 路径仍可送同一逻辑消息，A2 按逻辑消息键去重。
- `delivery_receipts` 按 `(conversation, authorDevice, authorSeq, recipientDevice)` 记录；发送方按当前设备列表保持待补发目标，任一设备 ACK 只结清该设备。界面可显示“已收到”当任一有效设备确认。
- 设备列表变化时，新目标从下一条消息开始；不重发历史，不追认旧设备。

### 5.4 吊销

- 用户签名吊销原件随设备列表发送；接收方验签后写 `peer_revocations`，立即从投影移除/标 revoked。
- 发送方对已吊销设备停止新发；被吊销设备不再进入新会话。
- 接收方按本机收到吊销时刻拒绝该设备此后到达的消息；已接受的历史保留并标记来源已吊销；不远程擦除。
- 本机 A2/B2 被自己的用户吊销时，主设备停止同步/直投；伴随设备不能继续解密未来消息。用户公钥和安全码不变。

### 5.5 GBNV

- 作者（仅 A1/B1）为每条消息签名 `lamport` 和因果前驱集合；前驱至少包含发送时已见的对方最大 `(device, seq)`。
- 统一键：`(lamport, authorDevice, authorSeq)`；同作者顺序不变；并发按设备公钥与序号打平。
- 接收端先验证签名与当前授权，再等待因果前驱；前驱未到时等待，不显示后继；窗口/依赖上限超出触发通道重建/补发，不丢弃。
- A1/B1/A2/B2 对同一有效消息集合计算同一键；A2 的两路副本按逻辑消息键去重后参与排序。
- 不引入全局时钟或第三方排序服务；物理时间仅显示。GBNV 只覆盖当前两个主设备作者，不声称覆盖未来群聊/第三写设备。

## 6. 模型冻结

S2-B 改成员资格、设备会话、吊销与排序，必须在生产实现前新增 Q8 设备同步模型（设备操作合并、吊销单调、每设备 ACK、GBNV 因果/并发），并从旧 `devices.qnt`/`order_*.qnt`/`revocation_*.qnt` 映射性质。Q8 变更单独一轮并由人签字；Q1–Q7 不改。S2-A 的 Q7 保持冻结。未签字不写 B1 生产代码。

## 7. 实施波次与门

### B1：设备列表与签名吊销

- 新表/列、签名操作、联系人控制帧、联系人详情 UI、本地/联系人吊销拒绝。
- 门：G1/G4/G6；旧 S2-A 与 S1 回归。

### B2：直接伴随扇出

- 只读设备会话握手、B→A2 直投、每设备 ACK、A2 直接落盘与 UI 合并。
- 门：G2；B1 的列表/吊销门重跑；A2 仍不能发送。

### B3：GBNV

- 逻辑消息键、Lamport/因果前驱、统一排序、跨作者等待与测试。
- 门：G3；全量 G1–G7；S1/S2-A/S2-B E2E 同时绿。

每波单独可回退：关闭 `s2b` 开关回到 S2-A；新表保留但不再写入；不删旧数据。三波都完成才声明 S2-B。

## 8. 安全与失败

| 场景 | 行为 |
| --- | --- |
| 伪造/错用户设备操作 | 静默丢弃；不落投影、不产生响应 |
| 同版本不同签名 | 保留冲突，不自动选胜者；界面告警 |
| 旧列表缺吊销 | 合并后吊销仍生效，不复活 |
| 被吊销设备直投 | 收到原件后拒绝其后到达；不回应 |
| 伴随设备尝试发送 | 服务端/UI 拒绝；不生成业务消息 |
| 因果前驱缺失 | 等待/补发/重建；不跳过 |
| Lamport 伪造/回退 | 签名验证 + 同作者序号/当前会话；异常拒绝，不重排已提交 |
| 迁移失败 | 旧库不变，失败关闭；不自动降级 |
| 设备列表/吊销日志 | 不含正文/私钥/联系人名；原件按用户隔离 |

## 9. 已知约束

- 联系人离线时可能继续向旧设备发送，直到收到吊销；这是无中心服务的边界。
- 伴随设备依赖主设备在线建立/更新会话；不能接管发送。
- GBNV 只覆盖两个主设备作者；不覆盖群聊或多写设备。
- 历史同步、用户私钥同步、恢复短语、群聊/文件不在本计划。
- S2-B 与 S1/S2-A 混合时不提供新保证；默认关闭，升级后再开。
- 迁移/回退只走备份；没有自动降级。

## 10. 测试与验收

- T1：S2-B 继承 S2-A 的映射签字（2026-11-26）；新增 `S2B#1`–`S2B#5`，见 `test-parity.md`。
- 单元/属性：设备操作合并、吊销单调、GBNV 因果/并发、每设备 ACK、迁移夹具。
- E2E：A1/B1/A2/B2 四进程 + 真实 relay；四个 T1 场景；S1/S2-A 全量回归。
- 性能：沿 S1 1k/10k 与 S2#2 1k 同步；S2-B 直投 1k 在 5s 内（A1→A2 与 B1→A2 各自），空闲内存仍按单实例 ≤800MB 记录。
- 只写可观察结果；线程/并发交错进实现测试，不塞进 UI 验收。

## 11. 验收正文

1. A1/B1 建立关系，A1 加 A2；B1 详情看到 A1/A2 的设备列表，A1/A2 看到 B1。
2. A1/B1 并发发送；A1/A2/B1 的同一消息集合顺序一致；A2 不因缺前驱先显示后继。
3. A1 吊销 A2 并发送吊销；B1 停止向 A2 新发；A2 不能解出此后消息；A1/B1 继续收发；历史保留。
4. 重启四台进程后设备列表、吊销、顺序、历史仍正确；A2/B2 仍不能发送。
5. 关闭 `s2b` 开关回到 S2-A；S1 1k/10k 与 S2-A 1k 同步门不回退。

命令在实现后固定为 `./mill server.s2be2e`、`./mill server.s2bperf`、`./mill store.test`、`./mill server.test`、`./check.sh`；未实现前不写 PASS。
