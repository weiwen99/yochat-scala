## 规模与交付边界

D1 要求先量规模。本计划的约束不是「35 条都要做」，而是仓库已有的硬上限：

| 发布波次 | 1 | 3（S3-A / S3-B / S3-C） | 3× |

倍率解释：

- **需求 0.4×** 是本次规划的核心结论。35 条全做，按分项估算需要 8,300–12,300 行生产代码，
  累计 27,900–31,900 行，**会撞穿 30,000 行上限**。所以 S3 必须是子集；延后的 19 条不是
  「不想做」，是按预算排不下，且其中多数还需要协议或密钥管理的单独 ADR。
- **表 +2**：拉黑需要一张只存公钥与理由的记录表（删除联系人后仍要保留）；「删除历史」跨本人
  设备只产生指令、由各设备确认，需要一张待确认指令表。两表都在现有 `store` 迁移序列内追加。
- **组件 +2**：拉黑名单是新的设置面板；搜索需要独立服务（加密存储下的检索边界，见下）。
  其余功能挂在现有面板与路由上，不新增组件。
- **配置 +3**：都是本地偏好，不参与协议，不进同步。
- **波次 3×**：三波各自可独立交付与回退，理由见「设计」。
- **工程师日**：估算，不是实测。以现有 S2b（0012/0013）的交付节奏为参照。

## 背景与缺口

S1/S2 之后，产品缺的是两类东西：

1. **关系的结束**。现在只能建立关系，不能拉黑、不能删除、不能解释「删了之后对方会看到什么」。
   这是 `docs/agents/verification.md` 明确留给 S3 的功能，也是用户日常最可能先撞上的缺口。
2. **发布级的最低可见性要求**。通知里能出现什么、界面上能不能看出走的是中继、键盘能不能
   走完主流程、用户在使用前知不知道中转能看到什么——这些在自用阶段可以不做，给别人用之前
   必须做。

其余候选（恢复短语、消息删除与墓碑、搜索与十万条、陌生对端预算、大范围重发批准、公开张贴、
在线状态、引用回复、联系人分组、公开别名头像）依赖更重的东西：密钥管理、协议状态、或一个
我们还没有的功能（如 presence）。逐条处置见下。

## 设计

### S3-A 关系结束

**数据**

```text
blocked_peers(user_pub BLOB PRIMARY KEY, sealed BLOB NOT NULL, version INT, created_at INT)
  sealed 里是理由码与拉黑时间；公钥明文作主键，与 contacts 的存法一致。
device_commands(id BLOB PRIMARY KEY, kind INT, sealed BLOB NOT NULL, state INT, created_at INT)
  「删除历史」跨设备只落一条待确认指令；state = pending | confirmed | declined。
```

不新增 `contacts` 列：联系人载荷已是密封 blob，拉黑标记放不进关系语义（删除联系人后关系没了、
拉黑还在），所以独立表。

**入口与顺序**

- 入站：在现有准入链（匹配联系人 → 授权校验）**之前**加一级 `blocked_peers` 查询。命中即丢弃：
  不落盘、不推进游标、不产生任何应用层出站（包括拒绝）。丢在最前，是为了让「拉黑期间对方的
  消息不增长本机存储」这条验收成立。
- 出站：发送前查拉黑表，命中则本地拒绝并返回明确错误码（`BlockedPeer`），不产生帧。
- 拉黑/解除/删除都是本地关系操作，先写本地（write-before-send），再由现有 `device_sync`
  把「关系变更」同步给本人其他设备。**删除历史不走 `device_sync` 自动执行**，只落
  `device_commands`，由各设备确认后才 DELETE。
- 锁序：`blocked_peers` 与 `contacts` 同层，按 `user_pub` 全序；`device_commands` 只在短事务里
  单表读写。任何路径不得先持会话行再申请 `blocked_peers`。

**不变量**

1. 被拉黑者的帧不推进任何游标，因此解除拉黑后现有 Gap 机制能要求重传——这是「补齐」的实现
   基础，不是新协议。
2. 超重发窗口的部分不能靠重传补齐：界面必须说明「需要对方批准或改走历史同步」，且对方若已
   删除，要给出可验证的「不再提供」答复（`9MKG1QMBXQAG6C12` 的采纳部分）。若现有控制帧没有
   可验证答复，这一小段是本计划唯一的线格式新增，需在实现前单独确认。
3. 删除已拉黑的联系人 → 关系删除，`blocked_peers` 记录保留，直到用户在拉黑名单里显式移除。
4. 重新添加 → 新关系，`safety_verified = false`；联系人刷新（换设备/吊销）→ 保留拉黑与校验。
5. 任何界面不得声称「对方不会知道」；拉黑确认页必须包含两条说明（可推断、绑定单把公钥）。

**失败模式**

- 写拉黑失败 → 整个操作失败并回滚，不允许「本地已拉黑、其他设备没同步」的中间态被当成成功。
- 解除拉黑后补齐失败（窗口外 / 对方不再提供）→ 会话不得停在「等待」；界面给出原因与下一步。
- 删除历史的确认指令在设备上失败 → 该设备保留历史并显示未完成，不静默吞掉。

### S3-B 发布级可见性

- **通知内容边界**（`G3JQAH0SXEXVDATA`）：现状是主进程只收到联系人标签与「有一条新消息」。
  本波把它变成有断言的契约：E2E 断言通知载荷不含正文、不含公钥；新增本地偏好「通知是否显示
  联系人标签」，默认显示。
- **连接方式可见**（`377PNHQWJ8PGCN80`）：只有中继一条路径，界面显示「经中继」与中继是否在线，
  复用现有状态，不加协议。
- **可达性基线**（`3AEMNVEGME49ZT2R`）：键盘走完「解锁 → 加好友 → 比对安全码 → 发消息」主流程，
  焦点顺序可预测；对比度沿用现有 `contrast-smoke` 门。WCAG 完整审计仍不在范围。
- **使用前告知**（`Q0MQBNAVS1TB1PBW`）：首启一页，逐条列出中转可见（端点、时间、帧数、密文）、
  联系人可见（设备列表，S2b）、以及「拉黑可被推断」「我们不提供在线状态」。已读版本记本地，
  版本升级后重新提示。

### S3-C 历史可用性（阻塞）

本地消息正文是应用层 AEAD 密封的（`messages.body` 是密文）。所以「全文搜索」先要回答一个
**存储层的取舍**，三条路：

- **A 有界解密扫描**：按会话分页解密后在内存里匹配。不新增明文索引，静态加密不变；代价是
  搜索结果延迟随历史增长，需要一条可测的上界。
- **B 明文倒排索引**：快，但把正文以明文落到库里，等于放弃静态加密的一半。除非改存储加密
  方案，否则不接受。
- **C 不做搜索**：把 100k 只当「滚动与首屏可用」，搜索留到以后。

`3TK81N30WS2S6JWB` 的十万条指标同样不能直接继承旧项目数字：它是旧验收口径，本计划只把它
当候选门，需 owner 与一次基准共同确认（ADR-0004 要求阈值变更走 ADR + 签字）。
