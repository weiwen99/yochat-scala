# 总体架构

<!-- tao:section overview -->
## 概述

本篇界定 YoChat 由哪些部分构成、它们之间如何划界，以及贯穿全局的执行模型：核心
逻辑写成不做输入输出的纯状态机，由一层执行器负责与网络、存储、时钟和随机数打交道。
各能力自身的设计见[用户与设备](keys-and-devices.md)、[好友交换](contact-exchange.md)、
[消息](messaging.md)与[本地存储](local-store.md)；技术选型、加密方案、状态机风格与
验证策略的理由分别见 decisions 目录下的四份决定。

范围为首个交付增量：桌面三端上的用户与设备、通讯录、一对一与自己的聊天会话。
群聊与文件传输不在本篇范围，但本篇的划界不得使它们无法接入（{need}`TASK_20260919_MN1FTNNX11BEA7GQ`）。

## 边界与架构

### 构件

- `yochat-core`：全部领域逻辑。不依赖 Tauri，不含界面假设，不持有网络句柄。
  内部分为纯状态机与适配两层；存储适配（SQLCipher）在适配层内，网络只在这里定义接口。
- `yochat-net`：窄接口的网络实现。它依赖 `yochat-core`，反向不依赖。
  传输在 iroh 之上；p2panda 产出的是被传输承载的字节，位置在这条接缝**之上**，
  随消息模型落地。
- `yochat-app`：桌面外壳（Tauri 2）。承担窗口、应用锁交互、系统钥匙串接缝，以及
  把核心的事件流转成界面能消费的形式。系统通知**直接调用各平台的系统通知接口**：官方通知
  插件在桌面端不交出点击事件，而「点通知跳到对应会话并定位到那条消息」要的正是它。第一期
  只在 macOS 上实现与验证，Windows 与 Linux 在持续集成启用之后补上（用户 2026-09-24 定）。
- `yochat-node`：无界面二进制，用于常在线设备。它与 `yochat-app` 并列，复用同一个
  `yochat-core`，不共享任何界面代码。**第一期常在线职责由长期运行的桌面进程承担**，无界面
  形态连同它在没有系统钥匙串时如何解锁以后再定（用户 2026-09-24 定）；在那之前它只是一个
  证明「不链接界面依赖」在构建期成立的占位。
- `ui`：Svelte 5 + Vite 前端。

桌面收发与补齐由界面定时节拍驱动。macOS 14 及以后显式关闭 WebView 的后台节流，避免窗口被遮挡或最小化后定时器停顿，导致常在线接收及最后一条日志的补齐延迟；该配置由 Tauri/Wry 的 `backgroundThrottling: disabled` 实现。旧版 macOS 和其他平台不支持这一配置，后台持续执行尚未在这些平台验证（{need}`TASK_20260919_80NB4PK0KR53XJVS`）。

界面维护每个组件生命周期最多一轮在途，聊天推进、私有通道刷新及历史推进逐阶段等待，每阶段派发前重新采时；单阶段失败不阻断后续阶段，卸载后不再派发。慢原生调用仍占用本轮，不能用Promise超时竞赛提前开门；停止组件不等于取消已经发出的RPC，旧组件完成不能释放新组件的门。`Date.now()`不是单调时钟，固定网络/SQL截止仍由后端单调时钟负责；继续推进依赖原生调用有界结束及Promise公平调度（{need}`TASK_20261102_HG0948Q7GA70QBQ5`）。

`yochat-node` 之所以是一个独立构件而不是一个运行参数，是为了让"常在线设备不需要
界面"这件事在构建期就成立：它不链接任何界面依赖，因此也不可能意外依赖界面状态。

`yochat-net` 之所以是一个独立 crate 而不是 `yochat-core` 里的一个模块，是为了让
"状态机看不到网络库的类型"这件事**在依赖图上成立**，而不是靠每次改动时读一遍签名：
`yochat-core` 的依赖图里没有 iroh 与 p2panda，它的公开签名因此在物理上写不出这些类型。
存储没有这样拆，是因为两者在这一点上不同——`rusqlite` 的句柄被 `Store` 完全包住，
没有任何公开签名需要提到它；而网络库的类型会自然地出现在连接、地址与错误上。

传输适配提供设备级屏蔽集合：更新时清除这些设备的排队入站、关闭连接、唤醒并取消等待中的发送；在途许可一经撤销不可恢复，立即解除也不会复活旧任务，新任务取得新的许可；许可索引使用弱引用并清理已结束项，不按历史设备数累积；后续发送在发现与连接前被本地拒绝，重新建立的入站连接也不进入应用队列。连接清理按具体连接标识判定，旧连接退出不能删除刚建立的新连接。用户公钥到设备集合的解析、持久化及启动时恢复由应用层承接；传输层测试本身不证明这些产品接线已经完成（{need}`TASK_20260919_FMT2MTRTWPK5HMG5`）。

### 三层划分

最内层是纯状态机：对每一处顺序或并发敏感的逻辑，提供一个 `step(state, event)`，
返回新状态与一串待执行效果。它不读时钟、不取随机数、不做输入输出。

中间层是执行器：驱动状态机、持久化状态、执行效果、把结果作为新事件送回。

最外层是适配：网络（p2panda 与 iroh）、存储（SQLCipher）、时钟、随机数、钥匙串。
它们只被执行器调用，对状态机不可见。

### 崩溃安全的执行顺序

执行器的顺序是本篇最要紧的一处约束。状态推进与"待执行效果"必须在**同一个事务**里
落盘（{need}`TASK_20260919_5X1SXR1ZNC2XQAWC`），效果在事务提交之后才执行，执行完成后再在另一个事务里标记完成。

两种更简单的顺序都不成立：先执行效果再存状态，崩溃后效果已经发生而状态没有记录，
重启会重做一遍；先存状态再执行效果并把效果丢在内存里，崩溃后状态已经推进而效果
永远不会发生。共存的写法把问题收敛成一件事——效果可能被执行多次（{need}`TASK_20260919_5X1SXR1ZNC2XQAWC`），因此**每一个效果
都必须幂等或可去重**。这正是规格要求消息去重的根本原因，而不只是为了应对多路径投递。

五类效果里，"起定时器"的幂等含义不自明，必须单独写死（{need}`TASK_20260919_5X1SXR1ZNC2XQAWC`）：每个定时器由（状态机实例，
等待种类，等待对象的标识，授权代数，**尝试序号**）派生出一个稳定标识，"起定时器"按该
标识幂等，"定时器到期"事件按该标识去重；去重集合是 `State` 的一部分（或与消费该事件的
状态推进同事务写入），并在该等待结束时清理，以免无界增长。

每次对外操作都有固定的单调截止期限，成功、明确失败、超时或取消均结束本次执行；不能依赖重启来解除挂起。网络发送的三十秒期限从接受发送时开始，包含命令排队、等待共用拨号锁、连接、开流、写入及等待对端读取；阶段推进不延长期限。单独连接唤醒沿用十秒期限，同样包含排队与锁等待。取消优先于同时就绪的超时和完成，期限届满优先于同时就绪的完成；操作结束时取消未完成的异步过程。时钟推进与运行时得到调度是明确前提，操作本身不在内部无限重试。网络超时不表示对端一定没收到，原件和去重身份保持不变；消息的业务送达确认及后续可靠重放仍由原有状态机负责，不能把超时当作成功（{need}`TASK_20260919_5X1SXR1ZNC2XQAWC`）。

尝试序号不可省：它由状态机维护、每起一次定时器递增，随状态同事务落盘。少了它，同一次
等待的第二次到期与第一次同标识——按"起定时器幂等"第二个定时器根本起不来，按"到期去重"
第二次到期被当作重放丢掉，两种读法下重试循环都断在第一次，兜底重发这条离线送达的路也
就没了。没有这一条，崩溃就能突破超时动作的上限——定时器效果
已提交而未标记完成时进程终止，重启后效果被重放，于是同一次等待起了两个定时器、到期
产生两个事件，而状态机内的计数器只按事件计数，看不出它们来自同一次等待。一个能诱导
对方崩溃的攻击者由此获得放大本机资源消耗的手段，正是有界性那条规则要排除的事。

### iroh 地址映射的有界生命周期

维护固定版本的最小iroh vendor补丁并保留许可证与差异清单。远端actor退出并不释放Endpoint全生命周期保留的地址映射，因此并发连接上限和空闲actor回收不能替代映射池容量（{need}`TASK_20261101_9ZM9FK8YG0K5F2HY`）。

补丁先建模再实现：地址映射池固定容量，容量或地址代数耗尽立即拒绝，不排队、不无限生成重试；使用中的映射由明确持有者保护。未使用映射按单调时钟的固定期限回收，重复查询不续期；回收与使用的登记同锁。映射身份在进程内不复用，旧数据和旧释放动作不能命中新分配身份。模型的有限论域及公平时钟/回收前提须明示，实际 actor、QUIC 连接、路径和排队数据的持有范围逐一核对；单纯限制表长不能冒充全进程内存或联系人服务保证。只在同一时刻验证有限上限，不能把空闲回收当容量限制。

中转映射也须保留已知对象首次连接的空间。保留资格须传入内部映射准入，不能只在应用连接层分类；“已有联系人连接仍能传输”不覆盖陌生Initial耗尽映射后联系人的首次连接（{need}`TASK_20261101_H8R6C2M9V5Q7X4NP`、{need}`TASK_20260919_S5A75YBBYQ6HGGRA`）。

YoChat启用时端点与中转映射各总容量4096、陌生分配至多128；自定义传输未在YoChat启用，仍保留原固定总预算。普通iroh调用未启用分类策略时也保持原固定总预算。资源分类读取现有、已验证设备事实的共享视图，不另复制全量联系人；本机传输地址有保留资格。容量与分类争用立即失败，不等待锁，分类不授予任何发送或接收权限。条目按分配时类别计费，后来成为已知对象可以原子提升并返还陌生名额，提升不续期；撤销资格不强行回收使用中条目，旧分配在固定期限和持有者释放后退出。保留空间只在既有保留占用尚未耗尽总预算时成立，不承诺无限已知对象同时连接。

重连轮询在同一事务内领取至多32个目标并取得这些用户/设备的资格，不为纯连接复制整份关系、设备、吊销及删除引用表。资格沿用已建立未拉黑关系、本人或对端设备正面归属及所属用户吊销；引用删除只约束引用正文发送，不约束纯连接。领取、事实读取、本人名单流式筛选和SQL共享五秒工作截止；事实读取错误或超时回滚领取，不消耗原三十秒重试间隔，不猜测授权结果，不新增内部无限重试；全局保留及禁止名单按下段统一刷新（{need}`TASK_20261101_9V2DSHS7EAVG63CM`、{need}`TASK_20260919_S5A75YBBYQ6HGGRA`）。

全局网络资源集合只投影保留资格和设备级传输屏蔽，不借用含删除引用/完整关系字段的发送授权快照。本人正面资格来自当前签名名单，对端来自已知正面绑定及该用户的关系/吊销；已确认应答仍按精确用户/设备的邀请截止加宽限判定，本机不进入保留集合。删除关系后的持久拉黑继续参与禁止集合。两个集合在同一SQL快照内取得，逐行筛选和16KiB名单流共用五秒工作截止，不读取无关消息、墓碑、公开资料或私有备注；失败不返回部分集合，不猜测授权。输出集合随已验证设备事实规模增长，不引入联系人数量上限或近似识别；有限查询投影与整进程压力/RSS是不同验收范围（{need}`TASK_20261101_A9VDMFEFDSEEV5KB`、{need}`TASK_20260919_S5A75YBBYQ6HGGRA`）。

### 网络控制请求的有界调度

单个对端的满邮箱或尚未结束的旧actor不得阻塞全局Socket调度。控制消息入队立即接受或失败，关闭sender后的join由独立清理事件推进，旧任务结束前不启动同身份的新actor。地址查询从调用开始共享固定十秒截止，排队和等待回复不分别续期；每个actor至多保留16个查询等待者，取消及到期者不再阻止空闲退出。关闭、容量满及到期只结束当前请求，不影响其他对端；连接注册与诊断读取同样有界，不把应用外层超时当作内部资源释放（{need}`TASK_20261101_M6R5V4X2J9Q7C8NP`、{need}`TASK_20260919_S5A75YBBYQ6HGGRA`）。

Quint 先检查两对端、三请求、容量一、有限时钟下的立即拒绝、固定期限、取消释放、关闭/清理/重启身份和公平时钟下终止；再对实际等待集合逐状态回放，并用真实 actor 邮箱及本机端点确认集成。模型不保证网络成功、任意调度下实时上界，也不替代全进程内存和联系人优先级验收。

### 并发

单个 tokio 运行时。每个聊天会话按实际`InstanceId`隔离业务状态，状态机调用串行，
业务状态内部不持有锁或运行时句柄。同一解锁身份的会话共享设备`Protocol`，由身份工作区协调独占推进。

**状态机串行不等于密码状态可以并发推进。** 网络效果可以并发，但同一条棘轮及共享设备
`Protocol`上的操作仍须串行（{need}`TASK_20260919_N0BEHW57ZGWS5B4A`）。提交分别核对
会话SQL版本与设备`ProtocolRevision`；冲突或失败不发布候选，受影响状态从已提交数据恢复。
不能仅靠“每个聊天会话一个状态机”保证设备密钥不会被跨会话覆盖。

### 效果的失效条件

效果落盘之后、执行之前，世界可能已经变了：用户删除了那条尚未送出的消息、拉黑了
对端、或吊销了目标设备。幂等只保证不重复执行，它完全不保证此刻仍然**允许**执行。

因此每个待执行效果携带一个授权代数，并在真正出站之前重新检查一次当前授权：目标
是否仍是联系人、是否已被拉黑、目标设备是否仍在设备列表中、它所引用的消息是否已被
删除。任一不成立即丢弃该效果并记录，而不是照旧发出去。

### 实例隔离

一台机器上可以并存多个用户及同一用户的多个设备实例。每个实例拥有独立数据目录、
数据库密钥与应用锁；同一OS用户可能读到另一个目录的字节，隔离承诺是不能据此解密。
产品实例选择先锁定原窗口，再打开固定作用域的新进程，见[独立窗口决定](decisions/local-instance-windows.md#DOC_20261106_B7NWNHEN8X4F4NG1--decisions)（{need}`UC_20260918_VX22BC4VKGYQ6MN2`）。

## 接口与数据契约

### 状态机契约

    fn step(state: State, event: Event) -> (State, Vec<Effect>)

`State` 必须可序列化且往返相等，不得包含连接句柄、文件句柄或任何指向运行时资源的
引用（{need}`TASK_20260919_5X1SXR1ZNC2XQAWC`）。`Event` 的构造者是执行器，包含：外部到达的数据、用户动作、定时器到期、**某对端由
不可达转为可达**、以及先前效果的完成或失败结果。可达性变化是字母表里**必须有**的一项，
不能并进"外部到达的数据"或"定时器到期"：`models/resend.qnt` 以含与不含它两种字母表
各跑一次，**不含它的那一种使离线送达的活性被证伪**——纪元不再切换，预算便不再重置，
双方都回到线上也再没有任何动作会重发。`Effect` 分五类：对外发送、持久化、起定时器、取随机数、
通知界面。时间与随机数只能作为事件进入，状态机内不得读取。

### 跨层的量各有独立类型

**跨越层边界、语义不同而底层表示相同的量，必须各有独立的类型**（{need}`TASK_20260923_PN0FFV6WZZY4PAT5`），彼此之间不提供转换、
不提供算术；由编译器承重，不靠命名约定，也不靠注释提醒。

依据是一次真实的缺陷：传输层的「日志位置」与产品层的「消息标识」都是无符号整数、名字
都带个序号，于是补齐机制误按后者检测缺失——而被加密定序层扣住的操作在那一刻只有前者，
缺失因此检测不到，整套重发机制在真实传输上从不发动（见[消息](messaging.md)的日志与排序
一节）。两层的用例各自全绿，错的是接缝；接缝上没有类型，就没有任何一处会报错。

一个量要不要单独立类型，判据是**混用它会不会产生一个仍然能编译、能通过单元用例的错误**。
会，就立类型。代价是一些显式转换，收益是这一类错误由构建报出，而不是等端到端撞见。

### 界面与核心之间

核心向界面推送事件流，界面通过命令调用核心；两侧都不共享内部结构，跨界的只有明确
定义的数据传输对象。

失败跨界时传递的是**稳定错误码加上其句子需要插值的值**，而不是一句话。文案属于
界面层，因为只有它知道读者用什么语言、以及周围的界面已经说过什么。错误码集合手工
登记，新增一个未登记的码应当无法通过构建；任一语言缺少对应文案同样应当无法通过。

### 与网络库的接缝

核心通过一个窄接口使用网络，接口只表达"向某设备发送字节""订阅某聊天会话的到达"与
"查询可达性"。p2panda 与 iroh 的类型不得出现在状态机的 `State` 或 `Event` 中（{need}`TASK_20260919_P2HD03NJRM84P241`），
否则状态既不可序列化也无法在测试里构造。

这一层管两段预算，分工要写清楚：规则 4 的有界性只约束**本机由超时引发的**动作，认证前
的开销与**已认证对端诱导本机产生的**动作都不在其内。

**认证前的准入预算**放在这一层，而不是留给上面的业务上限。在握手、分配大缓冲与任何
密码学处理**之前**，先过一道全局预算：并发连接数、握手速率、待处理任务数与总内存各
有上限，并为已建立关系的联系人保留一份不被陌生流量挤占的容量；预算耗尽时直接拒绝或
背压，不进入解密与验签。已认证对端的配额叠加在它之上，而不是替代它。

这一道是必需的，因为陌生身份可以自由创建：按对端计的限额挡不住不断更换身份的并发
连接，每个身份都不超限，总的握手、解密与验签开销却足以压垮机器，而此时本机一个超时
动作都没触发，超时有界性那条规则完全不受影响——它管不到这个方向。

握手入口先取得全局许可，再创建异步任务和接受连接：并发最多8次，令牌桶每秒补充16次、最多积存16次，每次握手五秒超时；额度耗尽时静默忽略Incoming，失败或取消归还并发名额但不退还速率额度。另叠加每个直接网络IP每秒8次、突发8次的速率桶，端口或未认证自报身份不能增加额度，IPv4映射IPv6归一化；Relay、Custom和未知传输共用一个来源桶，不按未认证端点键分配额度。来源历史最多32项，新来源到来时仅清理距最后接受满一秒的记录，满额拒绝；拒绝不延长保留时间，一秒足以补满空桶。全局补充、来源补充及逐出共享钳到最近处理时刻的单调时钟，迟到调用不能回拨桶的时刻。这消除单来源独占全局速率，不承诺分布式多IP洪流或同一NAT/Relay内合法对端的公平服务。这只限制正在接受的握手；已建立连接、负载、内部映射及保留容量由各自租约承担（{need}`TASK_20260919_S5A75YBBYQ6HGGRA`）。

联系人新候选的首条可靠Create不能借用旧候选已经占用、可能已消费的反向预密钥，也不能要求已经确认且尚未占用的新公告再生成一遍。安装事务在设备全局的`bundle_reverse_reservation`保存已被候选占用的最大公告序号，并为本候选一次性保存目标设备及最低序号`max(此前已占用序号+1, 当前实际公告序号, 1)`；两者与候选状态同事务提交，失败全部回滚，溢出明确拒绝。重放、轮询及重启不重复占用；候选替换、取消或同意退役可清除本候选屏障，但不退还或重置全局序号。若设备全局仍有旧公告在途，先重发同一原件并等待其精确序号确认，不能覆盖其他操作拥有的密钥材料；确实不足最低序号时才发布新公告。只有实际公告达到最低序号且已确认，才放行首条Create；这是本地发送条件，不证明对端仍有可用私钥或群已经建立，SDK仍须拒绝密钥复用，缺密钥及过期后的恢复属于原接入流程。此持久可靠效果不延长接入尝试或单次SQL/发送期限，也不保证永久离线下交付；本地调用有界，最终放行另以真实对端保存/确认和公平调度为前提。来源行中的设备32字节及序号8字节沿用原元数据计费；设备全局占用记录每行40逻辑字节归属本人的会话元数据，不因联系人删除而退款。受限旧库升级及无用户身份的旧记录归属见[本地存储](local-store.md)。

出站侧在复制负载前申请全局额度：最多1,024条发送、负载总量16MiB；排队、执行与等待读取结果共用该额度，直到上层取走结果，或不发布结果的任务实际终结时释放。入队失败立即释放，取消不能提前退还仍在途或排队的租约。超限返回`NetError::Busy`，表示未接受本次发送；可靠效果仍由执行器保留重试。同设备发送共用拨号锁并复用已建连接，避免突发并发握手；地址提示不走发送队列，Connect另有32个排队/执行中的唤醒槽（{need}`TASK_20260919_S5A75YBBYQ6HGGRA`）。

上述全局发送额度内部，历史块与恢复流量（历史确认、补缺请求及原件转发）各保留4条发送和4×512KiB负载空间，不扩大1,024条/16MiB总上限。普通流量最多占1,016条／12MiB共享部分；两类均可借用共享空闲，但不能借走彼此未使用的保留额，顺序证明仍走普通侧。否则批量原件虽属恢复，也会让四槽历史窗口全部因Busy等待原60秒持久租约。类别由效果的持久归属决定：历史transfer优先于恢复发送类别，后者与效果及重试租约同事务保存，不能因后续发送挤出进程缓存或Store重开而丢失；顺序证明的nonce准入仍只活在当前进程。已接受发送不被抢占，排队结果继续持有原类别租约，直到消费或实际结束后只归还一次；取消不能提前归还仍在途或排队的负载。三类别准入模型检查共享池及相互保护；任选一个保护类别的租约投影检查排队占额、原类别退款与迟到/重复退款。固定发送期限和公平消费是明确的终止前提，不保证永久不消费时仍可接纳新发送（{need}`TASK_20260919_S5A75YBBYQ6HGGRA`）。

发送结果按SendId匹配持久效果，编号不能在网络端点重建后从1复用。每次发布新端点前，在SQLCipher实例库的network_send_sequence中以原子事务预留2^32个编号；新范围从持久分配器的下一空闲编号开始；当前格式不存在扫描旧待办导入编号的路径。未用编号在关闭、崩溃或发布失败后留作空洞，不重新分配。传输端点在首次发送前只允许绑定一次范围，发送通过原子递增取得编号，用尽或越过有符号SQL整数范围就明确返回容量错误，不能回绕。旧端点即使仍有迟到结果，也只能命中旧效果；应用重启和e2e中转端点重建都走同一发布入口。号段分配带五秒SQL执行预算；它只解决结果关联，持久待发的重试与公平性边界见下段（{need}`TASK_20260919_S5A75YBBYQ6HGGRA`）。

持久Send效果的自动重试与原状态提交同事务登记，独立保存下一次本地重试时间；成功或失效丢弃原效果时，同事务触发清理重试条目。每次net_pump先处理已读取的发送结果，再按到期时间/效果标识领取至多32项，预先续订六十秒间隔并清除旧SendId，随后用当前联系人/设备/引用授权重查后投递原保存字节。既有授权已失效就记丢弃并结束；Busy、离线或失败保留原件，不重新加密、签名或生成协议nonce，不向状态机虚构连通纪元。实际每次网络发送仍共用原三十秒上限，旧结果只匹配当前SendId。崩溃在领取后或网络已接受但编号尚未记下时，期限仍持久，后续可重试同一原件；重复接收由既有原件标识去重。

当前格式的每条Send效果与重试时间同事务登记，不扫描旧效果补登记；零毫秒是正常时间并保存完整六十秒间隔，时钟倒退也等待完整间隔。恢复类别沿同一事务登记，按`(recovery,next_millis,effect_id)`索引领取，不读取密文判断类别；仅复用既有原件转发所有者的新授权请求可提升其类别，不能改该尝试的SendId或租约。格式升级仅接受[本地存储](local-store.md)规定的60／61／62至63元数据升级，其他旧库拒绝且保留；已提交的本地存储效果转换成无正文标记，不重做消息或网络发送。到期与回退各走索引范围，领取先读长度再逐项解码，总序列化材料最多80MiB；超出剩余额度的条目保留并延后，正常独立传输上限16MiB经JSON字节数组展开仍可放入。数据库VM执行带五秒预算，时钟加法溢出明确拒绝。有限积压轮转依赖公平轮询、时钟最终稳定及本地资源最终可用，不保证永久离线或持续饱和下交付（{need}`TASK_20260919_S5A75YBBYQ6HGGRA`）。

后台创建等待及发送重试时显式传入当轮毫秒时间，不能以默认0或前一阶段的旧时刻代替；
否则新等待在下一拍就会过期，造成额外重试。此生产时钟接线不同于模型中的单调服务
预算，也不改变原业务等待的期限和配额（{need}`TASK_20261102_HG0948Q7GA70QBQ5`）。

直接地址提示在同一把短期状态锁内同步更新，不再排队AddPeer命令或为它创建任务：每端点最多4096台设备、其中非保留资格设备最多512台，每设备最多16个SocketAddr。插入前检查额度，满时返回NetError::Busy，已存在条目在满额时仍可更新，超长/空列表不能覆盖旧有效地址。资格重分类时保留所有仍获资格的提示，按设备键顺序保留至多512条其它提示；拉黑清除相应地址并拒绝重加。地址提示是临时网络元数据，裁剪不改变持久联系人或授权，缺提示时仍走既有发现路径，禁用发现时须重新提供可用直连地址。资格和地址更新在同一锁内，不会因并发重分类绕过上限。IPC也在解析前限制地址数量。移除AddPeer后，命令通道虽使用unbounded_channel类型，生产者最多同时持有1024个Send、32个Connect和一次Shutdown；发送/连接许可从入队前持续到其结果/尝试终结，不能靠快速更换设备绕过排队上限。

物理Noq驱动另有端点级256名额，覆盖尚未完成握手与仍排空的连接；普通拨号、两种接收和IPv4/IPv6网络地址发现探测共用同一计数，0-RTT复用原物理连接。创建前以try_lock串行读取pending后再读Noq完整数量，合计不足限额才预约；同步发布后或异步创建完成/取消后释放预约，退款不取预约锁。应用读者退出不会提前归还Noq物理名额。饱和或争用立即拒绝本次新建，已有连接继续；不承诺固定排空时长或持续饱和下的新连接成功。这仍不是整个App任务数/RSS预算，见{need}`TASK_20261102_W4HPKP6130N384N4`。

连接与入站缓冲另用全局资源租约：每端点至多128份连接/拨号许可，其中未获得保留资格的设备至多16份；出站拨号在I/O前申请，入站在iroh设备认证后、启动读取前申请，认证前握手仍受上述独立八槽/五秒限制。相同原生连接的并发登记复用读循环，不重复占额或提前关闭有效连接；读循环以RAII在返回、失败或任务取消时关闭并移除自己的原生连接，不能清掉新的替代连接。只有实际缓冲消费或丢弃才归还它的额度，连接关闭不释放仍排队的数据。 每条物理连接以同一原子状态协调开始使用与空闲回收：未获得保留资格的连接空闲五秒、获得资格的连接空闲六十秒后关闭；正在发送、读取或等待入队的流持有使用凭据，不能被空闲回收误关，最后一个使用者释放后重新计算空闲时间。每条流原有三十秒期限独立生效，不随活动续期；回收按计时器触发时的当前资格复核。出站缺少连接额度时，在原Connect十秒/Send三十秒总期限内等待释放，取消或超时结束；这不保证持续满载连接池下每个联系人最终获得服务。

连接许可覆盖物理连接及其未读控制观察的完整寿命：每条物理连接至多产生一次可达和一次不可达，排队观察共享其连接租约，关闭、拉黑或取消不能提前退还未读观察的额度。消费最后一条观察且物理连接及在途使用者都释放后才归还许可。因此连接观察至多256条（非保留资格32条），发送结果另受1024份出站租约限制，控制队列最多1280条；消费不丢弃连通纪元或发送结果。应用每次net_pump至多读取256条观察（含控制、故障注入丢弃），到达负载仍另限64条；并发生产者持续填充也不能把单次轮询变成无限等待。资源耗尽时连接等待沿用原固定期限，不能绕过消费者背压继续接受更多观察。

每条流在首次分配之前预留1MiB最大帧，读完缩到实际长度，读缓冲、排队和等待背压全程持有同一份额度：总计最多4096帧/64MiB，非保留设备最多1024帧/16MiB，零长度数据也占帧数。上层poll取走或拉黑实际丢弃后归还；网络队列之后的Rust接收批次仍受批次限制约束，UI只接收业务DTO，不接收待回传处理的原始网络帧。等待全局额度、读取与对端队列背压共享从流开始算的原三十秒期限，取消同样终止，不按阶段重新计时。保留资格来自当前有效本人设备及已建立未拉黑联系人的正面设备绑定；本人已确认应答但尚待首条操作的关系，在精确邀请用户/设备作用域的接收宽限内也保留容量，过期或缺期限不保留，避免建立前被陌生流量堵住。资源优先级不授予任何消息或出站授权，原准入仍独立执行。

自动重试的授权取数以同一个32项批次上限为界，与领取额度共用常量。领取后在一个只读SQL事务内查询本批用户关系状态、目标设备正面绑定、按用户区分的吊销和引用目标墓碑交集，不载入全部联系人/吊销/引用目标。本人设备资格仍取当前签名名单，不能用累积peer_device替代；名单通过增量BLOB接口与16KiB读缓冲流式筛选本批目标，名字/签名等无关值跳过，不复制完整名单或全部条目，整个查询/读取带五秒单调预算。读取的是已验证并由类型序列化保存的名单，不在每次出站重新验签。查设备正面绑定使用(user,device)索引点查。输出至多本批32项事实；无关用户的坏记录不拖垮本批，所需事实读取失败则返回错误、不回退到不完整授权。

分派授权绑定本批原有用户、目标设备、代数和引用元数据，未收集的请求一律拒绝；合法数据的决定和拒绝原因与完整快照一致。本机未有名单时仍认本机，本人其它设备须在当前名单且未被本人吊销；其它用户独立正面归属不被第三人负面声明连带取消。该限定快照只用于发送重试，资源名单由专用投影承担；局部批次上限不等于联系人事实全局常量空间（{need}`TASK_20260919_S5A75YBBYQ6HGGRA`）。

QUIC内部窗口：单向流最多4条、双向流0条；每流接收64KiB、每连接接收256KiB/发送256KiB，乱序握手密码缓冲16KiB，应用DATAGRAM关闭。NAT打洞、多路径、保活及空闲沿用iroh默认设置。接收循环逐条读完整帧，连接窗口须覆盖所有并行流窗口，noq的MAX_DATA返还阈值`receive_window/8`也须放入当前流保留份额，两者由编译期断言保护。否则其它流可耗尽连接信用，使当前帧既无字节可读又无法返还信用。Quint和真实QUIC回放覆盖此读序/窗口/返还抽象，不是完整QUIC或全进程内存证明（{need}`TASK_20260919_S5A75YBBYQ6HGGRA`）。

全进程资源、首次联系人服务及应用静默须用真实压力/捕获验证，不能从单项租约或有限模型外推。静默的规范范围见[隐私与防护](../product/privacy-and-safety.md)；“零应用响应”不表示握手、ACK及关闭包也全为零。当前实际验收范围与平台限制统一见[主计划验证摘要](../plans/2026-09/20260918-yochat-f2f-messenger.md#DOC_20260918_BFV4FCXTMM9MQRDD--verification)（{need}`TASK_20260919_S5A75YBBYQ6HGGRA`）。


每条已打开的入站应用流先进行独立的九十秒容量准入：先原子预留对端邮箱的一帧及最大字节额，再等待全局帧／字节信用，二者共用同一截止，不因阶段变化续期。九十秒覆盖默认六十秒接收窗口及三十秒余量；未准入流只留在既有有界QUIC缓冲，不轮询可能分配正文的读取future，不让安静连接预占全局最大帧信用。对端预留与现有队列共用节点，帧数／字节合计仍受原上限约束；屏蔽清空数据时须保留尚由旧guard持有的计数，取消／中止精确释放后才移除空节点。

准入成功后另起固定三十秒读帧期限，部分字节不续期；读完即将预留原子转换为同对端FIFO消息，不再等待本地邮箱而丢失已读正文。已打开流上的准入加读帧上界因此改为一百二十秒，而非旧共用三十秒；此契约变更已获用户明确选择，发送期限、五次ACK尝试及业务／资源上限不变。容量准入到期仅结束当前未读取流、归还预留并保留连接；远端读取超时、格式／传输失败、屏蔽取消或reader中止仍关闭捕获的精确旧连接，不能清理替代连接。连接关闭也立即取消准入；活动guard只覆盖有界准入／读取，原空闲阈值不变。排队帧的全局租约仍随真实消费释放，不早退信用，不清除无关已排队消息，不制造业务送达回执；QUIC字节确认不等于应用持久接纳。接受新流的监听仍受空闲回收、连接关闭／拉黑／停止控制，期限依赖公平单调时钟和到期调度，不承诺硬实时抢占。此项不代替全局入站内存、已建连接或联系人保留容量预算（{need}`TASK_20260919_S5A75YBBYQ6HGGRA`）。

出站内存保留额不代替开流服务：同一设备许可内按历史块、修复、普通三类登记FIFO，按非空类别轮转取得一个连接／开流次序；已选定的队首不能被迟到类别越过。每个持续非空类别至多经过三个新授予轮次获得机会，不承诺每个请求在任意网络或调度下成功。次序在取得物理连接前等待，因此局部排队到期不能关闭连接；实际开流并标记活动后立刻归还，不将后续写入／收尾／传输确认串行化，也不增加连接或绕过四流限制。无竞争时不建队列／复制Waker；竞争者沿既有出站预算有界保存SendId与Waker，仅唤醒新可用队首，唤醒在短锁之外。栈guard负责排队取消和活动次序中止，旧许可与替代许可隔离；不新增逐帧Arc、通道、负载副本、Busy租约或重试。发送三十秒仍从API接纳起覆盖全部本地等待及I/O，不在取得次序时续期；类别FIFO指登记顺序，而非并发API调用的墙钟先后。轮次与取消／期限由`stream_open_service.qnt`承担，真实Rust端点另核对类别线序和安静对端独立性。

发送从API接纳时刻起仍使用原三十秒固定期限。取得`ConnectionUse`后，`DeliveryConnection`始终持有实际发送使用的精确物理连接，并区分本次是否已经开流：本次已开流后的写入、收尾、确认失败或future取消仍退役该连接；从未授予过任何流槽的连接在开流等待失败时也退役，避免反复复用初始不可用的连接。若该物理连接曾授予流槽，而当前发送只是在等待后续流槽，到期仍结束并如实报告本次发送失败，但不因此关闭承载其它工作的连接；信用继续按实际终态／结果消费规则归还，不提前退款。曾授予流槽的标记与现有活动状态共享同一物理生命周期，不能从旧连接带到替代连接。已开流发送只有远端QUIC接收确认且未返回`STOP_SENDING`才解除退役武装。尚未取得连接的取消不能关闭任意连接；屏蔽、端点关闭及reader退出仍独立关闭对应连接，旧发送／reader清理只能命中捕获的stable id，不能关闭后来替换的连接。退役不证明业务未送达、不退还业务预算、不允许重新封装，原可靠任务仍负责同原件重试及业务确认。`transport_send_retirement.qnt`的结束仅假设公平单调时钟、本地超时和reader清理，不假设网络最终送达；本地接收背压的帧／连接区别另由`inbound_backpressure.qnt`验证。该发送适配与最终产品路径由{need}`TASK_20260919_P2HD03NJRM84P241`和{need}`TASK_20261105_NJDK86BZVP0DHH4M`承接。

传输轮次公平与墙钟成功分开：双栈接收在奇数poll同时反转IPv4/IPv6顺序，两族各一条active socket且均ready时，数据最多等待一次poll；不外推为同族多地址逐条公平或墙钟期限。relay接收把输入尝试与输出槽分开：丢弃超大/无分段输入仍消耗本次工作预算，但不在返回前缀留下空洞；余段保留来源/stride，关闭前先交回本批已有数据。全预算丢弃且无队列等待者时自唤醒，空队列不能忙循环。有限队列排空依赖公平消费/poll，不保证取消消费者或无限生产时排空。

非home relay actor只由非空发包批次续期，空flush、失败或维护均不续期；flush只处理队列长度快照，拨号、退避、连接和发送共用同一单调截止，home降级不重置，取消/到期不等待sink关闭。home发布在单个watch写操作内同时核对权威URL和不可复用的Arc生命周期身份，关闭先清空再取消；四个等待状态订阅权威URL/owner变更，到期再检查等待开始后的晋升，迟到hint不授予豁免。最终退出决定后的晋升可由父actor重建，不保证旧actor必不退出。结束前提是公平时钟/到期调度、最终无需求且非home；执行器停止、无限home切换或OS锁调度不在墙钟结束承诺内。四路径32状态对拍只是计时器/队列投影，不是完整网络调度等价证明。

**已认证对端的配额叠加在它之上**，覆盖的是规则 4 与准入预算之间那片带：按对端、按滑动
时间窗，对**入站重发请求**、**对方发起的通道重建**与**纪元切换**各设上限，超限即丢弃并
计数。这三类都不是本机超时引发、也不在认证前，此前无人约束——一个已建立关系的联系人
可以用不超限的小请求换回大量重新加密的消息、可以反复要求重建，而本机的重建上限只管自己
作为发起方的那一侧。具体数值随其他数值一并实测确定。

**这三类配额的计数器进入状态机的 `State`**——不是执行器里的旁路计数（{need}`TASK_20260919_WJJ4H5F7WSPXKERS`）。这一条是模型定的，
不是风格选择：`models/quota.qnt` 把计数器一次放进 `State`、一次放在模型外各跑一次，
**放在模型外时那条上限被反例直接证伪**——守卫读不到计数器，受理动作无人约束，实际受理
数一路越过上限。凡是要被检验的上限，它所依据的计数就必须是状态的一部分。

计数器**与其他状态同事务落盘、跨重启保留**，这一条的依据是本篇的 `State` 契约（可序列化、
不含句柄、与操作同事务提交），不是 `quota.qnt`——该模型不建模持久化与重启。

### 中转能看到什么

投递需要知道送到哪里，因此**目的端点标识必然对中转设施可见**，这不是内容加密能
隐藏的东西。产品文档的告知必须与这一点逐字对得上（{need}`TASK_20260919_W1QMH1F4CEXS7VD1`）：既不能承诺"参与者标识不可读"，
也不能在告知清单里漏掉端点标识，否则那条需求的验收无法通过。

中转暴露边界及其原因如下（{need}`TASK_20260919_W1QMH1F4CEXS7VD1`）：

- **通信双方的端点标识都对中转可见**，不只是目的端（{need}`TASK_20260919_W1QMH1F4CEXS7VD1`）。每个客户端必须用自己的设备私钥向
  中转认证才能收发，中转的访问控制接口直接拿到该标识。换用临时密钥不能消除设备层
  寻址所需的稳定标识。
- **条数与长度可见。**中转按帧计数、按字节计量；它们属于已接受且须如实告知的限制，
  不能用内容加密声称隐藏。
- 另可见：客户端连接中转时的网络地址、中转协议版本与设备认证签名。

**层级要分清**：以上可见的都是**设备**端点标识——本产品中它的定位等同于网络地址。
中转由此知道哪两台设备之间有流量，**不知道它们属于谁**：用户公钥不进入中转可见范围，
用户层的身份与会话成员名单仍不可读。把设备层的可见性说成用户层的暴露，会把一条成立的
承诺说成不成立。

核对层级不能混淆：`relay_observation.rs`检查中转解封后的连接请求字段及其中不含用户公钥
或正文标记；转发帧本身为QUIC密文，但中转钩子不交出帧内容，因而此检查没有独立证明
全部数据报不含明文。TLS链路抓包同样不能替代解封后检查，本机自建服务的观察也不冒称
公共n0服务实测（{need}`TASK_20260919_W1QMH1F4CEXS7VD1`）。

历史实测入口固定于提交`9d28fb8c3105081b1cfac3ee4ae7a30ce4fb3aca`的
`experiments/relay-probe/`，使用未打本项目补丁的iroh 1.2、本机中转与DNS/PKARR服务，
不访问公共设施。中转访问控制钩子取得端点标识、协议版本、请求URI及请求头；
中转自身的收发帧数和字节计数器支持上述计量结论，但不能把传输帧数直接当业务消息数。
实验源码和独立锁文件已退役，可用`git show <该提交>:experiments/relay-probe/<文件>`
追溯。现行`relay_observation.rs`承接连接字段及敏感标记检查，
`relay_discovery.rs`检查发布记录不含直连地址；两者不重演旧探针的计数采样或全部过滤器对照，
也不把历史上游结果提升为当前补丁版本的独立验收（{need}`TASK_20260919_Q84FGP203EPHG687`）。

发现信息发布什么同样在这一层固定，不沿用所选库的默认值（{need}`TASK_20260919_Q84FGP203EPHG687`）。上述固定上游版本的实测结论：默认配置下发布的记录
**只含中转入口，不含任何直连地址**（以独立客户端`dig`查询自建DNS服务所得）。承重的是发布器
自身的地址过滤器默认值，**不是**端点级的那道——只放开端点级那道时记录仍然只有中转地址，
两道都放开才会把全部直连地址（含全局IPv6）写进记录。实现必须守住发布器那一道。
独立查询前须排除环境HTTP代理改写PKARR请求路径；本机服务配置不能单独证明请求未经过代理。

**用谁的中转与发现**（用户 2026-09-24 定，{need}`TASK_20260924_823S0AQ3VBRQC778`）：默认用 n0 的公共中转与发现服务，
用户可在设置里改为自建的中转与发现地址。默认即可用，是因为不接中转与发现的话，隔着 NAT 的两台
设备根本连不上——此前应用里两者都关着，两台设备只能靠带外交换的直连地址接上。代价是默认情况下
本产品依赖一家外部设施的在线，告知清单因此要写明 n0；换成自建的，这一行随之换成用户自己的地址。
发布器那一道「只发布中转入口」的过滤器两种情形都要守住。自建时应用向用户给的 pkarr 服务发布、
也经它查询，因此那台服务要能答查询（iroh-dns-server 两样都有）；设置存在本机库里，重启后生效。
端到端构建默认两者都关，测试全程不碰外部设施；本机自建服务的通过不等于公共n0在线性验收（{need}`TASK_20260924_823S0AQ3VBRQC778`）。

PKARR HTTP查询与发布各使用固定十秒总期限，覆盖连接、响应头、完整响应体及验签，不随分块进展续期。签名包最多1104字节；HTTP中省略URL已携带的32字节公钥，因此响应体最多1072字节。声明长度超限时不读取正文，未声明长度或分块传输时每次追加前检查剩余预算；合法响应仍核对所请求公钥和签名。默认与自建配置共用该客户端，发布器继续只公开中转入口。超时旧PUT不阻塞后续地址更新；取消不能撤回服务端已收请求，服务端须按PKARR签名时间戳保留较新记录，不能向任意重放旧记录的服务器承诺地址新鲜性。固定期限依赖运行时公平调度，未承诺同步签名校验可被硬实时抢占（{need}`TASK_20261105_K0BAB8QKCJRY0EFN`）。

## 失败处理

失败分三类，处理方式不同，不得互相冒充（{need}`TASK_20260919_5X1SXR1ZNC2XQAWC`）。

**业务拒绝**是系统按规则作出的正当答复，例如向被拉黑的联系人发送被拒绝。它是一个
正常结果，带明确的错误码呈现给用户，不重试。

**暂时故障**是外部条件造成的，例如对端离线、连接中断。它不呈现为错误，而是状态：
消息停在"已写入本地"，通道重建停在等待。只有在超过所设时限之后才告诉用户，并说明
它会自动继续。

**不变量破坏**是本不该发生的情况（{need}`TASK_20260919_5X1SXR1ZNC2XQAWC`），例如状态反序列化失败、事务提交后读不到自己写入的
数据。受影响的那个操作快速失败并如实上报，不试图猜测或修补；但失败限于该操作，
不得使整个应用不可用。

横贯三类的一条硬规则（{need}`TASK_20260919_5X1SXR1ZNC2XQAWC`）：存储读写失败必须报告为失败，不得翻译成"没有数据""不存在"
"空列表"这类语义答案。本地是唯一的副本，没有第二处可以在下一次请求时纠正一个错误
的答案，而下游会据此创建、跳过、从零开始或删除，这些动作往往不可逆。这条规则在
类型上落实：所有可失败的查询返回的是"存在与否"和"读得到与否"两个独立的答案，
不把后者折叠进前者。

## 验证

### 协议层

用 Quint 建模并做有界模型检验，覆盖：消息的按序应用与重发、通道重建、组成员变化的
并发、邀请交换、删除指令的逐设备确认。用模拟器导出执行轨迹，写一个回放器把轨迹逐步
喂进真实的 `step` 并比对可观察状态，使规约与实现不一致时测试变红。

### 超时是模型中的一等动作

时间不是模型里的背景假设，而是一组显式动作。建模规则固定如下：

1. 每一处等待都对应一个可在任意时刻、任意多次触发的超时动作（本组两条归
   {need}`TASK_20260919_PFGXDHF5JWV01TRJ`）；**不存在"等待终会
   结束"的隐含前提**，设备可以永不再上线，网络可以永久分区。
2. **安全性质在包含任意超时序列的执行上都必须成立**：不丢消息、不重复、不越权、
   不产生无法解释的空洞、不把未完成说成已完成。
3. **活性性质必须写明其公平性前提**（例如"双方最终持续在线且通道最终稳定"），并且
   每一条活性性质都要有一条不依赖该前提的安全对偶——前提不满足时系统可以停下，
   但不能损坏，也不能对用户撒谎。

   前提里的 `connected` 取**强读法**：*对端可达期间，一次已发起的投递尝试能够完成*。
   弱读法（可达只是允许尝试，尝试仍可能失败）不采用。这不是措辞偏好，它撑着上一条
   和下一条：`models/quota.qnt` 以两种语义各跑一次，只有强读法下"连通期内一次投递能
   完成"成立；而 `models/resend.qnt` 的 `perEpochWeakConnected` 模块把取法固定为
   "每连通纪元有界 + 含可达性事件 + 弱读法"，**其中离线送达的活性被证伪**——一旦永久
   连通，纪元不再切换、预算不再重置，有限预算被失败的尝试耗尽后再无动作重试。（被证伪
   的是**活性**；有界性在弱读法下仍然成立，两者不要混读。）

   **因此第 3、4 两条与有界口径三者咬合，不能各自单独引用**（{need}`TASK_20260919_PFGXDHF5JWV01TRJ`）：有界性按纪元计之所以
   成立，前提是 `connected` 取强读法。这句话必须留在文档里——模型跑通了而它依赖的
   前提没写在任何地方，那是最容易在下一次修改中被无声推翻的东西。

   强读法对实现的要求是具体的（{need}`TASK_20260919_P2HD03NJRM84P241`）：网络层报告"可达"必须意味着一条已建立的、可承载一次
   完整投递的通道，而不只是地址可解析或握手已开始；做不到这一点时，可达性事件就不该
   发出，否则模型里成立的活性在实现中不成立。
4. **超时触发的动作必须有界**：由超时引发的重试、重建、广播与请求的次数受配置上限
   约束。有界性有两种口径，**用哪一种不由各篇自选，按下面这条判据定**：

   - （本组两条归 {need}`TASK_20260919_1BBHDZ61GTE9MGAG`。）**承载"对方离线七天后上线，期间发送的全部消息按原顺序到达"这条承诺的等待，
     按每个连通纪元内有界**——兜底重发、请求重发、历史同步的块重试属于这一类。
     依据是 `models/resend.qnt`：三种取法各跑一次，只有"每连通纪元有界 + 事件字母表
     含'对端由不可达转为可达'"同时满足纪元内有界与离线送达的活性；**"每滑动时间窗
     有界"那一种在纪元内有界上直接被证伪**（见[验证策略](decisions/verification-strategy.md)
     与计划的执行记录）。
   - **不承载该承诺、只为本机自保的等待，按滑动时间窗内有界**——通道重建的重试、
     超限批准的退避请求属于这一类。它们必须能在对端**始终可达**而通道坏掉的情形下
     继续恢复尝试。这一项的两半要分清各自的来源：模型给出的是"窗口滚动是恢复尝试与
     告知的唯一来源"（`models/rebuild.qnt` 的告知活性以"窗口会滚动"为前提之一，去掉
     即被证伪）；而"纪元切换在通道坏而对端始终可达时不会发生"是由纪元定义直接得出的
     推论，**未单独建模**——`rebuild.qnt` 里没有可达性与纪元这两个概念。

   两者都不是"全执行累计有界"（{need}`TASK_20260919_1BBHDZ61GTE9MGAG`）——按累计检验会与"对方离线七天
   后上线，期间发送的全部消息按原顺序到达"这条产品承诺直接冲突，也会让一个持续投递
   坏数据的对端把上限打满之后永久钉死一个聊天会话，使这条防拒绝服务的规则自己变成
   攻击手段。**连通纪元**的切换由网络层的可达性观察给出：某对端从不可达转为可达即开启新纪元。
   这个事件本身必须限速——**按对端、按滑动时间窗对纪元切换设上限**，超过之后不再重置
   预算、不再立即重试，直到窗口滚动。没有这条，有界性就交到了对端手里：它反复断开
   重连（甚至不断开，只是停止应答到保活超时再恢复）就能一次次重置预算，而"离线七天后
   上线补齐"只消耗一次切换，不受这条上限影响。本机重启同样构成一次切换，其代价由同一
   条窗口上限兜住。

   这条规则的覆盖面要说清楚：它只约束**本机由超时引发的**动作，不覆盖**对端诱导本机
   产生的**动作——认证前的握手、解密、验签与界面提示不在其内，那些由准入预算承担，
   见本篇的与网络库的接缝一节。把这条规则说成"拒绝服务的形式化对应"会让人以为拒绝
   服务已经被模型覆盖，实际覆盖的只是其中一个子集。

### 端到端验收用什么工具

上一节把大量验收判给「端到端」，因此这一层的工具必须写死（{need}`TASK_20260919_0R2EC1M6896HVHT7`），否则三十多项任务的界面观察
各凭各的办法，彼此不可比也无从复核。

采用 **WebdriverIO 加 `@wdio/tauri-service`**，driver provider 固定为 **`embedded`**——
WebDriver 跑在应用进程内，不需要外部驱动。这个选择不是偏好，是平台约束逼出来的：Tauri 官方的
`tauri-driver` **只支持 Windows 与 Linux**，macOS 没有可用的 WKWebView driver 工具。该服务的另外
两个 provider 都不采用：`external` 就是 `tauri-driver`，同样缺 macOS；`crabnebula` 虽然跨平台，
但需要订阅（macOS 上要 `CN_API_KEY`），不把交付验收挂在付费凭证上。本条要连同理由一起留着，
否则以后有人照多数 Tauri 教程改回 `tauri-driver`，在 macOS 上会直接失效。

由此固定三件事：

- **多设备验收用 multiremote。** 「A 发 B 收」「B 的另一台设备」「三台设备任意两台先收到都收敛」
  这类验收需要同时驱动多个应用实例，由该服务的 multiremote 承担，不自建编排。
- **纯界面断言可用 browser mode。** 布局、键盘可达、深浅色与对比度这类不依赖真实外壳的检查，
  可把前端放进普通 Chrome 对着 Vite dev server 跑，不必起 Tauri 二进制，快且稳。涉及外壳行为
  （窗口、应用锁、通知、系统外观切换）的仍走 `embedded`。
- **判定靠 DOM 断言，不靠比对像素。** 需要留证时截图由 WebDriver 出——它截的是 webview 内容，
  由引擎自身产出，因此不经过操作系统的屏幕录制授权。桌面级截图工具不作为判定手段：在没有该
  授权的机器上它只会返回桌面而不报错，看起来像「窗口没起来」，而实际窗口可能好好地开着，也可能
  位于另一个 Space 或屏幕外——三种情形在截图上无法区分。

普通构建与E2E构建使用独立产物目录，避免普通Cargo调用覆盖含WebDriver的二进制。
WebDriver服务器、任意JS执行能力及`withGlobalTauri`仅存在于E2E feature/覆盖配置，
前端按Vite的e2e mode导入；关闭debug assertions时启用E2E直接编译失败。
E2E的应用标识、数据根和Keychain服务与生产隔离，单元测试不访问开发机登录钥匙串；
真实Keychain集成由隔离产品二进制承担，清理在失败路径也须发生
（{need}`TASK_20260919_TE9DN97R1P2SBQ18`、{need}`TASK_20261105_15XXFKGF6EBXP2BC`）。

macOS系统通知直接使用`UNUserNotificationCenter`；有效bundle标识与系统授权是前提。
通知标识只含会话、作者设备和消息标识，不藏正文；来源取本机关系记录而非对方自称名字。
普通E2E记录器/模拟点击只能验证路由，真实投递与点击要用隔离签名通知包及系统投递列表，
不能互相冒充。包的冻结回执保存在`.app`外，签名后向资源包写入元数据会破坏资源封印
（{need}`TASK_20260919_84943YC4AF86ZET8`、{need}`UC_20260918_KZACP3YFJW0WRWBK`）。

### 每条需求的验收在哪一层

层级按被验证的东西定，不按测试数量或覆盖率定：

- 多方交错下的时序承诺——按序应用、去重、重发有界、通道重建、成员收敛、删除的逐设备
  确认——在**协议层**验收（本组两条归 {need}`TASK_20260919_WSG175RHG9NHXPD0`），结论由 Quint 的性质检验加回放器对拍给出；
- 单机的状态推进、崩溃重启后的恢复、存储的事务承诺在**实现层**验收，结论由 proptest
  对拍与对真实 SQLite 的性质测试给出；
- 解析、序号运算、令牌解码的边界在**纯函数层**验收；
- 用户可观察的路径——邀请、应答、确认、收发与多设备同步、十万条量级下的界面测量、
  深浅色外观与键盘可达——只能**端到端**验收。相关单元测试通过不能顶替它们，那证明不了
  这条路径真的跑通过。

每条 REQ 落到哪一层，逐条写在本次计划的覆盖对照与任务的 `verify` 里；实现据此执行，
收尾据此逐条核对。
