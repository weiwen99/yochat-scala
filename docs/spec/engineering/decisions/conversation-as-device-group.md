# 聊天会话建模为设备组

<!-- tao:section decisions -->
## 设计决策

```{adr} 聊天会话建模为设备组
:id: ADR_20260918_T2WCAY7DFFWJPC4K
:status: proposed

<!-- tao:field context -->
**背景与备选：** 规格要求一次一对一聊天在双方各自的多台设备之间同步，要求新设备读不到加入之前的
消息，要求被吊销的设备读不到吊销之后的消息，并且要求后续阶段支持群聊。这四条看上去
是四个功能，但它们问的是同一个问题：在任一时刻，谁有权解开这条消息。

可行的做法有两条。一是把一对一建模成两个用户之间的双方通道，多设备再在其上叠一层
扇出：每台设备各自与对端每台设备维持一条通道。成员数为 m、n 时要维持 m×n 条通道，
而设备的增删要在每条通道上分别处理。这条路在群聊里并非不能用——成对加密同样可以
向群成员设备扇出——但成本随成员数平方增长，且"谁该收到"要在应用层自己维护。二是
把一次聊天直接建模成一个成员为设备的组，用组密钥协商承担全部成员变化。

两条路的实现与验证成本没有同口径的实测对比，下面的选择基于语义契合度而不是实测
数据。早期原型只验证库参考实现下的并发增删、离线成员加入与重投组合；
泛型成员类型及该原型都不证明应用自己的成员算法和定序实现正确。

实测 p2panda-encryption 0.7.1 的 `MessageGroup<ID, ...>` 对成员标识类型是泛型的，
成员可以是任意可比较的值，不限于"用户"。

原型固定在提交`81e936fd2e86534ac15180485fc4eaac6b377c38`的
`experiments/device-group-probe/`，使用未打本项目补丁的p2panda-encryption 0.7.1、
`AckedTestDgm`及测试定序器。历史观察为：并发增删在投递期间视图不同、投递完毕收敛；
新成员未得到加入前正文而得到加入后正文；离线积压倒序及重投后正文仍解出、四方视图收敛。
但已处理的create/welcome重到曾返回`GroupAlreadyEstablished`，原型直接unwrap因此失败，
改为记账后才完成观察。应用须按原件身份去重或明确处理可预期的重复，不能将所有receive错误吞掉。
这不是当前独立成员、真实网络或任意重投序列的证明，现行责任由下方协议回归及模型承担。
一次性原型及独立锁文件已退役；源码可用`git show <该提交>:experiments/device-group-probe/<文件>`
追溯，历史完成状态不因删除实验载体而撤销（{need}`TASK_20260919_2AQRGA1K60DY1E6E`）。

<!-- tao:field decision -->
**选择：** 采用第二条：一次聊天会话就是一个组，成员是参与方全部未被吊销设备的设备公钥。
与自己的聊天会话是只含本人设备的组，一对一是双方设备并集的组，群聊是多个用户设备
并集的组——三者是同一个机制的不同成员集合，不是三套代码。

成员集合的权威来源是各用户自己签名的、带版本的设备列表：一次聊天会话的成员即
参与方设备列表的并集。设备加入映射为组的 add，设备吊销映射为组的 remove。

用户明确选择“不连带移除C”：B帮C入组后，仅吊销B不连带撤销仍在有效签名设备列表中的C，以用户签名设备授权为准。所有当前会话统一使用独立成员；未发布旧成员算法快照与控制格式明确拒绝，不提供迁移。入站组变更授权及并发吊销后的密钥保护继续保留。

成员操作的**提案、目标实际收到的欢迎、目标确认**不是同一事实。Add按创建时冻结来源当时已知的操作集合及初始名单知识；其它观察者不能仅因看到Add就推断目标已继承这些知识。只有目标对该Add的真实ACK才授予冻结快照，本机作为目标时则从实际通过验证的Welcome取得知识。ACK迟到或重放不能复制来源后来才知道的事实，合并相同Add时必须核对同一份不可变继承。成员知识也不等于拥有对应棘轮：实际AddAck/Forward的私有贡献仍须按普通密码路径处理；本该提供的定向贡献缺失仍失败，不能笼统吞掉`MissingDirectMessage`。

这一区分覆盖原设备和替代设备并发重新汇合：CD分别Add B/A后，B还可能在未知D提案时再次Add A；A尚未收到B的欢迎便可发出不含B专属贡献的旧更新。B须按A实际确认的知识处理，而非按自己发出的提案推断A已知道B。Add/ACK原有因果依赖、原始受众隔离和当前授权检查保持不变；当前格式不迁移旧知识快照。端到端接替、故障恢复和最终集成仍由 {need}`TASK_20261105_NJDK86BZVP0DHH4M` 验收。

本机创建、加入与移除命令在消耗预密钥或写入组状态之前核对会话双方：会话标识须与本机用户及登记对端一致，本机设备须仍有效，对端须为未拉黑的已建立关系。加入目标只能来自双方已验证授权；已有完整签名设备列表时以最新列表为准，尚无完整列表的初始交换只认已验证的交换设备。移除只执行双方已验证的永久吊销，不把设备签名的组 Remove 当作用户吊销证明。自动本人通道创建复用相同核对。入站显式 Remove 同样要求会话双方已验签的用户吊销证明：group_receive 在关系提升和元数据写入前拒绝未授权移除，decode_inbound 在推进加密状态前再次检查，旧状态中尚未应用的缓冲移除也重查；证明补到后可重新处理同一原件或依赖。此项不改变序列化字段或格式版本。Create/Add 的作者、显式目标及欢迎历史中的成员、已移除设备、加入来源、确认者和操作作者按会话双方授权核对；旧缓冲中的成员操作在依赖放行前重查。合法旧原件允许引用双方已验签吊销证明对应的旧设备，但生成新组密文、送达确认和重建新一代前仍检查全组当前授权，避免只过滤投递目标却让旧成员继续解开新密文。本人私有通道按已验证吊销生成移除和换钥，状态、原件及可靠发送同事务保存；后台及用户动作都推进清理，每次动作最多32步，版本不变即停止，即使有效名单只剩本机也清理已有组。已建立的独立成员联系人会话也由相同入口按双方当前有效设备并集自动加入有新包的设备、移除已证实失效且未获另一方授权的设备；出站绑定实际对端用户，不能沿用本人通道的授权上下文。第三方联系人设备不成为候选，旧缓存名单不能覆盖最新列表。未建组的联系人会话不由此另起组；不迁移旧成员算法快照。丢失当前状态后的逐次许可恢复和原子安装按既有安全边界执行（{need}`TASK_20260920_GSW6Y996D2E1E681`）。

丢失组状态后的重新接入不能假设旧控制密文仍可解。延迟换钥可能在新欢迎之后才补到：它不能被无凭据忽略，也不能重新更新已安装的新链。仅给冷目标补新公开包仍可能报`UnknownSecretUsed`；只重建观察者到目标的二方通道，也不足以恢复目标的作者发送链。因此退役须同时处理目标二方通道、作者链起点及关联秘密，但不删除独立成员事实、不倒退作者日志位置。同次恢复只能重设一次，来自另一帮助者的新控制不等于新的恢复尝试；每设备/会话的最高已安装尝试号与密钥同事务持久保存（{need}`TASK_20261030_M7M0CME5QMG60C3S`、{need}`TASK_20260920_GSW6Y996D2E1E681`）。

独立session的隔离检查点候选绑定可信的本机已安装尝试、用户/设备/会话、目标对首次欢迎及检查点的逐次许可、帮助者及真实新欢迎位置。审计该帮助者从0至检查点之前的完整签名原件和回链；欢迎历史每条Add/Remove均查询不可变原件，核对作者、位置、会话、目标和类型。Add的冻结继承及初始知识位还须匹配原件中的Welcome来源快照。所有ACK均读取被确认的原件分类，确认过的成员事实必须保留且帮助者已知，不能因两边都缺事实就跳过。缺原件返回待补证错误，错误作用域或签名拒绝；原件库仍负责拒绝同作者位置分叉和非原生日志宽度的引用（{need}`TASK_20261031_E3GTXDN2C3TSW1YC`、{need}`TASK_20260920_GSW6Y996D2E1E681`）。

缺少二方状态时，只以本次首次欢迎对应AddAck/Forward为凭据，从实际初始预密钥帧推进二方传输；已有通道只推进未处理定向帧，不将旧秘密装回作者链。旧原件真实依赖保留，只有普通session实际处理新欢迎并生成准确ACK才返回候选；跨作者依赖缺失返回等待，缓冲不等于密码成功。坏密文、同位置分叉、准备后授权失效均拒绝且不修改输入；同次已覆盖检查点不重装，新检查点可沿已有通道继续准备。调用方在安装前重查当前授权和持久版本，将旧前缀、成员事实、新链、设备私料、原件、确认和尝试标记原子保存，不能把迟到控制一概改成成功（{need}`TASK_20261031_E3GTXDN2C3TSW1YC`、{need}`TASK_20260920_GSW6Y996D2E1E681`）。

隔离候选与现有Store的正常轨迹、写入失败、版本冲突和重启回归，不等于完整产品重新加入验收，也不代表异常模型轨迹、任意跨作者确认知识传递或多目标恢复均已覆盖。长旧前缀只压缩精确的同作者线性依赖边，分支、跨作者边、欢迎节点及未知依赖不能因此消失；压缩不能减少逐条验签审计所需原件，也不证明任意碎片化图有常数空间。当前启用范围和未覆盖项统一见[主计划验证摘要](../../plans/2026-09/20260918-yochat-f2f-messenger.md#DOC_20260918_BFV4FCXTMM9MQRDD--verification)（{need}`TASK_20260920_GSW6Y996D2E1E681`）。

<!-- tao:field consequences -->
**影响与后果：** 收益：多设备、设备吊销、后续的群聊共用同一条代码路径与同一组不变量，规格里
"新设备读不到加入前消息"与"被吊销设备读不到吊销后消息"直接由组密钥协商的语义
给出，不需要另写逻辑；通道数量从 m×n 降为每聊天会话一个。

代价与责任：组成员算法与操作排序须由应用实现——p2panda-encryption 只提供
`AckedGroupMembership` 与 `ForwardSecureOrdering` 两个 trait，生产实现不在库内。
这是本项目并发上最难的一处，必须形式化建模。首版的实现被刻意限制为"两份签名设备
列表的并集"，权威在设备列表而不在一张通用授权图，因此不引入 p2panda-auth；群聊
阶段若需要角色与管理员，再评估引入它。

另有一处必须记住：一个用户看到的成员集合取决于它确认过哪些成员操作，库的
`members_view` 明确按观察者返回。因此"当前成员"不是一个全局事实，代码里不得假设
各方看到的成员集合时刻相同。

两个原成员同时加入同一设备时，不能以成员集合去重代替完整协议验证。确认消息携带密钥交换结果，除指向所确认操作外，还须保留当前控制头部的因果依赖；否则后续确认可能先于发送方早先的密钥交换到达。欢迎消息实际声明的祖先属于入组前历史，不要求新设备补取这些原件；未知依赖仍等待，放弃某个位置不能作为任意未知位置在欢迎之前的证明。定序压缩/完整表示的等价性不能替代真实密码回归（{need}`TASK_20260920_GSW6Y996D2E1E681`）。

`concurrent_join_probe.rs`为各收件人生成独立预密钥，覆盖不同目标接入、额外同目标提案、延迟确认、更新、入组前缓冲和重启，要求后续正文在所有有效远端方向各恰好解开一次，并保留缺少必要私有贡献时的失败。当前独立成员以操作保留多来源事实；不沿用早期探针对重复加入的临时拒绝规则。`welcome_merge.qnt`的同来源合并性质不代替Add知识、密码交付契约或实际产品接替验收（{need}`TASK_20260920_GSW6Y996D2E1E681`、{need}`TASK_20261105_NJDK86BZVP0DHH4M`）。
```
