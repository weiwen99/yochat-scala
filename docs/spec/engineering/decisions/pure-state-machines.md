# 核心逻辑写成纯状态机，效果外置

<!-- tao:section decisions -->
## 设计决策

```{adr} 核心逻辑写成纯状态机，效果外置
:id: ADR_20260918_7GY2XVRX0C7MR6ZA
:status: proposed

<!-- tao:field context -->
**背景与备选：** 本项目的正确性集中在几处并发与顺序敏感的逻辑上：消息的按序应用与去重、重发与
通道重建、组成员变化、邀请交换、删除指令的逐设备确认。规格同时要求用形式化规约与
性质测试来保证这些逻辑，而形式化规约唯一不沦为墙纸的办法是让它与实现对拍。

如果这些逻辑与网络、时钟、随机数、数据库调用揉在一起，就既无法对拍，也无法用性质
测试覆盖交错序列——每个新情况只能在多处打补丁，而补丁之间的相互作用没有任何东西
能检查。

<!-- tao:field decision -->
**选择：** 每一处这样的逻辑写成一个纯转移函数：

    fn step(state: &State, event: Event) -> (State, Vec<Effect>)

`State` 可序列化、不含句柄；`Event` 包含网络到达、用户动作、定时器到期、**对端由不可达
转为可达**、以及先前效果的完成结果——可达性变化是独立的一项，不并入前两者，理由与依据见
[架构](../architecture.md)；`Effect` 描述要做什么（发送、持久化、起定时器、取随机数），
由外层执行器执行并把结果作为新的 `Event` 送回。

时间与随机数一律作为事件输入，状态机内部不读取系统时钟、不生成随机数、不做 IO。

<!-- tao:field consequences -->
**影响与后果：** 规约轨迹可回放进真实`step`并比较可观察状态，性质测试可以生成包含
崩溃/重启的事件序列。持久状态只是恢复的起点：状态与效果同事务提交、效果幂等、
稳定定时器身份及出站前重查授权仍由执行器承担；纯函数本身不提供这些保证
（{need}`TASK_20260919_5X1SXR1ZNC2XQAWC`）。

代价：调用方要多写一层执行器，直接调用变成"产生效果、执行、回送结果"三步，读起来
比直接 await 一个网络调用绕。效果的执行顺序与失败处理成为执行器的职责，必须明确
定义，否则复杂度只是从状态机挪到了执行器。

约束：任何进入 `State` 的字段都必须是可序列化的纯数据。这条一旦破例（例如为了
方便塞一个连接句柄进去），对拍与崩溃重放同时失效，因此它是硬约束而不是建议。
```
