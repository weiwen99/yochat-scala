# 用户、密钥与设备

<!-- tao:section overview -->
## 概述

本篇界定密钥的层次与用途、设备列表与吊销的结构、本地数据的静态加密与应用锁，以及
一台机器上多个实例如何隔离。聊天会话内容的加密见[消息](messaging.md)，关系的建立见
[好友交换](contact-exchange.md)，落盘细节见[本地存储](local-store.md)。

<!-- tao:section architecture -->
## 边界与架构

### 三层密钥

**用户密钥对**定义一个用户。私钥的可书写形式就是恢复短语。它**只用于签名**：签发
设备条目、签发吊销声明、为用户别名与头像的变更背书、签发邀请与邀请应答。它不承担
解密，加密所需的一切由下面两层提供。把长期身份密钥限制在只做签名，
是为了不让它同时暴露在解密相关的攻击面上。

**设备密钥对**由每台设备在本机生成，从不离开该设备。它同时是这台设备在点对点网络
中的地址，也是组密钥协商中这台设备的身份。

**数据库密钥**是一个随机生成的值，用作本地加密数据库的口令。它不由前两者派生，
而是被它们各自封装一次。

### 用户私钥的持有范围

用户私钥只存在于用户明确指定的设备上。未持有它的设备拥有自己的设备密钥与本人的
用户公钥，足以正常收发消息、参与组密钥协商，但**不能**把新设备签入设备列表，**不能**
签发吊销声明，也**不能**生成邀请与邀请应答（因而不能加好友）。把它复制到每一台设备，等于让任意一台的丢失升级为整个用户的
失守；而持有得越少，暴露面越小。

让第二台设备也持有它是一次显式的同步，在已持有的设备上发起、两端各自确认，经由双方
已建立的加密通道传输。**私钥只在两端确认都到达之后才传输**：传输若发生在确认之前，一个
永不确认的接收端上就躺着一份未被承认的用户私钥，而超时既撤不回它也作废不了它。同步状态
（发起／一端确认／两端确认／作废）放进 `State`，超时的效果是作废整次同步并清除中间状态，
不是弹一句提示——一个永远使能却只弹提示的动作，在模型里等于什么也没做。这是便利而不是
冗余：备份好的恢复短语本身就能重新取得这项能力。

实现消息分为元数据请求、目标确认、逐次密文、完成回执和不含种子的持钥声明。每条消息都在已建的本人私有会话中由设备签名，绑定用户、来源、唯一目标、来源域内递增的尝试号和原期限；消息作用域与真实作者分别核对。来源按钮的确认创建元数据请求；目标确认后，才生成独立的 p2panda X3DH 接收身份及预密钥，来源使用该包封装用户私钥，内层也绑定完整作用域。该身份不登记进全局设备密钥表，取消后不能借常驻设备密钥解开迟到材料。重复许可复用已保存的逐次密文，不重新加密（{need}`TASK_20260919_5VV5HJ3Y1E8W1X4M`）。

期限为来源发起后十分钟，两端按各自当前墙钟检查，未来超过完整期限加999毫秒的作用域也拒收（入站秒精度的取整余量，不延长原截止时间）；这不是对任意时钟回退的保证。拒绝、过期、替换和当前设备授权失效时清除目标逐次私料。来源本机取消停止新封装与业务重试，不能召回已发出的合法授权密文；目标本机作废才能阻止尚未取得材料的后续解密。完成通知只说明某设备已取得能力，未知或离线不能推断为“所有私钥副本都丢失”，界面给出条件式的全丢失说明（{need}`TASK_20260919_5VV5HJ3Y1E8W1X4M`）。

验收须分别观测“目标已经知道用户私钥材料”“目标仍持逐次解密私料”和“签发接口已经启用”，不能以`holds_user_key = false`证明确认前没有种子。真实解密成功形成历史知识，SQL回滚、删除临时材料或接口未启用均不能将其重置；双端确认前不发送种子才是安全边界。尝试号按来源域持久递增，不比较不同来源的编号；普通重启不复用旧号，短语重建使用新的设备身份。合法完成、逐次私料清理和完成回执同事务保存，第三台本人设备只收到不含种子的能力通知（{need}`TASK_20260919_5VV5HJ3Y1E8W1X4M`）。

远端持钥状态未知时返回`null`，不能由缺少持钥声明推成`false`。创建、短语加入、声明丢失或离线都可能使观察者不知道真实能力；吊销确认在未知时保留条件式的身份冒充风险说明，已认证的持有事实才显示为已知持有。取得种子的设备还必须先以现有数据库密钥持久建立恢复封装，才能报告持钥升级完成；封装写失败不能发送成功回执。封装与SQL的可重试提交顺序见[本地存储](local-store.md#DOC_20260918_9810WZW7EA7H8FC5--architecture)（{need}`TASK_20261102_9C3WTTYBREVSEQR3`、{need}`TASK_20261102_02GQSJGE51Z1NGTF`）。

### 设备列表与吊销

设备列表是一份带单调递增版本号的集合，每个条目记录设备公钥、设备别名与加入时间，
整体由用户私钥签名。它随关系同步给全部联系人——设备公钥在点对点网络中本来就会被
通信对方看到，而联系人需要凭它拒收已吊销设备的消息，所以隐藏它既做不到也有害。

新建用户身份时，即保留只含创建设备的第一份用户签名名单，复用现有名单事务、证据计量和分发路径；不能等到增加第二台设备才建立这份证据。否则单设备作者的消息虽已发送，后来的设备却无法验证其历史排序证书。创建确认和未完成创建的重启恢复都检查本机原始绑定及固定起始记录，缺失时拒绝完成创建，不在读取时自动补签。

吊销是一条独立的签名声明，记录被吊销的设备公钥与签发时间戳，随设备列表分发。

吊销按“签名用户＋设备”判断。用户可以给任意设备公钥签发负面声明，验签成功仅证明该用户拒绝授权它，不能证明设备属于该用户，也不能切断另一用户的有效授权。出站快照保留用户维度，设备登记、邀请签发设备状态和当前成员检查使用各自用户的吊销集合。无用户上下文的入站地址与历史作者标记，只有在已验证正面绑定存在且全部已知绑定均被各自用户吊销时才视为已吊销；设备主动授权给双方时分别判断，不假定全局唯一归属（{need}`TASK_20261030_WZ83SVEFVPEDDKPJ`、{need}`TASK_20260920_GSW6Y996D2E1E681`）。

欢迎历史中的显式移除与直接Remove一样，需要会话双方之一针对自身历史绑定的用户签名吊销原件；如果设备仍获会话另一方有效授权，则拒绝移除。当前独立成员协议只移除显式指定设备，不读取旧连带移除格式。正面绑定由当前交换或重新验签的设备列表同事务保存，吊销后保留；旧库按格式拒绝，不回填，也不从负面声明或不带设备签名的加入公告反推绑定。证据已丢失时等待可验证元数据，不以任意用户声明强行通过欢迎（{need}`TASK_20260920_GSW6Y996D2E1E681`）。


历史归属补证保留设备原自签名和被签字段（所属用户、设备公钥、加入时间）；别名不在该自签范围内，不参与归属且不带入补证，避免显示字段令单条证明超限。定向吊销kind20使用可选TLV字段`0x1c`携带该条目，kind21的同字段为32字节SHA-256摘要。当前报文允许不附归属补证的吊销及确认，它们不表示接收方已取得正面设备归属；不附补证摘要的确认只能确认相应吊销原件。发送方首次取得补证后重置这条吊销各收件人的确认，不附补证摘要的确认不能停止补证；接收方核对用户、设备和原设备自签名后，把归属及吊销同事务提交才回确认。首次保存的证明固定，后来的别名或加入时间变体不反复重置队列；收到吊销的首次本机时刻不因补证改变（{need}`TASK_20261030_HJ35GF3WY0Z6CF3X`、{need}`TASK_20260920_GSW6Y996D2E1E681`）。

### 并发签发的合并规则

单调递增的版本号只在单一签发者下成立。持有用户私钥的设备可以有多台，它们在断连
期间各自从版本 `v` 签出不同的 `v+1`，而两个联系人可能以相反的顺序收到——只按"版本
更大者胜"或"后到者胜"都会让双方的成员视图分叉。

因此设备列表不作为不可分割的快照传播，而是**一组可合并的、各自签名的设备操作**
（加入、改名、吊销），版本号只用于检测落后与触发补齐。合并规则固定两条：加入与
改名按操作标识取并集；**吊销一经出现即永久生效，不能被任何未包含它的旧快照或并发
操作覆盖**。第二条是刻意不对称的——漏掉一次加入只是某台设备暂时收不到消息，漏掉
一次吊销则是一台本该被切断的设备继续收消息。

实现保留每批原始用户签名的`SignedDeviceList`，而不是声称签名过的快照也签了它与另一份快照的并集。先分别验证批次根签名、用户归属及设备自签名，再按`(批次版本, 批次签名字节)`的确定顺序选择每台设备的条目；不使用到达时刻或签发时间选胜者。同版本不同签名与较低版本中尚未见过的加入都参与合并，缺席不等于吊销；较低排名不能覆盖已知较高排名的改名。合并外层摘要仅是变更标识，不是新用户签名，接收方须从原批次重算投影核对（{need}`TASK_20260919_35DXYYM7SVWXGTXR`、{need}`TASK_20260920_GSW6Y996D2E1E681`）。

投影只保留支撑各胜出条目的批次及最高版本见证，不保留完整投递流水。N台设备最多N+1份原批次，最坏仍可包含O(N²)条目；后续真实签发的完整新名单可压缩被取代的见证，但不能伪造根签名或让永久吊销消失。该空间界限不等于全进程内存上限，也不意味着旧客户端能够验证合并摘要或互通（{need}`TASK_20260919_35DXYYM7SVWXGTXR`）。

### 吊销的判定只用本地时间

收到某设备的吊销声明之后，本机拒绝该设备此后**到达**的一切消息，不看消息自称的
创建时间。判定依据是两个本机自己观察到的时刻：这条消息何时到达本机，以及吊销声明
何时到达本机。

理由是对称的一句话：创建时间由发送设备自己写入，一台已被吊销但仍持有设备私钥的
机器可以把它设成吊销之前的任何时刻；而本机的接收时刻不受对方摆布。对于在声明到达
之前就已经接受的消息，事后无法分辨真伪，因此标记为"来自已吊销设备、其声称时间
无法核实"交给用户判断，不假装能判定。

本机收到针对“当前身份用户＋本机设备公钥”的有效永久吊销后，旧密码组仍列本机为成员也不恢复授权。入站验签后仅继续接收公开设备名单和吊销原件；其它接入、私有同步、组操作及恢复包作为正常拒收结束，不推进密码状态、不落新业务内容、不生成应用回信，也不把成员授权失败上抛为其它设备同步失败。缺少正面绑定、尚在加入流程的设备不等于已吊销；其它用户或其它设备的吊销也不触发这个本机终态。既有本机数据不因此自动擦除。该边界复用用户维度吊销的不复活及不跨用户抑制规则，实际入站回归另验证密码状态、原件和回信游标均不推进。

### 静态加密

数据库密钥被封装两次，两份封装存放在数据库旁的一个文件里：

- 用应用锁口令封装。口令先与一个仅存于本机系统钥匙串的随机值绑定，再经 Argon2id
  拉伸。
- 用恢复短语派生的密钥封装。

**方向性必须写明**（{need}`TASK_20260919_M09VDQV6DHRV5633`）：整体强度是所有封装中最弱的那一条。口令这条之所以绑定本机钥匙串
随机值，正是为了让它**不可移植**——把数据库与封装文件拷到另一台机器上，即使输对
口令也打不开；恢复短语是那条可移植的路。若再加一条纯口令的可移植封装，整个方案的
强度就塌缩到口令熵，因此不能加。

具体算法与参数见[技术选型](decisions/technology-stack.md)。另有两条实现要守住的判据，
各自的承接写在它们自己那一条上：

**恢复短语取 24 词，不取 12。**它是用户私钥的可书写形式：一旦它与全部持有用户私钥的
设备一同丢失，签发设备条目与吊销声明的能力就**永久消失**。这条的代价是不对称的——多抄
12 个词是一次性的麻烦，熵不够是不可挽回的。

**口令错与封装损坏不得区分**（{need}`TASK_20260919_M09VDQV6DHRV5633`），一律报「解不开」。区分它们等于给出一个判定口令的旁路：
拿到封装文件的人可以据此确认某个口令是否正确，而不必真的打开数据库。恢复短语则不同——
词不在词表里或校验位不符是**输入本身不合法**，能当场判定且不泄漏任何关于正确短语的信息，
因此单独报告，这对打错一个词的用户有用。

**恢复短语与用户私钥是同一份材料的两种写法**，不是两个独立的秘密。设计正文说的
「恢复短语是用户私钥的可书写形式」要落到实现上：**同一份 32 字节的熵既作为用户私钥的
种子，又生成 BIP39 助记词**；种子随其余密钥材料存在加密库内。

由此推出两件事：

- 「设置中再次查看恢复短语」**不需要另存短语副本**——解锁之后从种子重新导出即可
  （本组两条均由 {need}`TASK_20260919_YNE0A885R3XZ7TV2` 承接）。
  若把短语另存一份，就凭空多出一处可被取得的副本，而该需求的来源理由正是要避免这个。
- 种子**只能写入一次**。它是本用户的根，改它等于换了一个人；实现上第二次写入必须失败，
  而不是悄悄覆盖。

「再次查看」这个入口要**当场再要一次应用锁口令**，不复用「当前已解锁」这个状态：
已解锁只说明此前输过口令，而屏幕摊在那里时那拦不住任何人。

**恢复这条路不得读取钥匙串。**它是可移植的那条，一旦依赖本机钥匙串就失去了存在的理由。
实现上这一条要落在**接口形状**上而不是靠自觉：解封的入口不接受钥匙串参数，拿不到就不可能
依赖（{need}`UC_20260918_KW9DXS3704B5MYB2`）。

身份构造的独占范围早于开库：创建、恢复短语加入和无用户私钥加入，必须先取得不可克隆的`InstanceOwner`，才访问Keychain或写密钥封装/元数据。失败时仍持有同一owner，只回滚本次新建文件；已有数据库缺少对应密钥时拒绝覆盖。构造完成把owner直接交给Store/AppLock，不释放后重抢。已解锁时再次查看短语以实际数据库密钥作常量时间凭据校验，不为查看重开Store，也不延长空闲期限。该边界来自`identity_construction.qnt`及真实并发/失败重试回归，不把单个Identity互斥锁当作跨进程写者保护。身份构造及真实多实例/失败恢复由{need}`TASK_20260919_YNE0A885R3XZ7TV2`和{need}`TASK_20261105_YPAH5T3KWHKKYV5B`承接。

Keychain只在`NoEntry`时生成并保存随机值；权限、平台/临时读取错误及损坏长度均拒绝，不能覆盖旧值，写失败不能返回未保存值。目录隔离不等于Keychain隔离：正式service为`YoChat`，E2E为`YoChat E2E`，二进制与对应清理helper须成对冻结，不能用新helper清理旧生产service。E2E有界清理只针对测试service，只有系统44（未找到）可忽略；生产配置专项的测试账号则按本次精确账号清单清理，不能整服务删除。错误分类回归不替代真实OS故障注入；分类及原生账号隔离分别由{need}`TASK_20261105_Y730729MBTAQEJ8S`和{need}`TASK_20261105_NJDK86BZVP0DHH4M`承接。

### 设备级密码私料的唯一所有权

一次性私料由设备级Protocol账本唯一保存，组快照不携带可复活它的副本。同一包跨会话也只能消耗一次；等待较久的组使用设备当前材料，不能因旧组快照看不到后来发布的包而误判已消费。成功消费与组状态、原始签名操作及生成效果同事务提交，失败恢复整个候选。当前格式拒绝旧私料布局；已有组却缺少全局Protocol时明确失败，不隐式生成另一加密身份，无关的本地历史读取不因此被禁用（{need}`TASK_20261030_8AFPXVWJPSERSDAG`）。

准备材料的隔离、容量、剩余有效期以及终局决定归[本地存储的密码状态契约](local-store.md#DOC_20260918_9810WZW7EA7H8FC5--architecture)，不能以取消网络尝试为由删除仍可能被迟到控制引用的密钥。共享预密钥模型只展开单设备串行Store中的两组、三个密钥编号，签名、X3DH和实际SQL原子性由真实回归补查；它不证明任意多进程并发写入或永久离线下完成（{need}`TASK_20261030_8AFPXVWJPSERSDAG`、{need}`TASK_20260920_GSW6Y996D2E1E681`）。

### 应用锁与聊天会话代数

每次解锁产生一个新的聊天会话代数。所有跨界请求在发起时捕获当时的代数，结果返回时
必须同时满足三条才允许写入：实例相同、代数相同、且**当前处于已解锁状态**
（{need}`TASK_20260919_CNDAGMZJP5S3CJ6R`，它的 verify 里逐条造了不满足的情形）。

**锁定动作本身立即使当前代数失效**，而不是等到下一次解锁才换新的。差别在那段
无人看管的时间里：若只在解锁时换代数，锁定之后、再次解锁之前返回的结果，其代数
看上去仍然有效，照样会落到界面上——而那正是屏幕摊在那里的时候。第三条"当前已解锁"
正是为这段窗口而设。

锁定、空闲自动锁定与切换实例走同一条路径，因此不存在"某一种比另一种弱"的可能。

空闲自动锁定默认启用，期限五分钟；主界面可设为 1–1440 分钟，设置按实例持久保存。
Rust 使用进程内单调时钟，只有窗口收到的可信指针、滚轮和键盘输入可续期；收包、同步、
状态查询和异步答复都不续期。用户输入先检查截止，再续期，因此截止时刻的迟到输入不能
救回旧会话。缩短期限按最近一次真实输入重新计算，可立即触发锁定。

数据库入口与独立的 250 毫秒后台心跳检查相同截止；心跳在数据库互斥区繁忙时跳过本轮，
下一次取得锁后检查，库入口在接纳新操作前也检查。该调度前提是现有数据库操作会有界结束、
运行时最终继续调度。UI 同样用单调时钟保存截止，250 毫秒检查并在每次跨界结果落地前检查，
锁定先移除主界面和短语再等待 IPC。暂停的窗口恢复后，旧结果先经过截止与会话所有权检查。
解锁创建新会话；旧成功、旧错误与旧锁定确认均不能恢复锁定前的主界面。
所有可排队的锁定、续期和期限设置 IPC 都携带发起时的会话代数（十进制字符串，避免 JS
整数精度损失），Rust 在身份互斥区内比较当前代数后才改变状态。旧请求即使超过 UI 五秒
等待期限才真正执行，也不能锁住或续期后来解锁的新会话。初次取得权威状态与代数前，
UI 不展示主界面或恢复短语、不发送续期/设置；丢失的状态查询不会放出秘密
（{need}`TASK_20261105_CTXDXSBVFZNMNBG3`）。

### 实例隔离

每个实例——不同用户，或同一用户的不同设备实例——拥有独立的数据目录、独立的数据库
密钥、独立的钥匙串条目与独立的设备密钥对。同一用户的多个设备实例在协议上就是多台
设备，因此一台机器就能演练多设备同步、历史同步与吊销。

## 失败处理

钥匙串不可用时，依赖它的操作（用口令解锁、改口令）**拒绝执行并说明原因**，不降级
为不绑定钥匙串的弱封装——降级会悄悄把不可移植性去掉，而用户无从察觉。此时恢复短语
仍然可用，界面应当指出这一点。

封装文件缺失或损坏时明确报告，不尝试重建数据库（{need}`TASK_20260919_M09VDQV6DHRV5633`）：重建等于丢掉全部历史，而这必须是
用户知情后的选择。

签名验证失败、条目归属不符或合并投影不能由原签名批次重算时，一律丢弃并计数，不向来源产生任何响应。不能仅因批次版本较低或同版本签名不同就当作重放丢弃，合法并发批次按上述合并契约处理。丢弃由{need}`TASK_20260919_35DXYYM7SVWXGTXR`承接，诊断计数由{need}`TASK_20260919_DAY5XXYDM3XKNHEH`承接；持续验签失败本身是值得注意的信号。

## 验证

Quint 建模设备加入与吊销在并发下的收敛，以及吊销声明传播过程中各联系人视图不一致
的窗口。传播延迟与设备离线作为显式动作建模，允许某台设备永不再上线。

本篇的等待与其超时动作：

| 等待 | 超时动作的效果 | 是否有界 |
|---|---|---|
| 吊销声明传播到某个联系人 | 向尚未确认的对端重播一次 | 每个对端在一个时间窗内有上限，窗口滚动后恢复；**对端转为可达时另重播一次**（受架构篇的纪元切换上限约束） |
| 用户私钥同步的两端确认 | 该次同步作废，双方清除本次同步的一切中间状态，须重新发起 | 单调，作废后不重复触发 |
| 空闲自动锁定 | 锁定应用，作废当前聊天会话代数 | 单调，锁定后不重复触发 |
| 等待设备列表补齐 | 向本人其他设备与该用户的联系人重新请求 | 每个连通纪元内有上限 |
| 等待加入事件（已见到更高版本的设备列表） | 标记该版本为"变更来源未知"并告警 | 单调，不重复触发 |

检验的安全性质（在任意交错与任意超时序列下成立）：收到吊销声明之后不再接受该设备
的任何消息；一条吊销一旦被某方接受就不会被任何后到的旧快照撤销；重播次数在任意一个滑动时间窗内不超过所配置的上限（与上表口径
一致，不是全执行累计——累计口径会与"窗口滚动后恢复"自相矛盾）；空闲自动锁定触发之后，锁定前产生的结果不再落地。

活性则写明前提——**在某台设备最终稳定在线（◇□online）的前提下**，它最终收到吊销并停止
被接受。取 `◇□` 而不是 `□◇`：重播由本机的时间窗定时器驱动，若对端每次上线都恰好落在两次
重播之间，`□◇online` 成立而吊销永不送达；上表新增的"对端转为可达时另重播一次"正是为了
让这条活性不再只依赖定时器的运气。

它的安全对偶不依赖该前提：前提不成立时，该联系人的吊销传播状态停在"尚未送达"。这个状态
是 `State` 里每个联系人的一个字段，不是界面上的一句话——靠界面成立的对偶在模型里没有
载体，无法检验。

一次性私钥不出现在这里：它只存在于签发对应邀请的那台设备上，不跨设备同步，因此没有
"清除进度"这回事，见[好友交换](contact-exchange.md)。

proptest 覆盖：数据库密钥两条封装路径的往返、聊天会话代数过滤的性质（任意请求与锁定
交错下，旧代数结果永不落地）、设备列表版本单调性。

Kani 覆盖设备列表与吊销声明的解析，包括长度、条目数与版本号的边界。

静态加密的验收要在未解锁状态下扫描整个数据目录，确认不存在可直接读出的消息正文、
联系人名称或密钥材料；这条以实际文件内容为准，不以代码路径为准。
