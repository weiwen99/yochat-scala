# 好友交换

<!-- tao:section overview -->
## 概述

本篇界定邀请与应答的结构与签名覆盖范围、一次性密钥的生命周期、安全码的构造，以及
联系人关系的状态机。密钥层次见[用户、密钥与设备](keys-and-devices.md)，关系建立
之后的消息通道见[消息](messaging.md)。

<!-- tao:section architecture -->
## 边界与架构

### 邀请

邀请是一段可以被人复制粘贴到任意渠道的文本，携带：

- 协议版本与用途标签 `yochat/invite/v1`
- 发起方**用户公钥**
- **本方渠道标签**与**本方权威账号**——即发起方自己在该渠道上的账号
- 定向邀请另有**对方权威账号**——被邀请方在同一渠道上的账号
- 一次性公钥（本份邀请专用，它同时就是邀请标识）
- 一个**设备公钥**：签发这份邀请的那台设备。它不用于接收应答——应答经渠道回传，
  见「承载形式」；它是关系建立之后对方投递第一条操作与后续消息的地址
- 有效期
- 可选的一段备注
- 以上全部内容由发起方的**用户私钥**签名

由用户私钥而不是设备私钥签名，是一个保守的选择：加好友不频繁，而且敏感，值得要求
持有用户私钥的那台设备在场。它的收益要说准确：**一台不持有用户私钥的设备，无论是否
已被吊销，都签不出邀请与应答**，因此不能以本人名义去认识新的人——这一点在把签名交给
设备私钥的方案里做不到，因为吊销只随设备列表分发给已有联系人，从未与本人打过交道的人
无从得知它，而安全码由双方用户公钥导出、那把公钥是真的，也拦不住。

**但对仍持有用户私钥的被吊销设备，这条收益不成立**：它能签出完全合法的邀请与应答，
还能签新的设备列表把自己加回去、并对合法设备签发吊销。持有用户私钥就等于持有这个身份，
它属于恢复短语泄漏那一类威胁，不是吊销能处理的。文档各处不得把收窄后的结论写成全称（{need}`TASK_20260919_WPP64DJDH6659YMQ`）。曾经考虑过的「内嵌签名设备列表 + 设备
私钥签名」方案让不持用户私钥的设备也能离线发邀请，代价正是上面这条，权衡之后不取。

邀请不携带用户别名，也不内嵌设备列表：别名、头像与完整设备列表都在关系建立之后经
已建立的通道同步。这样公开张贴一份邀请的暴露面只有用户公钥、渠道账号、一台设备公钥
与有效期。

只放签发设备一台，是因为解开应答需要那份一次性私钥，而它只在这台设备上：**应答必须
在签发该邀请的设备上粘贴与确认**，界面在其他设备上如实提示应去哪台设备处理。私钥不
离开签发设备，作废因此是真正的收回（{need}`TASK_20260919_5NM8Z6W23J25315B`）。

**定向邀请**额外声明被邀请方的渠道账号，应答方界面据此核对"这份邀请是不是给我的"；
**不定向邀请**不指定接收者，可以贴出去被多个人分别应答。界面优先推荐定向邀请。

### 承载形式

两者都以深层链接文本承载，路径对称：

```text
yochat://friend/invite?v=1&d=<base64url-unpadded>
yochat://friend/reply?v=1&d=<base64url-unpadded>
```

**邀请与应答都由人复制粘贴，经双方已经在用的那条渠道传递**；YoChat 不从网络接受入站
的邀请或应答。这一条是渠道绑定成立的前提：绑定靠的是把「渠道说这条消息是谁发的」与
「产物自己说它是谁的」对起来，而经网络直投的产物没有前者可比。

版本以 TLV 内的版本字段为准；外层 `v=` 存在时必须与之逐字相等，不等即拒——它只是一层
不解码的快速筛，不是权威来源（裸 `d` 形式下没有外层 `v`；{need}`TASK_20260919_5NM8Z6W23J25315B`）。`d` 是该产物的规范编码，
整体 base64url 无填充。

规范编码是**二进制 TLV**：1 字节 tag、**2 字节大端长度**、值。长度定长而不是"短则一字节、
长则两字节"——后者没有任何比特能告诉解码器该读几字节，根本无法解析，而"唯一最短形式"
这类规则只有在长度字段本身可自描述时才有意义。定长两字节每个字段多花一字节，换来解析
无歧义（{need}`TASK_20260919_5NM8Z6W23J25315B`），这笔交换在这里是划算的。值长度上限因此是 65535，任何超出的输入一律拒绝。

为使同一份内容只有一种编码，另有三条写死：

1. **可选字段缺省时不得出现其 tag**，不允许长度为 0 的占位
   （本组三条均由 {need}`TASK_20260919_5NM8Z6W23J25315B` 的解码器性质测试承接）。
2. **base64url 无填充解码必须拒绝**含填充字符、含字母表之外字符、以及尾部冗余比特非零
   的输入。
3. **签名字段整条 TLV（tag、长度、值）都不参与被签字节**；邀请摘要覆盖的是包含签名字段
   在内的完整规范编码，因为应答要绑定的是"那一份邀请"这个整体。

各 tag 的编号、是否必需、长度上下界与值域：

| tag | 字段 | 必需 | 长度 |
|---|---|---|---|
| 0x01 | 协议版本 | 是 | 1 |
| 0x02 | 用途标签 | 是 | 1–32 |
| 0x03 | 本方用户公钥 | 是 | 32 |
| 0x04 | 本方渠道标签 | 是 | 1–32 |
| 0x05 | 本方权威账号 | 渠道非"当面"时必需 | 0–64 |
| 0x06 | 对方权威账号（仅定向邀请） | 否 | 1–64 |
| 0x07 | 一次性公钥（邀请）／邀请标识（应答） | 是 | 32 |
| 0x08 | 设备公钥 | 是 | 32 |
| 0x09 | 有效期（Unix 秒，大端） | 邀请必需 | 8 |
| 0x0A | 所应答邀请的摘要（仅应答） | 应答必需 | 32 |
| 0x0B | 备注 | 否 | 1–200 |
| 0x0C | HPKE 封装密钥（仅应答外层） | 应答必需 | 32 |
| 0x0D | 密文（仅应答外层） | 应答必需 | 1–65535 |
| 0x0E | 联系人私有发现能力（仅应答密文内层） | 应答必需 | 32 |
| 0x7F | 签名 | 是 | 64 |

字段按 tag 升序出现且不得重复；任何版本下遇到未知 tag 一律整条拒绝（{need}`TASK_20260919_5NM8Z6W23J25315B`）。**接收方必须先把
收到的 TLV 重新规范化，与原字节逐字节相等才继续**，摘要与验签一律在规范化后的字节上
计算。没有这一条，两串不同字节可以解出同一份逻辑内容而双方算出不同摘要：一个旁观者
只要转贴一份等价重编码的邀请，就能让应答在发起方处静默失配，双方都以为对方没理自己。

签名覆盖**除签名字段本身之外的全部 TLV 字节**，其中包含协议版本与用途标签。六类签名
产物各带一个被签名覆盖的用途标签，互不通用：`yochat/invite/v1`、`yochat/reply/v1`、
`yochat/device-list/v1`、`yochat/device-entry/v1`、`yochat/revocation/v1`、
`yochat/profile/v1`（其中 device-entry 由设备私钥签名，其余由用户私钥签名，
见[密钥与设备](keys-and-devices.md)）。没有这道域分隔，一个正确的签名可能被搬到
另一类产物上复用。

不用 `k=v` 文本承载字段：公钥与签名是二进制，在 `k=v` 里要先编码一次、外层再编码
一次，三把公钥加一个签名共 160 字节，TLV 方案占 216 字符而 `k=v` 方案约 288 字符，
还没算键名与分隔符。更重要的是签名必须覆盖一份唯一确定的编码（{need}`TASK_20260919_5NM8Z6W23J25315B`），而查询参数的顺序、
转义与重复键都会让"规范编码"出现歧义，那是签名绕过的经典来源。

解析器宽进：接受完整链接、省略 scheme 的 `friend/invite?...`、以及裸的 `d`。界面另
提供"复制为纯文本"直接输出裸 `d`，用于会破坏链接的渠道（例如微信不让自定义 scheme
被点击）；二维码编码同一个规范串。生成时检查总长度，超出上限时提示缩短备注（{need}`TASK_20260919_5NM8Z6W23J25315B`），不得
静默截断。

### 应答

应答的 TLV 分两段：**明文头**含协议版本、用途标签 `yochat/reply/v1` 与邀请标识（即该
邀请的一次性公钥）；**密文**用该一次性公钥加密，含所应答邀请的摘要、应答方用户公钥、
**本方渠道标签**与**本方权威账号**（即应答方自己在该渠道上的账号）、应答方用于本次交换
的一台设备公钥、随机32字节联系人私有发现能力、可选备注，以及应答方**用户私钥**的签名。

能力与其它内层字段共同签名并经HPKE加密，不进入明文头、公开设备列表或资料。能力按双方用户、邀请摘要及能力本身导出相同的发现作用域，两端本地联系人代次独立保存。重复生成同一交换的应答须复用首次已提交能力；应答返回前，能力、关系和原交换设备准入同事务持久化。发起方仅在显式确认时将能力移入当前联系人作用域，与关系/设备绑定/删除待确认同事务提交；拒绝、过期确认、删除或拉黑不得由旧待确认恢复权限。能力只用于定位与密文外层，不能替代当前设备授权或触发应答方提前私有回应；本人多设备传递仅走认证加密的私有通道，具体接替契约见[自动接替候选](decisions/contact-bootstrap-takeover.md)。未发布协议不接受缺少该字段的旧应答（{need}`TASK_20261106_5QSVAWH365EDWNBW`）。

封装用 **HPKE（RFC 9180）base 模式**，套件为 X25519 + HKDF-SHA256 + ChaCha20-Poly1305，
接收方公钥即该邀请的一次性公钥；**AAD 为明文头的规范编码字节**（{need}`TASK_20260920_F5MDP1BS4S20XGC4`）。不写死这一套，"明文头作
AAD"就没有承载它的原语，实现者只能自己猜一种封装。

一次性公钥因此是一把 **X25519** 公钥，不是签名用的 ed25519——它是这套 KEM 的接收方公钥。
本机只保存导出它的那 32 字节输入材料，公私钥都由该材料导出，于是不存在"私钥还在、公钥
对不上"这种半截状态。HPKE 的 `info` 取 `yochat/reply-hpke/v1`，与摘要的用途标签同理：
给这一套封装一个自己的域。

**「明文头进签名」今天没有能走通整条验证顺序的攻击反例**，这一点要写明而不是含糊过去：
明文头里只有版本、用途与邀请标识，标识由验证顺序的第 1、4 步各钉一次，而版本与用途各只有
一个合法取值。它防的是**将来同时接受两个版本时**的降级。因此对它的检查落在"签名前像确实
包含明文头"这一条上，而不是一个攻击反例。

签名覆盖**明文头与密文明文内容的规范编码字节**，两段之间以各自的 4 字节大端长度前缀分隔
（`len(明文头) ‖ 明文头 ‖ len(密文明文) ‖ 密文明文`），避免两段无边界拼接时可以互相挪用
字节。
明文头不在签名与 AAD 之下时，任何能重投这串字节的人都可以改写版本而验签照样通过，
同一段密文就会被按另一版规则解释——设计既然写明「忽略未知字段等于给降级攻击留口子」，
就不能把版本本身放在覆盖范围之外。

两份产物各自只声明**本方**的账号，不替对方声明——定向邀请里的对方账号是发起方指定
的收件人，不是对方的自述。字段名就按"本方"与"对方"固定下来，避免实现时把方向弄反。

标识放在密文之外，是为了让发起方直接定位是哪一份邀请，不必对每份有效邀请逐一试解；
否则畸形应答的解密开销随有效邀请数线性放大。标识本来就是公开的，明文携带无额外暴露。

**签名必须覆盖规范编码后的整份邀请的摘要**——含发起方用户公钥、渠道账号、有效期、
一次性公钥、邀请所载设备公钥、协议版本与用途标签——**以及应答方自己声明的全部内容**（{need}`TASK_20260920_F5MDP1BS4S20XGC4`）。
邀请摘要取 `SHA-256("yochat/invite-digest/v1" ‖ 规范编码字节)`，用途标签使它不与安全码、
逻辑消息标识等其他摘要混用。

只覆盖邀请标识是不够的，这里有一条现实的绕过：标识就是那把一次性公钥，而它在邀请
里是公开的。任何看到邀请的人都能复用它另造一份署名自己的邀请拿去给
第三方，再把收到的应答转交原发起方——两份邀请的标识相同，应答在原发起方处既能
解开也能验签，于是他会把一份并非给他的授权当成给自己的。覆盖整份邀请之后，应答
与它实际应答的那一份绑死。

覆盖应答方自己声明的设备公钥与渠道账号，则是堵另一条路：拿到一次性私钥但没有对方
用户私钥的攻击者，会试图解开应答、换进自己的设备或账号再转投。整份应答由应答方的
用户私钥签名，攻击者伪造不了。

加密使应答方不必向发起方之外的任何人公开自己的标识。这造成一个必须让用户知道的
不对称：**发邀请的一方暴露设备公钥与渠道账号，应答的一方不暴露**，所以"由谁发邀请"
是一个有隐私后果的选择（{need}`TASK_20260919_5NM8Z6W23J25315B`，它逐字核对公开张贴与定向邀请的代价文案）。

### 渠道绑定怎么生效

这套绑定的适用前提是：邀请与应答**经由一条能显示发件人的中心化渠道传递**（微信之类）。
在这个前提下，绑定靠的是一次**两个方向各做一次**的人工比对：

1. A 在渠道上把邀请发给 B。B 看到两个账号：渠道自己显示的**发件账号**，以及邀请里
   声明的**本方权威账号**。B 比对这两者是否一致——不一致就说明这份邀请不是从它声称
   的那个账号发出来的（例如被人从别处转发过来）。
2. B 在同一条渠道上把应答发回。A 同样比对渠道显示的发件账号与应答里声明的本方权威
   账号。

比对的对象始终是"渠道说这条消息是谁发的"与"产物自己说它是谁的"。这就是为什么账号
必须是该渠道权威、全局唯一、不由用户随手改动的那一个——昵称、备注可以随手改成任何
样子，比对它等于没比。也是为什么两份产物各自只声明本方账号：一方替另一方声明的东西，
对另一方而言没有任何证明力（{need}`TASK_20260919_QDJR74RRME6FVXED`）。

定向邀请多一道：邀请里还有发起方指定的**对方权威账号**，B 可以据此核对"这份邀请是
不是给我的"，A 在确认时也能核对应答方声明的本方账号是否就是自己指定的那个。不符时
醒目告警而不自动接受——填错账号的也可能是个合法的应答方，这个判断留给人。

这一道可以由应用代劳：本机保存着本方的渠道身份表（见[本地存储](local-store.md)），
收到定向邀请时直接把其中指定的对方账号与本方同渠道的已保存账号比对，把结果摆在界面
上。**但只有这一道能自动**（{need}`TASK_20260919_QDJR74RRME6FVXED`）——第 1、2 步比对的是"渠道说这条消息是谁发的"，而 YoChat
读不到微信之类渠道的发件人，那必须由人来做。本方账号缺失时如实提示补充，不得因为
比不了就显示为相符。

签名覆盖这些账号字段，所以中途改不了；但签名证明不了账号的归属，那是渠道的事。
整条绑定的强度因此不超过该渠道对账号所有权的保证，也不能替代安全码比对——安全码的价值
恰恰在于它不依赖这条渠道。

**当面交换与二维码不在这个前提内**，要单独留位置：那里没有"渠道发件账号"这种东西可比，
硬要填一个账号只会让用户学会随便填，等到真正需要比对的那次也照填不误。因此内置一个渠道
取值"当面"，选它时账号可空（TLV 里那个 tag 缺省），界面显示的不是"回到渠道核对发件账号"
而是"当面交换，建议当场完成安全码比对"——当面其实比任何渠道绑定都强，只是此前文档没有为
它留位置。

两条边界要写死，否则"当面"会变成一个绕过检查的口子：

- 渠道**不是**"当面"而账号缺省的邀请或应答，接收方一律拒绝
  （本组两条由 {need}`TASK_20260919_QDJR74RRME6FVXED` 承接）；
- 渠道是"当面"时**不支持定向邀请**——定向邀请按定义要指定对方在该渠道上的账号，而当面
  没有账号可指。界面在选"当面"时隐藏定向选项。绝不能出现"当面 + 定向 + 空账号"然后把
  自动比对判成"相符"，那正是规格明令禁止的"把无法比对显示为相符"。

### 一次性密钥的生命周期

生成邀请时创建一对一次性密钥，私钥随邀请记录保存在**签发这份邀请的那台设备**上，
不同步到本人其他设备。作废就是在该设备停止受理并覆盖该私钥的存储；因为别处没有副本，
不再需要"清除进度"这种两段式承诺。

承诺的强度要与本地存储一致，不能更强：与本机全部数据一样，**物理不可恢复不在承诺范围
内**——按[本地存储](local-store.md)自己写明的边界，预写日志与空闲页可能仍持有旧字节，
其保护来自数据库整体加密。因此不能写"该私钥不再存在于任何设备上"或"截获的应答再也打
不开"这类无条件表述：那既超出机制，也没有任何可执行的检查能通过它。一次性私钥单独成表，
作废时执行该表的安全覆写；与全部私钥材料一样，它不写入任何日志或崩溃报告。

吊销一台设备时，把它签发的全部未过期邀请一并作废并提示重新生成——那些邀请的一次性
私钥就在它上面，而它已经不被信任，不会配合删除。不向已被吊销的设备发送任何作废
指令：一台不被信任的设备不会因为收到一条指令就去删钥。

代价不在投递上——应答经渠道回传，不存在投不进来这回事——而在于**解开应答必须在签发
这份邀请的那台设备上**：那台设备不在手边时，粘贴应答的动作就得等它。这是"作废可兑现"
换来的，取舍写在规格的一次性公钥需求里（{need}`TASK_20260919_5NM8Z6W23J25315B`）。

### 安全码

首版采用可重算的构造，参数固定如下：

- 派生：`HKDF-SHA256`，用途标签 `yochat/safety-number/v1` 作为 info
- 输入：双方用户公钥按字节序升序排序后拼接（排序使两侧算出同一个值）
- 输出：**128 位**
- 展示：把这 128 位当作无符号整数，十进制零填充到 39 位数字，分成两段（前 20 位与后
  19 位），每 5 位一组断开
- **谁念哪一段是确定的**：用户公钥按字节序**较小**的一方念第一段（前 20 位），较大的
  一方念第二段（后 19 位）；两侧界面各自据此显示"你念哪一段、你核对哪一段"

参数写死到字节，否则写不出可互操作的实现：`salt` 为空（按 RFC 5869 即全零）；
`IKM = pk_min ‖ pk_max`，两把用户公钥各 32 字节原始编码、按字节序升序拼接；
`info` 为 `yochat/safety-number/v1` 的 UTF-8 字节；输出长度 `L = 16`。

测试向量由**独立实现**给出（`tools/safety_number_vectors.py`：按 RFC 5869 逐步手写 HKDF，
只用 Python 标准库的 hmac 与 hashlib，不碰任何与本项目实现同源的库）。本实现与它逐位相符：

| pk_a | pk_b | 输出（十六进制） | 39 位十进制（前 20 ‖ 后 19） |
|---|---|---|---|
| `00×32` | `01×32` | `f32a5f4e2eba2007bb0d6edcfb6e8de5` | `32322241246696336480` ‖ `9895409466880200165` |
| `00,01,…,1f` | `1f,1e,…,00` | `ad7fe2dba5878e134963cf6a9150aeb3` | `23062046619859128756` ‖ `0574654139576921779` |
| `07×32` | `07×32` | `ff9e47ee75acd510127efb1bb189ad1e` | `33977498077260527556` ‖ `9903690618547842334` |
| `09×31‖00` | `09×31‖01` | `2906b33df51052cd3161c7ffc47d017a` | `05453313706841328801` ‖ `2493603621289394554` |

交换两个输入的顺序必须得到同一个值——排序正是为此（{need}`TASK_20260919_20WC4ZWNSZY85QWY`）。

**明示的上界**：做 q 次派生的成功概率不超过 q² / 2¹²⁸。这是生日界，也是本设计对外承诺的
那一条（{need}`TASK_20260919_20WC4ZWNSZY85QWY`）；实际强度分两种情形，必须都写出来，不能只挑高的那个说：

- **攻击者事先不知道应答方的用户公钥**时（本组两种情形同归
  {need}`TASK_20260919_20WC4ZWNSZY85QWY`），他必须先把冒充发起方的公钥写进转发出去的邀请，
  之后才从应答里读到对方的真实公钥，此时一侧的安全码已经固定，只能搜另一把密钥去命中，
  那是单目标搜索，约 2¹²⁸。
- **攻击者事先知道双方的用户公钥**时（公开张贴邀请恰恰使公钥公开，对方也贴过邀请就更是
  如此），他可以两侧同时搜，退化为生日界 2⁶⁴。

因此对外承诺按 2⁶⁴ 这条下界写，单目标那条只作说明。同一节后文讨论分段时用的也是 2⁶⁴
基线，两处口径一致。上界与展示长度必须一起改（{need}`TASK_20260919_20WC4ZWNSZY85QWY`）：截短输出而不改上界，等于悄悄削弱它。

分段分配之所以要写死，是因为安全码对两侧是**对称**的——双方算出同一个值，分段不会自发
产生差异。文档若只说"分成两段各由一方念出"，最自然的实现是两侧界面都写"你念第一段"，
于是两人都念第一段、第二段从未被任何人核对，攻击者只需让 20 位十进制碰撞，成本从 2⁶⁴
掉到约 2³³。性质测试里要有一条：对随机公钥对，两侧算出的"本方应念段"必定不同且并集
覆盖全部 39 位。

任何设备在任何时候都能重算，从而能核对"已校验"这个结论是否仍然对应此刻持有的那把
用户公钥——规格把这条列为必须满足的性质（{need}`TASK_20260919_20WC4ZWNSZY85QWY`）。

比对流程指示双方各念一段、各自核对收到的那一段，任一段不符即判为失败。这不是密码学
上的知识证明——中间人同时看得到双方公钥，算得出真正的安全码——而是流程保障：它逼
双方都真的计算并查看。

界面必须提示换一条渠道比对（{need}`TASK_20260919_20WC4ZWNSZY85QWY`）。安全码全部价值就在于它不依赖传递邀请的那条渠道；在同一
条渠道里比对，控制该渠道的人可以连安全码一起替换。

### 关系状态机

邀请自身的状态：草拟 → 已发布（有效期内）→ 已作废或已过期。

关系的状态在两侧各有一条，必须都写出来，否则链路会断在中间（{need}`TASK_20260919_GWD9N0YMH757CHCV`）。

**发起方**：无关系 → 待确认（收到一份可解开且验签通过的应答）→ 已建立 → 已拉黑；
与应答方对称，另有一条出口：待确认 →（**超过所应答邀请的有效期加同一段宽限**）→ 无关系。
到期之后该应答转为"已过期，无法再确认，请重新交换"，界面不再提供确认入口；**确认动作
本身也要做一次前置检查**，而不是只在收到应答那一刻检查过期。

两侧的时限必须相同且都存在（{need}`TASK_20260919_GWD9N0YMH757CHCV`）。只给应答方加到期、发起方不加，会造出一种谁也发现不了的
坏状态：B 到期降级为无关系，A 此后才点确认并进入已建立、发出组加入操作，而 B 按陌生
对端一律丢弃且不回应——A 的通讯录里多了一个永远发不出消息的"好友"，B 那边什么也没有，
两侧界面给出的原因都是假的。这类执行还骗得过"关系要么建立、要么回到无关系"那条活性：
两侧都不在中间态，性质成立而系统已坏。

**但对称到期并不能消灭这种分叉，只能缩小它的窗口，这一点必须写明而不是假装解决了**（{need}`TASK_20260919_CMQ5HX5V77QHC7KH`，它对保留与不保留短期记录两种取法各实例化一份检验）。
A 在有效期末点确认、组加入操作在途中延迟，到达时 B 已降级，分叉照样发生；把 A 改成"等
对方接入才算已建立"也只是把分叉换个方向——B 的回应一旦丢失，A 到期降级而 B 已经建立。
这是两将军问题：在投递不可靠的前提下，不存在一条能让双方**必然**就"关系是否成立"达成
一致的有限交换。因此本设计不写那条做不到的不变量，改为保证**分叉可被发现、可被恢复**：

- 进入已建立的一侧，若在一个阈值内收不到对方的任何操作，界面如实提示"对方可能没有完成
  这次交换"，并提供"重新交换"入口，该入口清理本地这条关系。
- 降级为无关系的一侧，对该邀请保留一条短期记录（只含邀请标识与对方用户公钥），使同一次
  交换的迟到操作能被识别为"过期交换"而不是陌生对端，界面据此提示重新交换；这条记录不
  产生任何 YoChat 应用层出站数据，不违反对未建立关系对端的沉默规则。

**应答方**：无关系 → 已确认（发出应答的那一刻就进入此态）→ 已建立（收到对方的第一
条操作）→ 已拉黑；另有一条出口：已确认 → 无关系（**超过所应答邀请的有效期加宽限**）。
应答方自发出应答起即接受来自该邀请发起方——其用户公钥取自被应答的那份邀请——的
消息，在收到第一条之前不向对方发送任何东西。

这里的"第一条操作"包括发起方确认时必然发出的**设备组加入操作**，不限于应用消息：
发起方确认之后总要把应答方的设备拉进这个聊天会话的设备组，那条操作由发起设备签名，
本身就是"对方已确认"的可靠信号。若只认应用消息，发起方确认完却不打字，应答方就会
一直显示等待直到超时降级，而关系其实已经成立。

这条不可省略（{need}`TASK_20260919_GWD9N0YMH757CHCV`）：规格规定拒绝时什么都不发，也不应该规定接受时专门发一条什么，于是
应答方无从观察到对方已确认；而它若不认为关系已建立，对方的第一条消息就会被当作
陌生对端丢弃且不回应，对方只能无限兜底重发，首次通信永远建立不起来。让应答本身
构成本方的确认，是补齐链路而不新增消息类型的最小做法。

### 预密钥包在关系建立之后交换（2026-09-22 由用户决定）

建加密组要 X3DH，而 X3DH 要对方的**一次性预密钥包**。这一步先前在设计里是一处真空：
邀请与应答都不带它，而没有它就发不出第一条控制消息——那条消息里的组密钥正是向对方的
包加密的。

三件事是从库里实测出来的，它们把可选项收窄到两条：

1. **两边都要对方的完整一次性包**，不是单向。`Dcgka::encrypt_to` 要收方的包，
   `decrypt_from` 也要发方的包。指望「发起方只给一个 32 字节的身份公钥」是错的。
2. **一次性私钥用一次就被消耗**，再用一次报 `PreKeyReuse`。
3. **`MessageGroup` 的类型参数写死了一次性包**，不接受可复用的长期包。

第一条可选项是把包写进邀请与应答。它更短一个往返、能全程离线完成，但**与「一份不定向
邀请可被多人应答」这条产品承诺相冲突**：一份邀请里只能固化一份一次性包，所有应答者用的
是同一份，第一个人走完之后其余人的握手失败，而失败的形态是「关系建好了、消息发不出去」，
界面解释不了（{need}`TASK_20260919_N0BEHW57ZGWS5B4A`）。

因此取第二条：**关系建立之后经已建立的通道交换预密钥包，然后才建组。**

- 双方进入已建立之后，各自发出一条**预密钥包公告**。它由设备私钥签名，携带公钥材料、收件设备与公告序号。
  公告带两份包：**一次性包**给建组用（用一次就没了），**长期包**给恢复通道用（有效期内
  可反复使用，见[消息](messaging.md)的恢复通道一节）。这一条由
  {need}`TASK_20260923_93MAD0N3VCC6QRBT` 承接。
- 两边都拿到对方的包之后，发起方建组并发出 `create`；应答方处理它、回 `ack`。
- 关系状态因此多一段：**已建立但组未建**。这一段里发不出消息，界面必须如实说明它在
  建立加密通道，**不能显示成「对方没有说话」**——那是一句假解释。对方长时间不发包时，
  与通道长期不可用同一处理：如实告知并说明会在对方上线后自动继续。

**一份一次性包用一次就没了，因此「谁来触发下一份」必须有个着落**
（{need}`TASK_20260923_93MAD0N3VCC6QRBT`）。着落是：本机每认得一台新的对端设备，
就为它生成一份公告，保存待确认的原字节；未确认时最多每五秒补发一次原字节，不重复生成一次性包。公告绑定收件设备和发送方对该设备递增的序号，收方只在密钥登记与接收序号高水位同事务提交后返回签名确认。重复和乱序公告只再确认，不重新登记已消耗的包；旧确认不能清除新的待发公告。每台已知设备只保留一份最新待发字节和一个接收高水位，确认后释放待发字节，重启保持序号与去重结果。发送端私钥材料与公告也同事务保存，避免留下无法解开的公告。设备列表晚到、公告或确认丢失均由后续后台节拍继续；陌生与吊销设备仍先过现有准入。产品不接受旧的无收件人、无序号公告；该格式只留作协议层历史回归样例。两侧走同一条路径，因此各取所需。

可靠offer及其serial属于设备，不属于最初承载它的会话；合法公告可能先在另一会话发送。精确匹配的BundleAck使该offer从待确认转为已确认后，须按当前已认证设备归属找到实际联系人会话，释放仍有效的首次Create可靠效果，不能只看ACK旧信封中的会话。此时仍检查Completed尝试、拉黑和反向offer门槛，不替换原offer、不改变授权或延长期限；清掉offer本身不证明对端已安装通道（{need}`TASK_20260919_N0BEHW57ZGWS5B4A`、{need}`TASK_20261106_24PEVXETDE0NDVEJ`）。

按需补包细化（{need}`TASK_20261031_B8PHGQ7N23VJ9SKM`，生产接线由{need}`TASK_20260920_GSW6Y996D2E1E681`承接）：本机确有建组/加入需求而没有目标的新包时，请求绑定收件设备及本机最后持久登记的该来源公告序号。来源已有待确认公告时重发该原件；没有待确认公告且请求所见序号等于本机当前公告序号时，才同事务生成下一份新包。旧请求不生成新密钥，未来序号拒绝，重复新公告仍按高水位去重；不能把旧确认当作新公告确认。请求走设备签名的握手日志，不依赖正在修复的组密码，也不占聊天日志位置；仍先检查当前关系、设备授权及拉黑。后台周期重试请求与原件，按设备节流，不把空闲状态当作无限补包需求。该请求现已接入自动建组/成员加入缺包及欢迎持久等待重试；单份待发原件的存储界限不等于全部历史未消耗私料有常数空间界限。

补包同时涉及两个方向（{need}`TASK_20261031_B8PHGQ7N23VJ9SKM`）：发起方生成欢迎要用目标的新包，目标回复首次确认也可能消耗帮助者的新包。前一组完成不代表后一组的反向包仍可用；两个方向分别保持序号、高水位和剩余包。目标仅因缺反向包无法处理已验签欢迎时，原件应在受现有等待预算约束的持久队列中保留，按需索取帮助者的新包，收到后用当前授权经正常密码入口重试；失败不先消耗私料、更新组状态或宣告欢迎已处理，重启不丢待处理原件。成功后原件去重、组状态及消耗结果同事务提交，不重新签发帮助者旧控制。当前已接入类型化缺包、持久原件等待和补包后的正常接收重试；主动补包请求已接这些需求；首次联系人建组、旧状态安装与重新接入网络仍由GSW6承接。只有这一可恢复错误进入等待，坏签名、非法成员和实际解密失败仍按原有拒绝路径处理。每次重试重新验证原件与当前授权，不把持久等待当作未来授权；只有实际接收事务成功后移出队列。模型中帮助者持有原件且最终公平供应作为既有可靠重发机制的输入假设，不能据此省略产品中的可靠供应与授权重查。

请求使用kind 23，绑定收件设备及最后持久登记的来源公告序号，0表示尚未收到；编号不超过i64最大值。它由设备签名覆盖并走握手日志，原生位置固定0，不占聊天会话位置，内容为公开设备和公告元数据，不额外应用层加密。接收路径先验签和准入，再核对双方当前有效设备、会话所属用户、精确收件人及观察序号没有领先于当前待发序号，随后才允许关系推进或生成公告。合法首条请求可使已确认应答方进入已建立；非法请求不能借普通元数据供应先生成一份公告，再把自己的未来序号变成有效值。请求只在实际缺新包时发送，按设备而非会话持久节流；有效重试仍复用当前待确认原件（{need}`TASK_20260920_GSW6Y996D2E1E681`、{need}`TASK_20260919_N0BEHW57ZGWS5B4A`）。

同一设备的加密身份固定。公告的一次性包与长期包必须与已登记身份相同，首次公告的两份包也必须互相一致；不一致返回错误，不得触发依赖库的断言。两份包在隔离登记表中均校验成功才安装，后半份无效时不得留下部分登记或恢复已经消耗的公开包（{need}`TASK_20260919_N0BEHW57ZGWS5B4A`）。

长期公开包登记按已验证设备只保留当前有效、`expiry`最远的一份；同expiry保留现候选，总登记随设备数而非公告serial增长，不限制联系人数量。私料和一次性包额度不变，旧私有预密钥继续解迟到欢迎。包过期或墙钟回退到`not_before`之前时明确错误且不变更保存状态，后续当前有效公告可恢复；不为任意旧时钟保留无限历史fallback，也不放宽密码有效期。`longterm_registry.qnt`只承担有限同步登记，实际迟到X3DH、轮换/保存失败及千serial/重启由真实回归承担。

本人私有通道的签名起始记录仅在本人设备间独立使用 kind 18 的定向公告和 kind 19 的确认重试，字段 `0x1b` 承载记录或被确认的创建设备。不把记录附带在可能发给联系人的设备列表里。两者走握手日志并由发送设备签名覆盖，绑定收件设备；记录本身还带用户签名。收方仅接受本人未吊销设备，验证并固定记录后才确认，重复原件仍再确认；确认绑定发送目标与指定创建者，其他设备或旧创建者的确认不能停止当前重试。记录与确认本身没有额外的应用层加密：包含用户公钥、创建设备公钥及签名，网络传输仍由 iroh 加密；收件人只限本人设备。该记录不放入预密钥包，也不以重发记录为由生成新密钥材料。重试与存储边界见[本地存储](local-store.md)。

旧吊销原件（{need}`TASK_20260920_GSW6Y996D2E1E681`）独立使用 kind 20 的定向投递和 kind 21 的确认，复用 `TAG_TARGET_AUTHOR` 与 `TAG_REVOCATION`，走握手日志且序号固定0，不占聊天日志位置。投递承载一条非空、最多4 KiB的用户签名原件；确认中的64字节标识由用户公钥和被吊销设备公钥组成，另绑定收件设备。本人原件可发给本人设备及当前未拉黑联系人设备，联系人原件仅在本人设备间转交；接收方允许本人未吊销设备转交已持有原件，联系人发送方只能转交其本人用户的证明。接收方核对发送设备权限、精确收件人、证明用户归属及用户签名，原件落盘后再签名确认；重复原件再次确认，丢原件或丢确认由持久重试恢复。确认只停止对应发送目标、用户及被吊销设备的投递。设备列表和预密钥握手触发供应，后台继续补发，不为此生成预密钥。载荷本身无额外应用层加密，包含公开吊销身份、时间及用户签名，网络传输由 iroh 加密；原件不含正文、用户私钥或组密钥。既有 `Devices.revocation` 单条格式仍能接收，新路径不把全部历史装进无界数组。持久批量与退避见[本地存储](local-store.md)。

**「对端设备」包括本人的其他设备**（{need}`TASK_20260923_QK7N2XVDR9MHB4TC`）。恢复通道按设备封，
本人设备之间的补齐请求与答复同样要对方的长期包；只向联系人的设备公告的话，本人两台设备
之间一条丢包就会让那个位置永久停住，而界面上看到的是「对方没有说话」。

少了这一条，后加入的那台设备永远拿不到本机的包，而失败的形态正是本节开头点名要避开的
那一种：「关系建好了、消息发不出去」，界面解释不了。

**代价如实记着：预密钥公告及其确认不加密。**内容是公钥材料、设备收件人及公告序号，
拿到它推不出任何内容或用户层身份；但「所有业务消息都加密」这句话从此有一个例外，
不写出来就是在文档里撒谎。

**公告必须由承载它的那条操作签名覆盖——包自己那个签名不够**（{need}`TASK_20260919_N0BEHW57ZGWS5B4A`）。这是实测出来的：
`OneTimeKeyBundle::verify()`只验证签名预密钥及其有效期，一次性预密钥不在包自身的签名覆盖内。因此公告走p2panda操作上线，由设备私钥对整个头及正文哈希签名，覆盖完整包字节；不能把包内验签成功当作整个公告已认证。

**公告不进聊天会话的日志，它走自己的一条标识**（{need}`TASK_20260919_N0BEHW57ZGWS5B4A`）。每台设备在每个聊天会话里维护一条只增
日志（见[消息](messaging.md)的日志与排序一节），而公告不是那条日志上的内容：每份包只够
一个人用，每个对端收到的是不同的一份，收方不可能有完整的前序，因此它构不成一条可校验的
追加链。让它顶着聊天会话的序号 0 上线，还会与那个会话真正的第一条操作撞在一起——而同一个
（作者，会话，序号）配上不同内容，正是日志层用来发现分叉的那种重合。收方据内容种类反过来
核对这个标识：公告必须在握手日志上，控制消息与密文必须在它自称的那个聊天会话的日志上，
不符即整条拒绝。信封的明文头里仍写着聊天会话，收方据它知道这份包是为哪一段关系而来。

只改一次性预密钥的后果是**拒绝服务而不是泄密**：X3DH 把它掺进共享密钥，发方算出的秘密
合法收方推不出来，握手失败；攻击者同样推不出——身份密钥与签名预密钥都在包自己的签名覆盖内，
他换不掉。写明这一点是为了不让人以为「验过包就安全了」。

那条到期出口同样不可省略：没有它，"已确认"就是一个对某把用户公钥无限期开放的接受
窗口，而这是暴露面。它对应一个显式的超时动作，其效果是降级为无关系并如实告诉用户
这次应答没有得到回应——一个永远使能却什么也不做的超时动作，等于没有建模。

本地拉黑以独立记录保存拉黑前的关系状态，并与关系的 Blocked 状态同事务提交；重复拉黑不覆盖原状态。解除只恢复仍存在且仍处于拉黑状态的关系，不重新建立已删除的关系。应答验证读取持久拉黑名单，确认旧待确认项时再次检查；普通关系写入不能覆盖有效拉黑记录。当前实现的是本地决策保护，跨设备拉黑与解除的合并规则仍由通讯录同步任务承接（{need}`TASK_20260919_FMT2MTRTWPK5HMG5`，{need}`TASK_20260919_5V9YG7MWWE8TYWAW`）。

解除已建立联系人的拉黑时，同事务登记按用户/设备去重的连接恢复请求；对端离线或本机重启不丢失请求。后台每次最多取 32 台设备，每台至少间隔 30 秒，先保存下一次尝试时间再尝试；连接唤醒最多并发 32 项、每项至多十秒，不发送应用字节。每次尝试前重查联系人、拉黑和吊销状态，失效即取消；再次拉黑同事务清除请求并撤销在途连接许可。只有真实连接成功的可达事件才能触发原有可靠出站重放，不周期性重放消息或重置补发预算。确认可达后清除请求；时钟向后跳过一个间隔时重新锚定一次。连接尝试的时间与并发上限不替代陌生对端的全局准入预算（{need}`TASK_20260919_FMT2MTRTWPK5HMG5`）。

两侧都可以从任意状态进入已删除。删除时若处于已拉黑，留下一条仅含对方用户公钥的
拉黑记录，使其此后的应答继续被丢弃，直到用户显式移除该记录。

状态迁移全部由纯转移函数承担，密码学操作作为效果外置，因此可以对整条交换做模型检验
与随机序列测试。

## 接口与数据契约

### 验证顺序

收到一份应答时按固定顺序检查，任一步失败即整条丢弃且不产生任何 YoChat 应用层出站数据：

1. 用明文头里的邀请标识定位本机的邀请记录；不存在、已作废或已过期即丢弃
2. 用该邀请的一次性私钥解开密文；失败即丢弃
3. 声明的应答方用户公钥是否命中拉黑记录；命中即丢弃
4. 密文内的邀请摘要是否等于本机那份邀请的规范编码摘要
5. 用声明的用户公钥验签，且签名覆盖摘要与应答方声明的全部内容
6. 应答声明的渠道标签（归一化后）是否等于所应答邀请的渠道标签；不等按不符处理
7. 若是定向邀请：应答方声明的渠道账号是否等于邀请中指定的被邀请方账号
8. 按（邀请标识，应答方用户公钥）去重：同一对只保留一条待确认项，重复粘贴直接丢弃并
   计数。**注意去重键是这一对，不是邀请本身**——同一份不定向邀请被多个人分别应答是产品
   明确支持的场景，按邀请去重会把它废掉。对**已经建立关系的那个用户**经另一份邀请再次
   应答，作为一条新的待确认项呈现并标明"该联系人经另一份邀请重新应答"，由用户决定是否
   合并；联系人记录的字段刷新仍只走关系建立后的签名声明通道，不由应答改写

拉黑检查放在解密之后、验签之前，而不是最前面——应答方用户公钥在密文里，不解密看不到。
放在验签之前是为了省下一次验签与一次摘要比对；此时那个公钥尚未经验证，但据一个未经
验证的声明**提前丢弃**是安全的：伪造声明只会让伪造者自己被丢掉，不会放行任何东西。
丢弃的原因对用户可见。

对外的表述只能到这里为止（{need}`TASK_20260919_5AB9BSEC7J2FBZP2`）：**不产生任何 YoChat 应用层出站数据**，因此在应用层不可区分；**处理时长上的
残余差异未被消除，不作不可区分性承诺**。上面那句"省下一次验签"本身就是把两条路径区分
开的那点开销——在应答由人从渠道粘贴的路径上，攻击者拿不到稳定的观测位置，但这是路径带
来的，不是这套顺序给的保证。要真做到不可区分，得把检查移到最后或把全部丢弃路径填充到
固定时长，两条都有代价；本设计选择如实写明残余差异而不假装它不存在。

第 6、7 步不匹配时都不静默丢弃，而是照常进入待确认并在界面上醒目告警、不自动接受：填错
渠道或账号的可能是一个合法的应答方，这个判断应当由人来做。

第 8 步不可省：没有它，同一份合法应答被反复粘贴就会在待确认列表里堆出多条，用户分不出
哪条是真的；而"重新应答会刷新联系人记录"这条规则若照字面实现，一份**旧**应答还能把联系人
的设备公钥与渠道账号回滚到旧值。去重集合随邀请记录保存，邀请过期或作废时一并清理。

无论哪一步失败，都不产生任何 YoChat 应用层出站数据，因此拉黑与其他失败**在应用层不可区分**；处理时长
上的残余差异未被消除，不作不可区分性承诺（见上一段）。

### 持有证明

设备的授权集中在一份由用户私钥签名的设备列表上；设备加入列表时向签发设备证明持有
其私钥，那是唯一要求持有证明的时刻，那时两者都在场。该列表不进入邀请与应答，而是在
关系建立之后经已建立的通道交换。

由此有一个必须写明的例外（{need}`TASK_20260919_5AB9BSEC7J2FBZP2`），否则"不得接受任何未被设备列表覆盖的设备公钥"与邀请、应答
各自携带的那一台设备公钥自相矛盾：**邀请与应答中由本方用户私钥直接签名的那一台设备
公钥，等价于一份仅含该设备的设备列表，其有效期仅限关系建立期间**——在收到对方完整的
签名设备列表之前，双方的设备组成员只能是交换期间这两台。

配一条收敛规则：首次收到对端的签名设备列表时，若其中**不含**交换期间使用的那台设备
公钥，该设备立即移出设备组并向用户告警。没有这条，一台从未被对方用户签入列表的设备
可以长期留在组里收全部消息，而界面看不到对端的这种异常。那台设备的持有证明由 P2P 握手
中对设备私钥的使用承担，这一点也要写出来，不能默认。

需要保证的是"这台设备属于这个用户"，而这件事只由用户签名提供——设备自己的签名
只证明某人持有那把设备私钥，完全不说明它属于谁。邀请与应答由用户私钥直接签名，
正是同一条道理走到底。

代价写明：一台被入侵**且仍持有用户私钥**的设备可以以该用户名义发出邀请与应答。这
不是签名方案能解决的问题——持有用户私钥就等于持有这个身份，它属于恢复短语泄漏那一
类威胁。不持有用户私钥的设备，即使尚未被吊销，也发不出邀请与应答。

### 对外表现

对未匹配的应答、来自未建立关系的对端、以及已被拉黑的对端，一律不产生任何 YoChat 应用层出站数据（{need}`TASK_20260919_5AB9BSEC7J2FBZP2`），包括拒绝、送达确认和错误回执。

2026-11-01 用户决定采用应用层静默并告知传输差异。iroh/QUIC 握手、ACK、关闭等传输包仍可能存在；连接结果和时序也可能因路径不同而不同，不能承诺对方只看得出是否在线，或不能据此探测关系状态。产品须明确展示这一边界，抓包验收须结合应用层发送记录区分传输包，不能将出现 ACK 判作应用层响应，也不能仅凭没有正文就认定没有应用层回执。规范依据为 {need}`REQ_20260918_MXHYRG96W0VKB031`。

## 失败处理

交换过程中的全部失败对外一律表现为"没有响应"（{need}`TASK_20260920_F5MDP1BS4S20XGC4`），对内则区分并向用户说明：邀请已过期、
邀请已作废、应答无法解开、签名不符、对方在拉黑名单中。这五种对用户是不同的信息，
对网络上的对端是同一种沉默。

用户拒绝一份应答时同样不产生任何 YoChat 应用层出站数据。需要向对方解释时，双方本来就共享着那条
用来传递邀请的渠道。

一次性私钥不会缺失：邀请只带签发它的那台设备，私钥就在那台设备上。应答经渠道回传，
因此不存在"投递不到"这回事；在**其他设备**上粘贴应答不是错误，界面如实说明解开它需要
签发该邀请的那台设备，并指出是哪一台。

| 以上各行 | 由 {need}`TASK_20260919_CMQ5HX5V77QHC7KH` 在含任意超时序列的执行上检验 | — |

这张表是本篇对"每一处等待都要有超时动作"的落实，架构篇的全局性质按各篇的这类清单
取并集，而不是自己另列一份枚举。

检验的性质写明其前提（{need}`TASK_20260919_CMQ5HX5V77QHC7KH`）：**在双方完成带外安全码比对并各自标记为已校验之后**，其持有
的对端用户公钥必定互为真身。之所以要带上这个前提，是因为状态机本身允许双方不作
比对就建立关系——那时中间人攻击是一条合法执行，把它当反例只会掩盖真实的前提条件。
与之配套另检验一条：未经比对的关系在任何执行中都不得被呈现为已认证。

超时相关的安全性质（在包含任意超时序列的执行上都必须成立；{need}`TASK_20260919_CMQ5HX5V77QHC7KH`）：一份邀请在过期或作废之后，
任何执行中都不再有新的关系据此建立；应答方的"已确认"态与发起方的"待确认"态在任何执行
中都不会无限期停留——各自要么转为已建立，要么因超时回到无关系，两者都对用户可解释；
应答方在已确认态不向对方发送任何消息；**任何一侧进入已建立之后，两侧要么都到达已建立，
要么至少有一侧在有限步内向用户显示这次交换未完成**——不写"不存在一侧已建立而另一侧无
关系"这条不变量，因为投递不可靠时它做不到（见上文两将军那段），写一条做不到的性质只会
让模型检验要么失败、要么迫使建模者偷偷加一条投递保证。

做得到的那一条是它的细化，**一并检验**（{need}`TASK_20260919_CMQ5HX5V77QHC7KH`）：**任何执行中，一侧已建立而对方处于无关系态时，
对方必定持有该次交换的那条短期记录**。这条性质与"降级时保留短期记录"那条机制互为存在
理由——`models/exchange.qnt` 对保留与不保留两种取法各实例化一份检验它：保留时 12 步内
无反例；不保留时找到反例——B 应答后超时降级且不留记录，A 随后确认并进入已建立，其设备组
加入操作已经在渠道里，B 按陌生来源丢弃，两侧从此不一致且都无法解释。因此"无关系"这个
状态**不足以作为关系一致性性质的载体**，必须拆出"是否持有该次交换记录"这一维；把它们
混为一谈，这条性质就既写不出来也检验不了。

活性性质及其前提：**在双方设备最终稳定连通（◇□connected）、且发起方在有效期内作出
确认或拒绝的前提下**，两侧**一致地**建立关系，或两侧一致地回到无关系。前提写成
`◇□connected` 而不是 `□◇connected`：后者只保证无限次可连通，每次连通期都短于一次投递
的执行同样满足它，性质会被证伪；而"最终稳定连通"同样包含"离线七天后上线并保持在线"
这类要保障的场景，不是要避免的 `□connected`。它的安全对偶不依赖该
前提：前提不成立时，两侧各自停在一个有原因、可向用户解释的状态上，不产生错误的
"已认证"结论，也不丢弃任何已经落盘的记录。

proptest 覆盖邀请与应答的编解码往返、验证顺序在任意字段被破坏时的行为、以及关系
状态机在任意动作序列下不进入未定义状态。

Kani 覆盖令牌解析：长度、设备公钥个数、有效期字段的边界，确保畸形输入不会导致
越界或超量分配。
