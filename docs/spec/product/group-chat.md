# 群聊

<!-- tao:section scope -->
## 目标与边界

本篇界定 YoChat (有聊) 中多人聊天会话的隐私承诺与成员管理规则。

交付边界：群聊不在首个交付增量内，属于后续阶段。本篇刻意只固定那些无论实现方案
如何都必须成立的产品承诺；成员变更的并发语义、群规模上限与加群流程等，在该阶段
开始前按当时可得的能力澄清后再补充。群加密方案的可行边界要以实际可用的密码学库
为准，现在把细节写满，只会写出一份实现不了、最后要逐条划掉的需求。

范围内：群消息的加密边界；成员加入与移除对可读范围的影响；角色与权限；退出；群内
拉黑；群消息缺失的可检测性；成员集合的最终一致性。

范围外：一对一聊天会话见 [聊天会话与消息](messaging.md)；关系的建立见
[好友与通讯录](contacts.md)。

## 需求

```{req} 群消息只有当前成员能解密
:id: REQ_20260918_78D42FH8SES6P5CE
:status: proposed

系统应对群消息端到端加密，使只有该群当前成员的、未被吊销的设备能够解密。

<!-- tao:field acceptance -->
**验收：** 非成员即使取得全部传输数据也无法解出任何群消息内容。

<!-- tao:field source -->
**来源：** 群聊是用户明确要求的能力，其隐私承诺应与一对一聊天会话一致。
```

```{req} 新成员读不到加入之前的消息
:id: REQ_20260918_V4CX98RRRNSPKJ12
:status: proposed

系统应使新加入的成员无法解密其加入之前发送的群消息。

<!-- tao:field acceptance -->
**验收：** 成员加入后，加入之前的群消息在其设备上不可读；其他成员不受影响。

<!-- tao:field source -->
**来源：** 群成员构成会变化，加入一个群不应当等于取得此前全部对话的阅读权。
```

```{req} 被移除成员读不到之后的消息
:id: REQ_20260918_VKJNMX125CHGGDCY
:status: proposed

系统应使被移除的成员无法解密其被移除之后发送的群消息。

<!-- tao:field acceptance -->
**验收：** 成员被移除后，其余成员继续发送的消息在该成员设备上不可读。

<!-- tao:field source -->
**来源：** 移除成员如果不能真正切断访问，这个动作就只是界面上的装饰。
```

```{req} 群角色与权限
:id: REQ_20260918_EWJ8QV12FWCSDN8S
:status: proposed

群应具备所有者、管理员与成员三种角色。管理员可以增加与移除成员；只有所有者
可以任免管理员与解散群；所有者不能被其他人移除。

<!-- tao:field acceptance -->
**验收：** 逐项验证每种角色可以执行与不能执行的操作；越权操作被拒绝，且被拒绝的结果对
发起者可见。

<!-- tao:field source -->
**来源：** 用户要的是朋友圈子内的群，需要有人负责秩序，但不应当出现任何人都能解散群的情形。
```

```{req} 成员可以自行退出
:id: REQ_20260918_MGYFJHW22Y328MPW
:status: proposed

群成员应能自行退出群，退出后无法解密其退出之后的群消息。

<!-- tao:field acceptance -->
**验收：** 成员退出后，其余成员继续发送的消息在该成员设备上不可读；其余成员看到退出事件。

<!-- tao:field source -->
**来源：** 退出不应当需要请求别人同意，否则用户会被困在一个他不想待的群里。
```

```{req} 群内可拉黑成员，范围由用户选择
:id: REQ_20260918_SKDZ5T7T2DM4MW4V
:status: proposed

用户应能拉黑群内的某个成员，并选择该拉黑是全局生效还是仅限于这个群。拉黑状态
维护在拉黑方本地；被拉黑者的群消息仍会到达本机，但不得落盘、不得呈现，且不得
向其产生任何表示拉黑的响应。

<!-- tao:field acceptance -->
**验收：** 拉黑某成员后，其群消息不出现在界面上，本地存储不因其发送而增长；选择仅限本群时
该成员在其他共同群中的消息不受影响；被拉黑者收不到任何表示拉黑的数据。

<!-- tao:field source -->
**来源：** 群消息是发给全群的，本方无法让某一个成员不再向群里发布，除非退群。所以群内拉黑
只能做到"到了但不留下"，这与一对一拉黑的"不接收"有实质差别，必须写明而不能
含糊成同一件事。差别的代价是被拉黑者仍能消耗本机的带宽与解密开销，这由速率
上限承担。范围可选是因为两种意图都真实存在：有人只是在这个群里话太多，有人是
真的不想再有任何往来。
```

```{req} 群消息的缺失同样必须可被检测
:id: REQ_20260918_NEQR8SPMDZYM04FY
:status: proposed

系统应使群成员能够识别出自己缺失了群里的某些消息，而不是把缺失表现为没有人
说话；具体机制在该阶段开始时确定。

<!-- tao:field acceptance -->
**验收：** 人为丢弃投递给某个成员的若干条群消息，该成员能够察觉缺失并最终取得它们，或者
得到一个关于这段缺失的明确说明。

<!-- tao:field source -->
**来源：** 群里的误解成本比一对一高得多：如果不同成员看到的消息不一样，而谁都不知道自己
少看了东西，对话会建立在各人不同的前提上，最后变成人与人之间的不信任而不是
一个技术故障。这条承诺必须先定下来，机制怎么做可以晚一点。
```

```{req} 成员变更最终收敛
:id: REQ_20260918_8WAFG4K1R6TECM4T
:status: proposed

在没有中心协调者的前提下，系统应使全部成员对群成员集合的认知最终收敛到一致的
结果，即使成员变更是并发发生的。

<!-- tao:field acceptance -->
**验收：** 以性质测试验证：对任意并发的成员增删序列与任意投递顺序，在通道静止之后，全部
成员对成员集合的认知一致。

<!-- tao:field source -->
**来源：** 没有中心服务来给成员变更排序。若不同成员对当前成员集合的认知不一致，加密的目标
集合也就不一致，会直接导致部分成员读不到消息，或者不该读的人读到消息。
```

<!-- tao:section cases -->
## 用例与性质

```{uc} 被移除成员读不到之后的消息
:id: UC_20260918_49YPAZ7HXXTHPA7S
:status: proposed
:verifies: REQ_20260918_VKJNMX125CHGGDCY

<!-- tao:field given -->
**给定：** 一个有若干成员的群，其中成员 M 处于正常状态。

<!-- tao:field when -->
**当：** 管理员移除 M，随后其余成员继续在群中发言。

<!-- tao:field then -->
**则：** M 无法解出移除之后的任何群消息；其余成员之间的收发不受影响。
```

```{uc} 并发成员变更最终一致
:id: UC_20260918_F4F9TTFEH9PX60RZ
:status: proposed
:verifies: REQ_20260918_8WAFG4K1R6TECM4T

<!-- tao:field given -->
**给定：** 一个群的若干管理员同时在离线或分区状态下执行成员增删；投递通道允许任意顺序与延迟。

<!-- tao:field when -->
**当：** 各方恢复连通并同步直到通道静止。

<!-- tao:field then -->
**则：** 全部成员对当前成员集合的认知一致；不存在某个成员被一部分人认为在群内而被另一部分人认为已被移除的持久状态。
```

<!-- tao:section questions -->
## 待确认事项

- 群规模上限。它直接决定成员变更与密钥更新的代价是否可接受，须在该阶段开始前给出
  一个有依据的数值。
- 长期离线的成员如何追上期间发生的成员变更与密钥更新，以及追不上时的表现。
- 加群的流程：谁可以邀请、是否需要批准、被拒绝的一方看到什么。
- 群内解除拉黑之后，能否像一对一那样补齐拉黑期间的消息。群消息到达时没有落盘，
  要补齐就得向其他成员重取，而他们未必还持有、也未必愿意提供。能不能做到在实现
  群聊时才有答案，因此本篇没有把它写成需求。
- 群消息缺失的检测机制，以及缺失无法补齐时如何呈现。
- 群的元数据（名称、头像、公告）由谁修改、如何在没有协调者的情况下收敛。
- 角色变更的并发语义：成员集合收敛不等于管理员/所有者权限收敛。并发任免、移除及解散
  如何共同判定，须与越权拒绝一起设计，不从设备组成员收敛直接推导。
- 一对一聊天会话里那套"解密失败就自动重建通道并重传"的恢复办法，在群里未必成立：
  重建可能涉及多个成员，而重传的内容取决于谁还持有原文。群的恢复策略须在该阶段
  单独设计，不能假定它是一对一方案的推广。
