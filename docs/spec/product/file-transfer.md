# 文件发送与共享

<!-- tao:section scope -->
## 目标与边界

本篇界定 YoChat (有聊) 中两件相关但不同的事：把一个文件发送到聊天会话，以及把一个
文件或目录共享给指定的联系人由他们自己来取。两者默认都不复制文件——系统记录的是
本地位置与内容指纹，而不是另存一份。

区别在于：发送是一次投递，会出现在聊天会话里，并带有默认七天的有效期；共享不进入
任何聊天会话，默认不过期，联系人可以直接浏览对方共享给自己的目录树。用户可以在
发送时显式选择发送一份独立副本，用磁盘占用换取内容不再随源文件变化的保证。

交付边界：两者都不在首个交付增量内，属于后续阶段。本篇固定必须成立的产品承诺与
安全边界；下载策略、配额与保留期等在该阶段开始前确定。

发送与共享都属于持有文件的那台设备，因此浏览一个用户的共享时，最顶层是按设备
组织的。

范围内：文件发送与有效期；可选的独立副本；源文件变化时的呈现；共享与可见范围
（可按联系人分组）；按设备组织的共享目录树与浏览；路径与符号链接的暴露边界；撤销；
分块完整性校验；多源并发下载与转发的逐次授权；进行中传输的可见性；下载与浏览的
持久记录；速率与并发上限。

范围外：消息本身见 [聊天会话与消息](messaging.md)；网络暴露面见
[隐私与防护](privacy-and-safety.md)。

## 需求

```{req} 发送文件到聊天会话
:id: REQ_20260918_V18R6CZZ5M2NN0HY
:status: proposed

用户应能把本机的一个文件发送到聊天会话。系统默认不复制该文件，而是把它标记为
在一段有效期内可被该聊天会话的参与方下载；有效期默认为七天，用户可以调整。

<!-- tao:field acceptance -->
**验收：** 发送后对方可以下载并得到与源文件逐字节一致的副本；双方都能看到剩余有效时间，
发送方可以延长它；超过有效期后新的下载请求得到已过期状态；发送动作本身不产生
额外的本地文件副本。

<!-- tao:field source -->
**来源：** 用户要的是把这个文件给对方，而不是再存一份。被发送的文件在本机已经有了，再复制
一份只是浪费磁盘。有效期则让发送出去的东西不会无限期地占着发送方的共享位置。

这与"消息默认永久保存、不设保留期"并不矛盾，因为过期的对象不同：消息的本地
副本是它唯一的存在，过期等于销毁用户的记录；而这里过期的是"继续向对方提供这个
文件"的授权，用户自己的文件一个字节都没动。即便如此，到期仍然会让对方取不到，
所以双方都应看到剩余时间，发送方应能延长它。
```

```{req} 可选择发送独立副本
:id: REQ_20260918_CEMPWSR9M6FEV0NM
:status: proposed

用户应能在发送文件时选择发送一份独立副本；此时系统把该文件复制到自己的存储，
之后源文件的修改、移动或删除都不影响对方能取得的内容。

<!-- tao:field acceptance -->
**验收：** 选择发送副本后修改源文件，对方下载到的仍是发送时刻的内容；界面在提供该选项时
说明它会占用额外的本地空间。

<!-- tao:field source -->
**来源：** 默认不复制的代价是源文件一变，对方就取不到原来的东西了。对确实重要的一次发送，
用户需要一个能兑现"我发出去的就是这个"的选项，而是否值得这份磁盘占用，应当由
用户当场决定而不是由系统一律替他决定。
```

```{req} 源文件变化时如实呈现
:id: REQ_20260918_P5MF7948P6D5ZFDD
:status: proposed

如果一次尚在有效期内的发送或一项共享，其源文件已被修改、移动或删除，则系统应
把它标记为不可用并说明原因，不得提供与发送时刻内容不一致的数据。

<!-- tao:field acceptance -->
**验收：** 发送后修改源文件，接收方看到明确的不可用状态并说明原因；下载过程中检出内容与
指纹不符时中止并报告，不产生部分写入的结果文件。

<!-- tao:field source -->
**来源：** 不复制文件就必须承担源文件会变这件事。悄悄给出变化后的内容比给不出更糟——接收方
无从知道自己拿到的并不是对方发出的那个。
```

```{req} 共享文件或目录
:id: REQ_20260918_07ZTRZZEFSTR2AV6
:status: proposed

用户应能把本机的一个文件或目录共享给指定范围的联系人。共享默认不过期，用户可以
设置有效期；共享不主动发送到任何聊天会话，也不复制源文件。

<!-- tao:field acceptance -->
**验收：** 设置共享后，处于可见范围内的联系人能看到它，范围外的联系人看不到；共享不在任何
聊天会话中产生消息；设置共享本身不产生额外的本地文件副本。

<!-- tao:field source -->
**来源：** 发送文件与共享文件是两件事。前者是一次投递，后者是长期把一部分东西放在那里让
特定的人自己来取，不需要每次都在聊天里说一遍。
```

```{req} 发送与共享都属于提供它的那台设备
:id: REQ_20260918_EZN5NZFG4287AF2T
:status: proposed

一次发送或一项共享应属于持有该文件的那台设备，只在该设备可达时能被取用。浏览
某个用户的共享时，最顶层应按设备组织，每台设备以其设备别名标示，共享的相对
路径位于设备之下。

<!-- tao:field acceptance -->
**验收：** 同一个用户的两台设备各自共享内容时，浏览其共享看到两个以设备别名标示的顶层
条目；某台设备离线时其下的条目标为暂不可用，另一台设备下的条目不受影响。

<!-- tao:field source -->
**来源：** 文件在磁盘上，磁盘属于某一台机器。系统默认不复制文件，所以"这份内容在哪里"
天然就是"在哪台设备上"，把它藏起来只会让用户看到一个取不到的条目却不知道为什么。
顶层显示设备别名，用户一眼就能看出该去开哪台机器。
```

```{req} 浏览对方共享的目录树
:id: REQ_20260918_ZMQ37JWBGTS1557S
:status: proposed

联系人应能直接浏览对方共享给自己的文件与目录结构并按需下载，不需要经过聊天会话。

<!-- tao:field acceptance -->
**验收：** 在联系人详情中可以打开其共享，先按设备、再按目录层级浏览并下载；只列出共享给
本人的条目，范围外的条目既不出现也无法通过其内容标识取得。

<!-- tao:field source -->
**来源：** 长期共享的用处正在于随时能去拿。若每次都要靠对方在聊天里再发一遍，它就退化成
了发送文件。
```

```{req} 共享的可见范围逐项决定，可按联系人分组
:id: REQ_20260918_SQ2PCMRK0KXMYHDB
:status: proposed

用户应能为每一项共享单独设定可见范围，至少支持"全部联系人"、指定的联系人分组
与指定的单个联系人；范围可以混合使用。

<!-- tao:field acceptance -->
**验收：** 设为某个分组后，该分组内的联系人能看到并下载该条目，范围外的联系人既看不到也
无法下载它，即使他们知道其内容标识；此后往该分组中增删联系人，其可见范围随之
变化而不需要重新设定该共享。

<!-- tao:field source -->
**来源：** 不能逐项设范围，用户就只敢共享那些给谁看都无所谓的东西，这个功能也就没什么用了。
而在联系人多起来之后逐个勾选同样不可用，所以范围必须能以分组为单位表达——这也
正是联系人分组存在的主要用处之一。
```

```{req} 只暴露显示名与相对路径
:id: REQ_20260918_X6GEB41KB2VVNW2Z
:status: proposed

发送与共享应只暴露显示名以及共享根以下的相对路径；本机的绝对路径不得离开设备。

<!-- tao:field acceptance -->
**验收：** 检查发送出去的全部数据，不含共享根以上的任何路径成分与本机用户名。

<!-- tao:field source -->
**来源：** 绝对路径会泄漏用户名、目录结构乃至其他项目的名称，而这些与被分享的内容毫无关系。
```

```{req} 符号链接不得越出共享根
:id: REQ_20260918_ERJ5K0EGCWBKVRFY
:status: proposed

共享内的符号链接不得解析到共享根之外；指向外部的链接应被拒绝而不是跟随。

<!-- tao:field acceptance -->
**验收：** 在共享目录内放置指向外部文件的符号链接，接收方无法通过它取得该文件，且共享方
得到明确的提示。

<!-- tao:field source -->
**来源：** 跟随符号链接会让一次目录共享变成对整个文件系统的暴露，而用户在设置共享时完全
看不出这一点。
```

```{req} 撤销发送与共享
:id: REQ_20260918_E2E85RRHP5Q0YK7Z
:status: proposed

用户应能随时撤销一次发送或一项共享；撤销后新的下载请求得到不可用状态。系统应
说明撤销不能收回接收方已经取得的字节。

<!-- tao:field acceptance -->
**验收：** 撤销后新的下载请求得到不可用状态；撤销界面包含关于已取得字节无法收回的说明。

<!-- tao:field source -->
**来源：** 用户会把撤销理解为删除。说清楚它只是停止继续提供，才能让用户在分享敏感内容
之前做出正确判断。
```

```{req} 内容完整性可按分块校验
:id: REQ_20260918_7ASSB68RBP1REDMT
:status: proposed

接收方应能按内容分块校验所取得数据的完整性；校验不通过的部分应被拒绝而不是
写入结果文件。

<!-- tao:field acceptance -->
**验收：** 在传输中篡改若干字节后，接收方拒绝对应分块并报告校验失败，不产生部分写入的
结果文件；从多个来源取得的分块逐块校验通过后拼装出的文件与源文件逐字节一致。

<!-- tao:field source -->
**来源：** 用户要求不得因实现缺陷导致数据损坏。内容可能从多个来源分块取得，逐块校验是
唯一能在这种条件下成立的保证，也是多源下载能够成立的前提。
```

```{req} 多源并发下载默认开启，转发由被请求方逐次决定
:id: REQ_20260918_WF02KZAEBDF6Z7XP
:status: proposed

系统应默认从多个已持有同一内容的设备并发下载以提高分发速度。当本机作为非源头
设备被请求提供内容时，系统应展示请求方的用户与设备信息并征求用户同意；用户可
选择同意一次或永远同意，并可随时更改此前对某个请求方或某项内容的决定。作为
内容源头的设备按其共享可见范围提供，不额外征求同意。

<!-- tao:field acceptance -->
**验收：** 在多个接收方已持有部分内容的情况下，新接收方的下载速度高于只从源设备下载；本机
作为非源头被请求时出现含请求方用户与设备信息的征求界面，选择永远同意后同一请求
方不再被反复询问，更改该决定后立即生效；源头设备提供自己的共享时不出现该界面。

<!-- tao:field source -->
**来源：** 把同一个文件发给一群人时，只从源设备取会让源设备成为瓶颈，所以默认开启。但它
的代价是接收方之间会得知彼此持有某份内容——而这份内容是别人分享的，本机只是
碰巧也有一份，替别人转发并不在最初那次分享的授权范围内。所以决定权交给被请求
的人，并且给出足够的信息让他判断；"永远同意"让常见情况只问一次，可更改让一次
草率的决定不会永久生效。
```

```{req} 进行中的传输对提供方可见
:id: REQ_20260918_MDFC477C3YZ025YP
:status: proposed

当本机正在为他人提供内容时，系统应展示每个进行中的传输的请求方用户标识、设备
标识、网络地址、当前速率、已传输字节数，以及正在被读取的文件在共享内的路径。

<!-- tao:field acceptance -->
**验收：** 在有他人正在下载时，上述每一项都出现在界面上并随传输进展更新；同时存在多个
传输时分别列出；传输结束后从进行中的列表移除。

<!-- tao:field source -->
**来源：** 用户把文件放出去之后，唯一能判断这件事是否还在自己预期之内的办法，就是看见
此刻谁在拿什么。没有这个视图，用户既不知道自己的上行带宽为什么被占满，也无法
发现某个联系人正在把整棵共享树拖走。
```

```{req} 下载与浏览须持久记录并可查阅
:id: REQ_20260918_W3D5CMFZVPY859BV
:status: proposed

系统应持久记录每一次下载与每一次共享浏览，并能按内容、按联系人、按时间段汇总
出：下载次数与去重后的人数、下载成功次数与成功人数、浏览次数与去重后的人数，
以及每条记录的时间戳。这些记录应在用户删除它们之前一直保留。

<!-- tao:field acceptance -->
**验收：** 经过若干次成功与失败的下载与若干次浏览之后，上述各项汇总数字与实际发生的次数
一致；记录可按内容、联系人与时间段查阅；用户可以删除这些记录。

<!-- tao:field source -->
**来源：** 分享出去的东西被谁取走过、取了几次、有没有取成功，是用户判断要不要继续分享、
要不要撤销的唯一依据，而这件事只有发生的当时才知道，事后无法重建。区分次数与
人数是因为两者回答的问题不同：一个人反复重试和十个人各取一次，对用户意味着
完全不同的情况。
```

```{req} 下载与浏览请求受速率与并发上限约束
:id: REQ_20260918_DCB0NBAAA0AD554V
:status: proposed

系统应对下载与共享浏览的请求速率、并发传输数以及单个请求方可占用的上行带宽与
内存分别设定上限；超出上限的请求应被拒绝或排队，且不得导致本机不可用或使聊天
的收发受到影响。

<!-- tao:field acceptance -->
**验收：** 由多个联系人以远超正常水平的速率持续发起下载与浏览请求，本机保持可用，聊天
消息的收发不受影响，被拒绝或排队的请求数量在诊断信息中可见。

<!-- tao:field source -->
**来源：** 文件传输是本机对外提供的、成本最高的服务，任何一个已授权的联系人都能把它压满，
而这未必出于恶意——一次拖走整棵目录树就够了。上限要覆盖到浏览请求，因为列目录
本身也要读磁盘，比传字节更容易被忽略。
```

## 用例与性质

```{uc} 中断续传后内容与源一致
:id: UC_20260918_PQPPY8WVNP0FZVWD
:status: proposed
:verifies: REQ_20260918_V18R6CZZ5M2NN0HY, REQ_20260918_7ASSB68RBP1REDMT, REQ_20260918_WF02KZAEBDF6Z7XP

<!-- tao:field given -->
**给定：** 发送方持有一个大文件并已发送到聊天会话；传输通道允许在任意时刻中断，双方可在任意时刻重启；内容可以来自任意多个已持有它的设备。

<!-- tao:field when -->
**当：** 接收方开始下载，期间发生任意次中断与重启，直到下载报告完成。

<!-- tao:field then -->
**则：** 接收方得到的文件与源文件逐字节一致；不存在部分写入却被当作完成的结果。
```

```{uc} 指向共享外部的符号链接被拒绝
:id: UC_20260918_9SWG1HZ8CH1Q4TJJ
:status: proposed
:verifies: REQ_20260918_ERJ5K0EGCWBKVRFY, REQ_20260918_X6GEB41KB2VVNW2Z

<!-- tao:field given -->
**给定：** 共享根目录内存在一个指向共享根之外文件的符号链接。

<!-- tao:field when -->
**当：** 接收方尝试通过该链接取得目标文件。

<!-- tao:field then -->
**则：** 请求被拒绝，接收方未取得该文件的任何内容；发送出去的数据中不含共享根以上的路径成分。
```

```{uc} 源文件变化后不提供不一致的内容
:id: UC_20260918_91KW8482TQMKHB3D
:status: proposed
:verifies: REQ_20260918_P5MF7948P6D5ZFDD, REQ_20260918_CEMPWSR9M6FEV0NM

<!-- tao:field given -->
**给定：** 用户发送了一个文件且未选择发送副本，接收方尚未开始下载。

<!-- tao:field when -->
**当：** 用户修改了该源文件，随后接收方发起下载。

<!-- tao:field then -->
**则：** 接收方得到明确的不可用状态并说明原因，不会取得修改后的内容；若用户当初选择了发送副本，则接收方仍能取得发送时刻的内容。
```

## 待确认事项

- 接收方是否自动下载、自动下载的体积上限与存储位置，涉及移动端流量与磁盘占用，
  在该阶段结合平台情况确定。
- 发送与共享在本机保留的元数据配额，以及同时挂着大量共享时的性能表现。
- 源文件变化的检测时机：是在每次下载请求时按指纹校验，还是持续监视文件系统。前者
  简单可靠但只能在被取用时才发现，后者能更早提示用户，但在应用未运行期间同样无效。
  是否值得为此把已发送而尚未被取走的内容复制到本地缓存，是一个明确的取舍，在设计
  阶段决定。
- 目录共享后源端新增文件是否自动出现在共享中，还是需要一个显式动作。
- 转发授权的粒度：按请求方记住决定，还是按（请求方，内容）两者记住。前者简单，
  后者更贴合"这份可以帮转、那份不行"的真实意图。
- 多源候选发现是否在转发同意之前暴露“本机持有该内容”。这是与“是否发送字节”不同的
  隐私边界；后续设计需同时确定候选查询及授权顺序，不能只验证用户拒绝后的传输停止。
- 下载与浏览记录的保留规模与是否需要上限。它随使用持续增长，而本篇承诺在用户删除
  之前一直保留，需要确认这个增长在长期使用下是可接受的。
