# 好友与通讯录

<!-- tao:section scope -->
## 目标与边界

本篇界定 YoChat (有聊) 中，用户如何与另一个人建立关系、如何确认对面确实是本人、
如何中止关系，以及这些状态在自己多台设备之间的一致性。

范围内：邀请与应答的两轮交换；借助双方已有渠道完成身份对应；安全码比对；拉黑与
解除；删除联系人及其对历史与拉黑记录的处理；通讯录的跨设备同步、好友备注与检索。

范围外：用户与设备本身见 [用户与设备](users-and-devices.md)；消息的传递与顺序见
[聊天会话与消息](messaging.md)；群成员管理见 [群聊](group-chat.md)。

交付边界：本篇全部需求属于首个交付增量。

<!-- tao:section terms -->
## 术语

本篇使用的联系人、邀请、邀请应答、渠道绑定、安全码、用户公钥、用户别名、好友备注
等术语，定义见[项目术语](../glossary.md)。

<!-- tao:section requirements -->
## 需求

```{req} 关系需要双方各自确认
:id: REQ_20260918_1VXJQ68HXHM0JR0Q
:status: proposed

系统应仅在双方各自在自己的设备上作出确认之后建立联系人关系；任何一方单独的
动作不得使对方出现在自己的通讯录中并可以收发消息。

<!-- tao:field acceptance -->
**验收：** 发起方生成邀请而对方尚未应答时，通讯录中不出现该联系人；对方应答后，发起方
在**签发该邀请的那台设备**上看到一条待确认的应答（解开它需要只存在于该设备的一次性
私钥），确认之后双方才可收发。

<!-- tao:field source -->
**来源：** 没有中心服务，也就没有平台替用户拦截骚扰与垃圾请求。关系是否成立必须由双方
各自把关，这是这个模型下唯一的过滤手段。
```

```{req} 邀请由用户私钥签名并绑定发起方的渠道账号
:id: REQ_20260918_2276A5JCK1KGNS1A
:status: proposed

当用户生成邀请时，系统应产生一份携带以下内容的文本：协议版本与用途标签、发起方
用户公钥、发起方所依据的渠道标签与其在该渠道上的权威账号、一个专为该邀请生成的
一次性公钥（它同时就是这份邀请的标识）、一个设备公钥（即签发这份邀请的那台设备，
用于关系建立之后接收对方的第一条操作与后续消息，**不用于接收应答**）、有效期，以及
可选的一段备注。整份内容由**用户私钥**签名；不持有
用户私钥的设备不能生成邀请。邀请不携带用户别名——别名、头像等个人信息在关系建立
之后才同步。

邀请分两种，两种都要支持，界面应优先推荐定向邀请：**定向邀请**额外携带被邀请方在
该渠道上的权威账号，供应答方核对这份邀请是不是给自己的；**不定向邀请**不携带任何
接收者标识，同一份可以被多个人分别应答。

生成时系统应检查邀请文本的总长度，超出所用承载形式的上限时提示用户缩短备注，
不得静默截断。

<!-- tao:field acceptance -->
**验收：** 邀请的签名可用其中的用户公钥验证，改动任何一个字段后验证失败；一台不持有用户
私钥的设备无法生成邀请，界面说明应在哪台设备上完成；除渠道为"当面"外，不填写渠道与账号
时无法生成；
不定向邀请被两个人分别应答后，发起方分别收到两份待确认的应答，两位应答者互相不
知道对方也应答了；定向邀请被账号与其中所指不符的人应答时，该应答进入待确认列表
并带有不符标记，标记在确认按钮旁可见；备注长到使邀请超出上限时，生成界面给出提示
而不是截断。

<!-- tao:field source -->
**来源：** 加好友不频繁，而且是敏感私密的事，值得用最保守的做法：只有持有用户私钥的设备能发出
邀请与应答。**不持有用户私钥的设备，无论是否已被吊销，都因此不能以用户的名义与陌生人
建立关系**——把签名交给设备私钥的方案做不到这一点，因为陌生人根本无从得知发生过一次
吊销。代价是加好友必须在持有用户私钥的设备上完成，在"加好友不频繁"的前提下这个交换
划算。

这条收益到此为止，不能写成全称：**一台仍持有用户私钥的设备，即使已被吊销，仍能签出
合法的邀请与应答**，还能签新的设备列表把自己加回去。持有用户私钥就等于持有这个身份，
那属于恢复短语泄漏一类的威胁，不是吊销能处理的，见[用户与设备](users-and-devices.md)
的吊销告知需求。

邀请与应答都由人复制粘贴、经双方已经在用的那条渠道传递，系统不从网络接受入站的邀请
或应答——这是渠道绑定成立的前提，经网络直投的产物没有"渠道说这条消息是谁发的"可比。

邀请仍必须带一个设备公钥，但它的用途是关系建立之后对方投递第一条操作与后续消息：在
点对点网络里设备公钥才是可寻址的那个东西，光有用户公钥连不上任何机器。只放签发设备
一台，是因为解开应答需要那份一次性私钥而它只在这台设备上——**应答必须在签发该邀请的
那台设备上粘贴与确认**，在其他设备上粘贴时界面如实说明应去哪一台。

渠道与账号是必需的而不是可选的：YoChat 没有账号目录，一把公钥属于谁只能靠双方
已经在用的渠道来对应，而对应必须落在那个渠道上权威、全局唯一、不由用户随手改动的
账号上——昵称、别名这类可改的东西对应不出任何东西。
```

```{req} 每份邀请使用专属的一次性公钥加密应答
:id: REQ_20260918_37F049FH3B007X48
:status: proposed

每份邀请应携带一个专为该邀请生成的一次性公钥，应答用它加密；这把公钥同时就是
该邀请的标识。对应的一次性私钥只保存在签发这份邀请的那台设备上，不同步到本人
其他设备。该邀请过期或被作废时，系统应销毁它。发起方的长期用户私钥只用于签名，
不用于解密应答。

<!-- tao:field acceptance -->
**验收：** 同时生成的两份邀请携带不同的一次性公钥；一次性私钥不出现在本人其他设备的任何
数据中；作废一份之后，本设备拒绝该邀请的一切应答并覆盖该私钥的存储，而另一份不受影响；
用长期用户公钥加密的应答不被接受。与本机全部数据一样，物理不可恢复不在承诺范围内——
其保护来自数据库整体加密，这一点与[本地存储](../engineering/local-store.md)的边界一致，
不得写成"该私钥不再存在于任何设备上"或"截获的应答再也打不开"。

<!-- tao:field source -->
**来源：** 用长期用户公钥加密时，"作废"只能是一个策略判断——私钥还在，任何以后取得它的人
都能解开历史上被截获的全部应答。一次性私钥可以真的删掉，所以作废是密码学意义上
的收回而不只是不再受理——这里说的是密钥层面：私钥没有别处的副本可用来解密，因此不像
"用长期公钥加密"那样谁拿到私钥都能翻旧账。物理层面的不可恢复不在承诺内，与本机其他数据
同一条边界。多份邀请互不影响也随之成立。它还把长期私钥限制在只做
签名这一件事上，不必承担解密带来的那一类攻击面。

把一次性私钥限制在签发设备一台，是让"作废是密码学收回"这句话真的成立的前提：
私钥只要有副本在别处，本机删除就只是本机的事，而离线的那台不会因为收到一条指令
就去删钥。
```

```{req} 设备的授权由用户签名的设备列表承担
:id: REQ_20260918_2PEVDK1HG1EK3KSW
:status: proposed

一台设备的公钥只能通过所属用户的用户私钥签名的设备列表取得授权；该设备在进入
设备列表时，应向签发它的设备证明自己持有对应的设备私钥。系统不得接受任何未被
这样一份设备列表覆盖的设备公钥。

邀请与应答不内嵌设备列表，也不由设备私钥签名，而是各自由本方的用户私钥直接签名；
双方完整的签名设备列表在关系建立之后经已建立的通道交换。由此有一条必要的例外：
**邀请与应答中由本方用户私钥直接签名的那一台设备公钥，等价于一份仅含该设备的设备列表，
其有效期仅限关系建立期间**；在收到对方完整设备列表之前，双方接受与投递的设备只有交换
期间这两台。首次收到对端设备列表时，若其中不含交换期间使用的那台设备，系统应立即把它
移出设备组并告警。

<!-- tao:field acceptance -->
**验收：** 一台不持有用户私钥的设备既不能生成邀请也不能生成应答，界面说明应在哪台设备上
完成；关系建立之后收到的设备列表，其签名可用对方的用户公钥验证，验证不通过即整份
丢弃；保留合法的设备列表而替换其中任一设备公钥，接收方拒绝；把一个合法签名搬到
另一份邀请、另一个用户或另一台设备上复用，接收方同样拒绝。

<!-- tao:field source -->
**来源：** 需要保证的是"这台设备属于这个用户"，而这件事只由用户私钥的签名提供——设备
自己的签名只证明某人持有那把设备私钥，完全不说明它属于谁。因此授权集中在一份
由用户私钥签名的设备列表上，持有证明只在设备加入列表的那一刻要求一次，那时
新设备与签发设备都在场。

曾经考虑过让邀请内嵌这份列表、由发起设备用设备私钥签名，好处是不持用户私钥的
设备也能离线发邀请。它有一个当时没看出来的代价：被吊销的设备仍然持有那份旧的
签名列表，可以无限期地向从未与该用户建立过关系的人发出通过全部验证的邀请与应答，
而这些人无从得知发生过一次吊销——吊销只随设备列表分发给已有联系人。安全码也拦
不住，它由双方用户公钥导出，而那把用户公钥是真的。把签名收回到用户私钥之后，这条
路径不存在了：不持有用户私钥的设备签不出邀请，也签不出应答。
```

```{req} 应答只有邀请发起方能打开且不可改换作者
:id: REQ_20260918_GXF8WYYMWT40CFSM
:status: proposed

当用户应答一份邀请时，系统应用该邀请所携带的一次性公钥加密应答，使只有邀请的
发起方能解开；应答内携带协议版本与用途标签、所应答邀请的摘要、应答方用户公钥、
应答方所依据的渠道标签与其在该渠道上的权威账号、应答方用于本次交换的一台设备
公钥，以及可选的一段备注，整份内容由**应答方的用户私钥**签名。不持有用户私钥的
设备不能生成应答。应答方的用户别名、头像与其余设备在关系建立之后才同步，不进入
应答。

该邀请的标识（即它的一次性公钥）应出现在应答的密文之外，使发起方能直接定位是哪
一份邀请，不必对每份有效邀请逐一试解。

<!-- tao:field acceptance -->
**验收：** 除发起方之外，任何人都无法从应答中读出应答方的用户公钥、设备公钥与渠道账号；
取得一份合法应答后，构造一份声称来自第三方的变体、或把它转用到另一份仅发起方不同
却复用了同一把一次性公钥的邀请上，发起方均拒绝且不产生任何回复；改动所应答邀请的
任何一个字段都会使摘要不符而被拒绝。

<!-- tao:field source -->
**来源：** 邀请是公开的，认证责任因此全部落在应答上。加密使应答方的标识——尤其是那个
能被用来查在线状态、尝试连接的设备公钥——只对发起方可见，因此应答方不必为了
加个好友而把自己暴露给同一场合里的其他人。

签名必须覆盖整份邀请而不只是它的标识，否则有一条现实的绕过：邀请里的一次性
公钥是公开的，任何看到邀请的人都能复用它另造一份署名自己的邀请拿去给第三方，
再把收到的应答转交原发起方——两份邀请的标识相同，应答在原发起方那里能解开也
能验签，于是他会把一份并非给他的授权当成给自己的。覆盖整份邀请之后，这份应答
与它实际应答的那一份绑死；覆盖应答方自己声明的设备公钥与渠道账号，则使拿到一次性
私钥的人无法把别人的设备或账号换成自己的。

由应答方的用户私钥而不是设备私钥签名，是同一条理由的另一半：只有用户私钥能证明
"这台设备与这个渠道账号属于这个人"，设备自己的签名证明不了归属。
```

```{req} 邀请与应答必须绑定渠道上的权威账号
:id: REQ_20260918_YP7HYFDC5BSKK1BP
:status: proposed

邀请与应答都应必需地携带**本方**所依据的渠道标签与**本方**在该渠道上的权威账号——
各自只声明自己的，不替对方声明。渠道标签只需让人看出是哪个渠道，界面可以给出常见渠道
并允许用户自行填写；账号则必须是该渠道上权威、全局唯一、不由用户随手改动的那一个
（例如微信号，而不是昵称或备注）。比对之前渠道标签按统一规则归一化到**同一套标识**：自填标签
先去空白、折叠大小写，再按内置渠道的别名表映射到该渠道的固定标识（"微信""WeChat"
"weixin" 都映射到内置的微信标识），映射不中才保留为自定义标签。只做"内置用固定标识、
自填按字面"会让一方选内置、另一方手打同一个渠道名时归一化后不相等，把自动比对推进
"提示补充"这个常态。应答所声明的渠道必须与所应答邀请的渠道相同，否则
按不符处理。

**当面交换与二维码是例外**：那里没有"渠道发件账号"可比，硬填一个账号只会让用户学会随便
填。系统应内置一个渠道取值"当面"，选它时账号可空，界面显示的引导改为"当面交换，建议
当场完成安全码比对"，而不是"回到渠道核对发件账号"。

绑定由一次两个方向各做一次的人工比对完成：收到邀请的一方，比对渠道显示的发件账号
与邀请里声明的本方账号；收到应答的一方，同样比对渠道显示的发件账号与应答里声明的
本方账号。系统应在应答之前与确认之前，分别展示对方的用户公钥与对方声明的渠道与
账号，并明确提示用户回到该渠道完成这次比对；用户应能把这次对应记录为本地备注。
定向邀请另携带发起方指定的对方权威账号，供应答方核对这份邀请是不是给自己的，也供
发起方在确认时核对应答方声明的账号是否就是它指定的那个。

<!-- tao:field acceptance -->
**验收：** 除渠道为"当面"外，不填写本方渠道与账号时无法生成邀请或应答；选"当面"时账号可空
且界面不提供定向邀请选项，也不把"无法比对"显示为相符；应答界面与确认界面都展示对方的用户
公钥与其声明的渠道与账号，并包含要求用户回到该渠道比对发件账号的提示；定向邀请在
应答方一侧展示它所指定的对方账号；该次对应的记录不出现在发送给对方的任何数据中。

<!-- tao:field source -->
**来源：** YoChat 没有账号目录，无法自己证明一个公钥属于哪个人。可以借用的是双方本来就在用
的渠道——在那里"这条消息是谁发的"由该渠道保证。邀请与应答各自经由它传递一次，
双方就各自完成了一次对应。绑定必须落在那个渠道的权威账号上：昵称、别名、备注都
可以随手改，对应不出任何东西。

这条绑定的强度不超过那个渠道对账号归属的保证：账号可能被盗、可以转让，有的渠道
还允许改动账号本身。所以它记录的是"当时依据的渠道与账号"，并且不能替代安全码
比对——安全码的价值恰恰在于不依赖这条渠道。

它真正生效的地方在界面：用户若不回到渠道核对，这条绑定就等于没有。所以那句提示
不是可有可无的装饰，而是这条需求的承重部分。
```

```{req} 本方渠道身份可保存并复用
:id: REQ_20260919_757FNZE6B8FN15YV
:status: proposed

系统应让用户保存并管理自己的渠道身份——每条是一对「渠道标签 + 本方在该渠道上的
权威账号」，可在设置中管理，也可在生成邀请或应答时就地新增。界面应内置一组常见
渠道供选择，同时允许用户自行填写渠道标签。生成邀请或应答时从已保存的条目中选取，
不要求每次手工输入；用户可以指定一条为默认。

保存的渠道身份是本地私有数据，在本人设备之间随通讯录同步，但只在用户为某一份邀请或
应答选用它时才进入该产物；系统不得把整份列表发送给任何联系人，也不得未经选择就自动
附加。无论是否由保存的条目
填入，生成界面都应明确显示这一次将要写进产物的是哪个渠道与哪个账号。

收到定向邀请时，系统应把邀请中指定的对方权威账号与本方已保存的同渠道账号自动比对，
并展示比对结果：相符时说明这份邀请是发给你的；不符时醒目提示；本方没有该渠道的
已保存账号时，提示用户补充后再判断，不得因为无法比对就默认相符。

<!-- tao:field acceptance -->
```

```{req} 邀请各自独立，有有效期且可随时作废
:id: REQ_20260918_6J1EMT8Y9HZ68STG
:status: proposed

每份邀请应带有自己的标识（即它的一次性公钥）与有效期；用户可以同时持有多份有效
邀请，并能随时单独作废其中任何一份。因为一次性私钥只存在于签发这份邀请的那台设备上，
作废就是在该设备停止受理并覆盖该私钥的存储。

吊销一台设备时的处置要如实拆成两句：本人其余设备**不再受理**该设备签发的未过期邀请，
并提示用户重新生成；而**被吊销设备上的那些一次性私钥无法被销毁**——它已经不被信任，
也不会配合删除。若它同时持有用户私钥，它仍能解开投向那些邀请的应答并以用户名义确认，
因此系统应提示用户撤下已经张贴出去的邀请文本。

<!-- tao:field acceptance -->
**验收：** 同时生成的多份邀请各自有不同的标识，作废其中一份不影响其余；作废后新的应答被
拒绝，且本设备覆盖了该私钥的存储；吊销一台设备后，本人其余设备不再受理它签发的未过期
邀请并提示重新生成；已经据此建立的关系不受影响。

<!-- tao:field source -->
**来源：** 用户会在不同场合贴不同的邀请，需要能分别管理：哪一份贴到了哪里、哪一份该收回。
有效期把邀请能被使用的窗口限制住；单独作废让用户在发现贴错了地方时可以立刻
止损，而不必等到过期，也不必连带影响其他场合那一份。

"作废等于密码学收回"这句话需要一个前提才成立：私钥不能有副本在别处。早先的
方案把一次性私钥同步到本人各设备，于是承诺只能分两段——本机立即停止受理是确定
的，密码学意义上的不可解开要等全部副本清除完成，而离线的那台不会因为收到一条
指令就去删钥。把私钥限制在签发设备一台之后，这个差别消失了，作废重新成为一句可以兑现的承诺——但它
兑现的是"本设备停止受理且覆盖该私钥的存储"，不是"这串字节在磁盘上再也找不回来"，后者
与本机其他数据一样不在承诺范围内。

吊销一台设备时连带作废它签发的邀请，是同一条道理：那些邀请的一次性私钥就在
它上面，它已经不被信任，也不会配合删除。
```

```{req} 应答方自发出应答起即完成本方确认
:id: REQ_20260918_A1MZYZ7JV43G7EJ3
:status: proposed

应答方自发出应答起即视为已完成本方的确认。此后它应接受来自该邀请发起方——其用户公钥

不打字。在收到这第一条操作之前，应答方不向发起方发送任何消息。

两侧的等待都不是无限期的，且**时限相同**：超过所应答邀请的有效期再加一段宽限之后，
应答方这一侧降级为无关系、不再接受来自该用户公钥的消息；发起方那一侧的待确认应答同时
作废，界面不再提供确认入口，提示重新交换。界面给出的原因必须如实——应答方看到的是
"这次交换已过期，对方可能确认了也可能没有"，而不是"对方没有回应"，因为发起方确认了却
没打字、或应答方的设备长期离线，都会落到同一个可见状态上。

对称的时限缩小了两侧不一致的窗口，但**消灭不了它**：投递不可靠时不存在能让双方必然就
"关系是否成立"达成一致的有限交换。因此系统不承诺这种不一致不会发生，而应保证它**能被
发现、能被恢复**：已经建立关系的一侧在一个阈值内收不到对方任何操作时，如实提示"对方
可能没有完成这次交换"并提供重新交换的入口；已降级的一侧对该邀请保留一条短期记录，使
同一次交换的迟到操作被识别为过期交换而不是陌生对端，并据此提示重新交换。

<!-- tao:field acceptance -->
**验收：** B 应答 A 的邀请后，A 确认；即使 A 此后不发送任何应用消息，B 也在收到 A 的设备组
加入操作时把关系转为已建立；在收到这第一条操作之前，B 不向 A 发送任何消息；A 拒绝时 B
不收到任何数据，界面保持等待状态；等待超过邀请有效期加宽限之后，B 侧降级为无关系且此后
不再接受来自该用户公钥的消息，A 侧的待确认应答同时作废、确认入口关闭，两侧界面给出的
都是"这次交换已过期"而不是对对方行为的断言；在有效期加宽限之后 A 无法再确认该应答；
构造 A 在有效期末确认而其第一条操作在 B 降级之后才到达的执行，B 把它识别为过期交换并
提示重新交换（而不是当作陌生对端静默丢弃），A 在阈值内收不到 B 的任何操作时同样提示
这次交换可能未完成并提供重新交换入口；来自邀请中未出现的用户公钥的消息，B 始终一概
不接受。

<!-- tao:field source -->
**来源：** 没有这一条，这条链路就断了：规格规定拒绝时什么都不发，却从未规定接受时向应答方
发什么，于是 B 无从得知 A 已确认；而 B 若不认为关系已建立，A 的第一条消息会被
当作陌生对端丢弃且不回应，A 只能无限兜底重发。让应答本身构成本方的确认，是
补齐这条链路而不新增消息类型的最小做法——B 应答时已经作出了选择，再要求它对
同一个人确认第二次没有意义。

给这个状态定一个时限，是因为"已确认"态意味着 B 对该用户公钥无限期开放接受；
一个无界的接受窗口本身就是暴露面，而邀请本来就有有效期，顺着它收口最自然。
```

```{req} 安全码可带外比对
:id: REQ_20260918_FXAWEFJ6Q0S22E5S
:status: proposed

系统应为每个联系人提供一个可供人工比对的安全码，双方通过一条独立于建立关系
所用渠道的途径比对一致，即可确认之间没有中间人；比对结果记录在本地。该安全码
须满足：攻击者使双方看到相同安全码的概率不得高于所选构造明示的上界，该上界
须与展示长度、构造与用途标签一并记录在设计中；它随联系人的用户身份而定，不随
其增删设备而变；本人任一设备都能独立核对当前记录的已校验状态仍然对应着此刻
持有的那把用户公钥。比对流程应把它分成两部分，指示双方各自念出其中一部分并
各自核对收到的那一部分，而不是由一方念出完整值、另一方口头确认；任一部分核对
不上都不得记为已比对。

<!-- tao:field acceptance -->
**验收：** 同一对用户在各自设备上看到相同的安全码；设计文档给出所选构造的碰撞或猜中
概率上界及其推导，且该上界与实际展示长度一致；对方增删设备后本方的安全码与
已校验状态不变；把本地记录的对方用户公钥
替换掉之后，本人任一设备都能发现已校验状态不再对应当前公钥；已比对状态在界面
上可见；界面在引导比对时明确提示应当换一条渠道，而不是在刚才传递邀请的那条
渠道里比对；两人各自被指示念出不同的部分，两部分合起来覆盖完整的安全码。

<!-- tao:field source -->
**来源：** 签名证明的是"这条消息由持有某个私钥的人发出"，证明不了那个私钥属于你想找的人。
中间人不篡改已签名的消息，他整条替换、用自己的密钥重新签名：截获邀请、换成自己
的邀请转发，截获应答、换成自己的应答送回。每一步验签都通过，因为双方都无从知道
那个公钥本该是什么。借助已有渠道完成的对应把门槛提高到必须控制那条渠道，但控制
渠道的人恰恰做得到上面这件事。安全码的全部价值就在于它不依赖那条渠道：换一条
途径念一遍，攻击者没法同时控制两条。它由双方公钥导出，公开出去无害——攻击者
手里的公钥不同，算出来的安全码就不同，他伪造不了；把它当秘密处理只会让用户
不敢用最方便的方式比对。

各念一半的理由是流程上的，不是密码学上的：它不构成"知道即可信"的证明——中间人
同时看得到双方的公钥，因此他算得出那个真正的安全码，知道它证明不了任何身份。
它真正起的作用是逼双方都动手：一方念完整串、另一方回一句"对上了"，在现实中经常
意味着后者根本没看，而这正是安全码失效的主要方式。安全强度不因分开而下降，因为
两半分别由对方核对、合起来覆盖完整的值，攻击者仍须让整个安全码碰撞；只核对其中
一半就收工才会把碰撞难度降低到原来的开方量级，所以任一部分不符都必须判为失败。

本条刻意只写性质不写做法，因为可选的做法不止一种，而它们的取舍在设计阶段才
判断得清。把安全码定义成双方公钥的哈希是最直接的一种：任何设备任何时候都能
重算，代价是必须足够长（同类产品用到六十位数字）才扛得住碰撞搜索，而那么长的
东西现实中很少有人真去念。另一条路是先承诺后揭示的短认证串：双方在看到对方的
值之前先各自承诺，因此攻击者只有一次机会且失败当场可见，几位数字就够，人也就
真的会念。它的代价是不可重算——它只是那一次交换的事实，事后只剩一个存下来的
结论，没有东西可以拿来复核。所以本条把"任一设备都能核对已校验状态仍对应当前
公钥"写成必须满足的性质：无论选哪条路，都不能让已校验状态变成一个无法复核的
断言。值得注意的是，把安全码改成只有双方算得出的共享秘密（例如从一次密钥协商
导出）本身并不带来额外安全性——中间人是他那两条腿各自合法的参与者，双方各自
会看到什么他都算得出来；真正起作用的是承诺，不是保密。
```

```{req} 拉黑的可推断性须如实说明
响应"推断出状况发生了变化，这是点对点网络的固有性质，YoChat 无法避免；以及
拉黑绑定到对方当前的那把用户公钥，对方可以用一对新生成的用户密钥重新应答你
公开张贴的邀请，届时他会作为一个新的待确认应答出现，需要你自己辨认。

<!-- tao:field acceptance -->
**验收：** 拉黑的确认界面包含上述两条说明；系统不提供任何声称能完全隐蔽拉黑的选项，也
不声称拉黑能永久阻止某个人。

<!-- tao:field source -->
**来源：** 在这类网络中，持有对方设备公钥就能通过公开的发现机制查到在线状态，可用的中转
入口数量也很有限，因此"在线"这件事本身藏不住。既然藏不住，就不该让用户以为
藏住了。

拉黑的作用域也必须说清楚。用户就是本机生成的一对密钥，没有任何东西把一个人
与他的用户公钥绑定，所以拉黑只能作用到那一把公钥上——对方换一对新密钥再来应答
公开张贴的邀请即可。用户唯一的防线是自己认出来，而他必须知道这一点才谈得上
防备；把拉黑说成一劳永逸，是在骚扰场景里给出一个错误的安全预期。
```

```{req} 解除拉黑补齐期间的消息
:id: REQ_20260918_J22VY0VTZVRBY1P6
:status: proposed

当用户解除拉黑时，系统应恢复与该联系人的同步，并补齐拉黑期间对方发布的消息。

<!-- tao:field acceptance -->
**验收：** 拉黑期间对方发送 N 条消息，解除拉黑后：在上限之内的部分自动按原顺序出现；
超出重发范围上限的部分，界面说明需要对方批准或改走历史同步，会话不停留在等待；对方已
删除的部分，本方收到可验证的不再提供声明并在界面标明原因。此后的消息收发不受影响。

<!-- tao:field source -->
**来源：** 拉黑是一个可撤销的决定。若解除之后聊天会话永久损坏或缺失一段，用户实际上不敢
使用这个功能。
```

```{req} 删除联系人时询问是否删除历史
:id: REQ_20260918_F7ZBKSBAC1N4KM2K
:status: proposed

当用户删除一个联系人时，系统应询问是否同时删除该聊天会话的历史，并按用户的
选择执行。删除联系人这一关系变更随通讯录在本人设备之间同步；勾选同时删除历史
时，对本人其他设备只产生一条删除指令，由那些设备各自确认后才执行。系统还应
说明：被删除方的可观察现象与被拉黑相同——对方设备在线却不再有任何响应。

<!-- tao:field acceptance -->
**验收：** 选择保留时该聊天会话的消息仍可被搜索到；选择删除时这些消息在本设备上不再可读；
本人其他设备上该联系人同样消失，但其历史在各自确认该删除指令之前仍然完整；
删除的确认界面包含关于被删除方可观察现象的说明。

<!-- tao:field source -->
**来源：** 删除关系与删除记录是两个不同的意图。默认其中任何一种，都会让另一部分用户失去
他们本想保留的东西，而本地是唯一的副本。

两者的传播方式也必须不同，理由与消息删除一致：关系变更是保护性的，不同步会
让某台设备上该联系人仍然可达，拉黑与校验状态也会被旧记录覆盖回来；而删除历史
是破坏性且不可逆的，一次误触或一台失守的设备不应当能抹掉全部设备上的全部历史。
```

```{req} 删除已拉黑的联系人保留拉黑记录
:id: REQ_20260918_SD1XKGXS4DBG5ZTE
:status: proposed

当用户删除一个处于拉黑状态的联系人时，系统应保留一条仅含其用户公钥的拉黑记录，
使其此后的应答继续被丢弃，直到用户在拉黑名单中显式移除该记录。

<!-- tao:field acceptance -->
**验收：** 拉黑并删除某人之后，其对本方邀请的新应答不出现在界面上；该条目在设置的拉黑
名单中可见并可移除。

<!-- tao:field source -->
**来源：** 删除关系与撤销拉黑是两个不同的意图，而它们失败的方向不对称：若删除顺带解除了
拉黑，用户会在毫不知情的情况下重新变得可被打扰，这个方向不可接受。
```

```{req} 重新添加不继承校验状态
:id: REQ_20260918_XS6GKW2ZZ4R1CS6Y
:status: proposed

系统应把重新添加的联系人视为一个新建立的关系，安全码校验状态不继承，需要重新
比对。

<!-- tao:field acceptance -->
**验收：** 删除并重新添加某人后，该联系人处于未校验状态，界面明确提示这是新建立的关系。

<!-- tao:field source -->
**来源：** 删除删掉的正是承载那次比对结论的记录。把未经重新确认的信任延续下去，安全码就
失去了意义；而这个方向的失败是安全的，它只要求用户重做一次比对。
```

```{req} 联系人刷新保留拉黑与校验
:id: REQ_20260918_GG1H42XAJXA0M4ZT
:status: proposed

当联系人因增加设备或吊销设备而使其记录被刷新时，系统应保留该联系人
的拉黑状态与校验状态。

<!-- tao:field acceptance -->
**验收：** 对方更换设备后重新可达，本方对其的拉黑仍然生效，已比对的校验状态仍然有效；已建立
关系的联系人经另一份邀请再次应答时，它作为一条新的待确认项出现并标明来自另一份邀请，
不自动改写既有记录，拉黑与校验状态同样不变。

<!-- tao:field source -->
**来源：** 刷新不是新建关系。若刷新会清空这些状态，被拉黑的人只要换一次设备就能重新可达，
用户也要在对方每次换设备后重新比对安全码。
```

```{req} 通讯录在用户的设备之间同步
:id: REQ_20260918_1F7X3ZHJS4N07TRG
:status: proposed

用户的联系人记录及其拉黑状态、校验状态、备注名与备注说明，以及本方的渠道身份表，
应在该用户的全部设备之间同步。合并规则要可验收：拉黑与删除等保护性状态不被任何未包含
它的旧记录覆盖；删除后重新添加的联系人不继承删除前的校验记录。

<!-- tao:field acceptance -->
**验收：** 在设备 A 上添加、拉黑、完成校验或修改备注之后，设备 B 在连通后显示相同的状态。

<!-- tao:field source -->
**来源：** 多设备属于首个交付增量。若每台设备各有一份通讯录，用户必须在每台设备上重复
全部操作；拉黑尤其危险，在手机上拉黑而电脑上没有会让防护失效。
```

```{req} 好友别名与好友备注都是私有的
:id: REQ_20260918_0P17VCWKG2FZ26SZ
:status: proposed

用户应能为每个联系人分别设置两项仅自己可见的内容：一个好友别名，用来代替对方
自设的用户别名显示；以及一段较长的好友备注，用来记录任意说明（例如对方在某个
其他渠道上的标识）。两者都应能随时修改，并支持按好友别名、好友备注或对方的
用户别名检索通讯录。

<!-- tao:field acceptance -->
**验收：** 设置好友别名后界面以它为主显示该联系人，同时仍可看到对方自设的用户别名；按三者
中任意一项均可检索到该联系人；两者都不出现在发送给对方的任何数据中。

<!-- tao:field source -->
**来源：** 这是两件不同的事，合成一个字段会两头都不好用。别名要短、要能直接当称呼显示，
它存在的理由是对方自设的名字由对方决定、可以随时改、也可能重名或被冒用，用户
需要一个自己说了算的称呼才能稳定地找到人。备注要能写长句，用来记住这个人是谁、
通过哪个渠道以什么身份加上的。两者都是用户的私事，不应当让对方知道。
```

```{req} 联系人分组是私有的
:id: REQ_20260918_CE3T62ZJNE2FKYKE
:status: proposed

用户应能把联系人分组，一个联系人可以属于多个分组；分组及其成员关系仅自己可见，
不发送给任何联系人，并在本人全部设备之间同步。

<!-- tao:field acceptance -->
**验收：** 建立分组并加入联系人后，分组在本人其他设备上出现；分组名称与成员关系不出现在
发送给任何联系人的数据中；联系人无法得知自己被分在哪个组，也无法得知存在哪些组。

<!-- tao:field source -->
**来源：** 分组是用户自己整理关系的方式，它反映的是用户怎么看这些人，这件事没有理由让被
分组的人知道。在本增量内它就有独立价值：通讯录一旦超过几十人，按备注名检索只
能在已经想起是谁的前提下使用，而分组是"我想找那一类人"时唯一可用的入口，这正
是用户要求的通讯录管理本身。它同时还是后续文件共享设定可见范围时最自然的单位
——逐个勾选联系人在人多之后不可用。
```

## 用例与性质

```{uc} 同一份邀请被多人分别应答
:id: UC_20260918_RC0CZ2W71EG8BJ0H
:status: proposed
:verifies: REQ_20260918_2276A5JCK1KGNS1A, REQ_20260918_1VXJQ68HXHM0JR0Q

<!-- tao:field given -->
**给定：** 用户 A 生成一份**不定向**邀请并把它贴在一个有 B 和 C 在场的群里。

<!-- tao:field when -->
**当：** B 与 C 各自对同一份邀请作出应答，A 分别确认。

<!-- tao:field then -->
**则：** A 与 B、A 与 C 各自建立独立的联系人关系；B 与 C 之间不因此产生任何关系，也无法从邀请或应答得知对方也应答了。
```

```{uc} 双方各自借已有渠道完成对应

<!-- tao:field given -->
**给定：** A 与 B 在另一个渠道上互相认识，在该渠道上一条消息由谁发出是由该渠道保证的。

<!-- tao:field then -->
```

## 待确认事项

- 邀请与应答的承载形式（深层链接、二维码、纯文本）属于交互方案，具体格式见
  [好友交换](../engineering/contact-exchange.md)；本篇只约束两者都要能被人复制粘贴
  到另一个渠道里，且生成时要检查长度而不是静默截断。
- 邀请有效期的默认值，以及应答方"已确认"态的宽限时长。
- 备注字段的长度上限，与邀请文本总长度的上限一并按承载形式实测确定。
- 用户别名可以随时更改也可能被冒用，好友别名正是为此存在；是否还需要在对方改名时
  额外提示，留待有实际使用反馈后决定。
- 若未来改用先承诺后揭示的短认证串，须重新核对本人其他设备能够独立复核的验收要求；
  未参与原交换的设备没有可重算的短串。当前可重算构造、长度与上界推导以
  [好友交换设计](../engineering/contact-exchange.md#DOC_20260918_T09EDKCAGT4Q75JT--architecture)为准。
- 是否支持在一份应答被确认之前撤回它。
