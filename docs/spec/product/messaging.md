# 聊天会话与消息

<!-- tao:section scope -->
## 目标与边界

本篇界定 YoChat (有聊) 中一对一聊天会话与用户和自己的聊天会话里，消息如何产生、
如何传递、以什么顺序呈现、送达情况如何让用户看见，以及本地历史如何检索。

本篇的一个基本立场是：消息不因为传输或解密出问题而丢失，也不为此打扰用户。每条
消息在发出之前已经在发送方本地落盘，所以乱序会自行补齐，解密失败则由双方自动
重建加密通道并重传，两者都不需要用户做取舍。只有在长时间无法与对方连通时才告知
用户，并说明它会自动继续。

消息默认永久保存，不做任何自动清理；要清理只能由用户自己删除，而删除在每一台设备
上都由该设备的用户自己说了算——别的设备至多送来一条待确认的删除指令。

明确不做三件事。**不支持消息撤回**：撤回只是一个愿望，无法保证接收方没有看到，
而一条突然变成"已撤回"的消息通常只让对方更困惑；要更正就再发一条说清楚。
**不做表情回应**：想发表情，发一条带表情的消息就是了，不值得为它引入一套附着在
消息上的可变状态。**不做已读回执，只有已接收回执**：系统能诚实断言的只是数据到了
对方设备，人有没有看见它无从得知；真要对方确认，就让对方回一句。

范围内：消息的端到端加密；缺失检测与严格按序应用；乱序等待与接收方请求重发；发送方
兜底重发；无法解开时的自动通道重建；送达状态；离线送达；与自己的聊天会话；跨设备
同步与去重；引用回复；全文搜索；永久保存与用户主动删除；删除指令的逐设备确认；
操作目标的确定；存储失败的报告；接收、落盘与重发的速率上限；陌生对端的处理。

范围外：与谁能通信由 [好友与通讯录](contacts.md) 决定；用户与设备见
[用户与设备](users-and-devices.md)；群聊天会话见 [群聊](group-chat.md)；文件见
[文件发送与共享](file-transfer.md)；网络层暴露面见
[隐私与防护](privacy-and-safety.md)。

交付边界：本篇全部需求属于首个交付增量，覆盖一对一聊天会话与用户和自己的聊天会话。

<!-- tao:section terms -->
## 术语

本篇使用的聊天会话、等待、通道重建、送达状态、应用游标等术语，定义见
[项目术语](../glossary.md)。其中"等待"专指乱序造成的暂时状态，与无法解开消息后
触发的"通道重建"是两件事，不可互换使用。

<!-- tao:section requirements -->
## 需求

```{req} 发送与接收一条消息
:id: REQ_20260918_JW13382752N6T1XR
:status: proposed

用户应能在一个聊天会话中撰写并发送一条文本消息。该消息应先在本地落盘再进入
发送，并在会话参与方的任一未被吊销设备收到后，按作者写入的顺序呈现给对方。
消息的文本形式至少支持换行与常用符号字符；单条消息的大小上限见本篇关于输入
上限的需求。

<!-- tao:field acceptance -->
**验收：** 从一台设备发送一条含换行与表情字符的消息，对方设备的该聊天会话中按序出现该
消息，内容与原文逐字符一致；对方全部设备离线时，该消息停留在已写入本地的状态，
界面不报错也不丢失它；应用在发送后立即崩溃并重启，该消息仍在且状态不变。

<!-- tao:field source -->
**来源：** 这是整个产品最基本的那条承诺，本篇其余需求都是它的性质与边界。把它单独写出来，
是为了让"一对一聊天能不能用"这件事本身可被验收、可被追溯，而不是只能从加密、
顺序、重发等各条边界需求里间接推断。
```

```{req} 消息端到端加密
:id: REQ_20260918_DCNS38550F4AY1K5
:status: proposed

系统应对消息内容端到端加密，使只有聊天会话参与方当前设备列表中、且未被吊销的
设备能够解密。

<!-- tao:field acceptance -->
**验收：** 在传输路径上捕获的数据不含明文正文；一台设备被吊销之后无法解出此后产生的消息。

<!-- tao:field source -->
**来源：** 这是 YoChat 的基本承诺，也是不采用中心服务的理由。
```

```{req} 消息缺失必须可被检测
:id: REQ_20260918_YACX40YKDV0GV3G6
:status: proposed

系统应使每个聊天会话中的消息可以判定其前驱是否已经到达，从而能够识别出有消息
缺失，而不是把缺失表现为对方没有说话。

<!-- tao:field acceptance -->
**验收：** 人为延迟传输中的一条消息后，接收方等待该消息而不是直接呈现其后的消息；等待
超过所设时限之后，该聊天会话在会话列表与会话内以非打扰的行内方式标明有更早的
消息尚未到达、正在自动获取，且不提供任何会丢弃消息的入口。

<!-- tao:field source -->
**来源：** 没有中心服务，也就没有一份权威的消息列表可以对账。若接收方无法察觉缺失，丢一条
消息与对方沉默在界面上完全一样，用户会据此做出错误判断。
```

```{req} 严格按序应用，不得跳过
:id: REQ_20260918_537BK4VME23Y2GTW
:status: proposed

系统应严格按作者写入的顺序向用户呈现并应用同一作者在同一聊天会话中的消息，
不得跳过尚未到达的消息，也不得因为超时、缓冲区上限、内存压力或任何其他资源
原因而放弃等待。系统应为"能容忍多大程度的乱序与缺失"设定明确的上限，超出该
上限时触发通道重建与重传，而不是跳过。

<!-- tao:field acceptance -->
**验收：** 以性质测试验证：对任意到达顺序、任意重复投递与任意次中断重启，某一作者在某一
聊天会话中的已决序号集合始终是从该会话起点开始的连续区间，且每个非已应用的
位置都带有可向用户展示的原因。已决序号指已应用、已放行与已删除三者之和；
构造超出所设乱序与缺失上限的投递序列，系统触发通道重建并最终取得完整序列，
而不是跳过。

<!-- tao:field source -->
**来源：** 三条理由，都与"往前跳"这个诱人的做法冲突。第一，用户要按作者写下的顺序读到
消息，乱序呈现会改变对话的含义。第二，容忍乱序与缺失是靠预留尚未使用的解密
密钥换来的，这个窗口必然有界：超出之后那些消息就真的打不开了，而跳过会让系统
再也不去取回它们。第三，窗口留得越大、未用密钥存得越久，前向保密就越弱——它不是
免费的。所以常规的容错反射（超时放弃、缓冲区满了丢弃、淘汰最旧的）在这里都是
错的方向：正确的补救是重建通道并重传，让缺失的部分真的回来。
```

```{req} 等待只因乱序出现并自行结束
:id: REQ_20260918_BXC7RNH3YCQZ9BQY
:status: proposed

当同一作者的某条消息尚未到达而其后的消息已经到达时，系统应等待缺失的消息，并
在其到达后按顺序应用。该状态应自行结束，不需要用户做任何事，也不呈现为需要
用户处理的问题。

<!-- tao:field acceptance -->
**验收：** 制造一次乱序后恢复连通，聊天会话自动追上；等待期间界面不弹出需要用户处理的
模态提示，也不提供任何会丢弃消息的修复入口——行内的等待标识不属于此列。

<!-- tao:field source -->
**来源：** 乱序是网络的常态，它会自己好。把它呈现成一个问题，只会诱导用户去执行破坏性的
操作。
```

```{req} 无法解开的消息触发自动通道重建
:id: REQ_20260918_2MTCJFK2TX0E9ACY
:status: proposed

如果某条到达的消息无法解开，或缺失与乱序超出了系统所设的容忍上限，则系统应
丢弃这条尚未落盘的数据，与对方自动重新建立加密通道，并由双方重传各自尚未确认
送达的消息。该过程不需要用户参与，也不丢失任何已经落盘的消息。

<!-- tao:field acceptance -->
**验收：** 构造一条无法解开的消息、以及一段超出容忍上限的缺失，两种情况下在双方连通时
聊天会话都自动恢复，此前与此后的消息一条不少且顺序正确；全程无需用户操作，
也没有任何消息被标记为放弃。

<!-- tao:field source -->
**来源：** 解密失败与超出容忍窗口都是明确的信号，而每条消息在发出之前已经在发送方本地
落盘，所以发送方随时可以用新的通道重新加密再发一次。既然能完整恢复，就不该把
它变成一个需要用户做取舍的故障，更不该让用户去放弃消息。
```

```{req} 已发送消息永久保留原文
:id: REQ_20260918_XMX889MKAJ4QK8JX
:status: proposed

系统应在本地永久保留已发送消息的原文，包括已经确认送达的；只有用户主动删除，
或用户在本设备上同意了来自本人其他设备的删除指令，才使其消失。通道重建与重发
所用的正是这些原文。

<!-- tao:field acceptance -->
**验收：** 在对方确认之后重启发送方并由对方请求重发，已确认的消息仍能被重新送出；未经
用户删除或未经本设备确认的删除指令，不会使任何已发送消息的原文消失。

<!-- tao:field source -->
**来源：** 重建通道与重发都靠发送方手里还有原文，这是"不丢消息"能够成立的物质前提。而
保留到确认为止是不够的：对方的设备可能损坏、可能重装、可能新加一台设备想要
补齐，这些时候唯一还有原文的地方就是发送方。既然已经决定消息默认永久保存，
自己发出去的那一半没有理由例外。
```

```{req} 接收方可主动请求重发
:id: REQ_20260918_VBRZ8N5AC8QR0N3B
:status: proposed

当某条消息迟迟未到而其后的消息已经到达时，接收方应在自行设定的等待时限之后向
发送方请求重发缺失的部分；等待时限与用于保存乱序消息的缓冲区上限由接收方自己
决定。该请求与随后的重发应自动完成，不打扰用户。

<!-- tao:field acceptance -->
**验收：** 制造一次持续的乱序缺失，接收方在其设定的时限之后自动发出重发请求并在收到后
按顺序应用；全程无需用户操作，界面不弹出提示；缓冲区达到接收方设定的上限时，
接收方请求重发而不是丢弃已缓存的消息。

<!-- tao:field source -->
**来源：** 由接收方发起，与解密失败时由接收方发起通道重建是同一个形状：只有接收方知道
自己缺什么、等了多久、还能缓存多少。让接收方掌握时限与缓冲区上限，它就能在
资源压力下用请求重发来替代丢弃——而丢弃在这个模型里是破坏性的。
```

```{req} 发送方在长时间未获确认时兜底重发
:id: REQ_20260918_W5CABH0H2PAJ2TAG
:status: proposed

如果发送方在一段时间内没有收到某条已发送消息的送达确认，则应重发它；重发应
自动完成，不打扰用户，并受通道重建与速率上限的约束。

<!-- tao:field acceptance -->
**验收：** 让接收方完全收不到某条消息（既无乱序也无解密失败，因此接收方无从察觉缺失），
发送方在其时限之后自动重发，接收方最终收到该消息且不产生重复。

<!-- tao:field source -->
**来源：** 接收方能请求重发的前提是它察觉到了缺失，而察觉依赖于看到了更靠后的消息或者
解密失败。如果一条消息完全没有到达、且它是当前最新的一条，接收方看不出任何
异常——它和对方没说话无法区分。这种情况只有发送方能发现，因为只有它在等一个
始终没来的确认。
```

```{req} 重发请求由被请求方的全部设备共同应答
:id: REQ_20260918_Q15AKFP42V04BVM3
:status: proposed

当一方请求重发时，系统应把该请求送达被请求用户的全部未吊销设备及请求方本人的其他未吊销设备，由各设备分别
提供自己持有的部分；只有在这些设备共同持有的集合中仍然缺失时，才视为无法提供。

<!-- tao:field acceptance -->
**验收：** 被请求用户的两台设备各自持有所缺范围的不同部分时，请求方最终取得完整的范围；
任一台设备离线不导致其他设备持有的部分无法提供；联系人全部离线时，请求方仍能从本人常在线设备取得离线期间保存的消息。

<!-- tao:field source -->
**来源：** 删除指令需要每台设备各自同意，因此同一个用户的不同设备上的历史未必一致。向
单独一台设备请求重发会得到一个不完整的答案，而请求方无从知道别处其实还有。
能提供的范围是这些设备的并集，请求就必须按并集来问。
```

```{req} 重发只在请求方的入组基线之后提供
:id: REQ_20260918_MEK3HV5ENZDAE9SS
:status: proposed

每台设备在一个聊天会话中有一个入组基线，即它进入该会话成员集合时的位置。系统
应只对基线之后的范围提供重发；对基线之前的请求一律拒绝，无论请求方是否为该
会话的当前成员。取得基线之前的历史只能通过历史同步。

<!-- tao:field acceptance -->
**验收：** 一台新设备加入后请求基线之前的范围，被拒绝且未取得任何内容；它请求基线之后的
范围时正常取得；拒绝不会使该设备卡在基线处，它能继续接收并应用基线之后的消息。

<!-- tao:field source -->
**来源：** 棘轮只阻止新设备解开旧密文，它不阻止仍持有原文的设备用新通道重新加密再发一次。
没有这条限制，重发就成了一条绕过"新设备默认只能读取加入之后的消息"的通道——
恢复短语一旦泄漏，攻击者用一台合法的新设备身份就能把历史要走，而历史同步必须
在持有历史的设备上发起这条防线也就同时失效了。
```

```{req} 大范围重发请求须经被请求方用户批准
:id: REQ_20260918_XBRY5Q81Z4ZPP6ER
:status: proposed

重发请求的范围应有默认上限，以时间跨度与条数两者共同界定。超出上限的请求，
被请求设备不得自动提供，应交由该设备上的用户在界面上逐次批准；界面应显示请求
方是谁、来自其哪一台设备、以及所请求的范围与条数。系统不得提供对此类请求的
"永远同意"选项。没有界面的设备（例如常在线设备）应回应一条自己签名的"需人工
批准"声明，使请求方能把它与"未答复"区分开；该批准可以在该用户任一有界面的设备上作出，
经本人设备间的私有通道转达回持有内容的那台设备。同一请求方对同一范围的重复请求，在被
请求方合并为一条待批准项，不重复产生提示。

上限的例外只能由**被请求方**依据自己可核实的状态判定：凡落在它自己"已向**该请求方设备**
发出但未获**该设备**送达确认"的集合内的位置不计入超限范围——那是补送自己没送到的东西，
不是搬历史。**这个集合按设备记，不按用户记**：请求方另一台设备是否已确认收到，不影响
本台设备的正当补齐；按用户记会与"对方已收到"的任一设备粒度互相抵消（见该条需求）。请求
方声明的任何理由都不能使被请求方越过默认上限，"这是我先前拒绝的"这类说法对方无从核实。

<!-- tao:field acceptance -->
**验收：** 在上限之内的重发自动完成，用户不被打扰；超出上限的请求出现在被请求设备的界面
上并列出上述信息，未获批准时不提供任何内容；同一请求方对同一范围在批准前反复请求时，
被请求方只显示一条待批准项，批准之后再发起新的超限请求需要再次批准；无界面设备回应一条
可验签的"需人工批准"声明，请求方界面把该位置显示为"等待对方批准"而不是"未答复"，且该
位置照常放行、不阻塞其后的消息。

<!-- tao:field source -->
**来源：** 重发的用途是补齐最近缺失的那几条，不是搬运历史。没有上限，一台被盗的、加入
已久的设备就能把入组基线之后的全部历史一次要走——入组基线挡住的是加入之前的
部分，挡不住之后越积越多的那一段。设上限还顺带把两条路径的边界划清楚了：小
范围补齐自动进行，大范围取得历史必须走历史同步，而那一条本来就要求在持有历史
的设备上显式发起。不提供"永远同意"，是因为这个动作的代价随时间单调增长，一次
性的授权不该覆盖将来任意大的范围。
```

```{req} 无法提供的消息须有可验证的明确答复
:id: REQ_20260918_9MKG1QMBXQAG6C12
:status: proposed

如果被请求重发的消息在某台设备上已不存在，则该设备应回应一条由其设备私钥签名
的声明，说明本设备不再持有该范围。请求方按两种情形放行，且必须能区分它们：
收齐所依据的那一版双方设备并集中全部未吊销设备的声明时，标记为**相对该版本的**不再
提供——"需人工批准"声明既不是"不再持有"也不是"未答复"，收到它的位置标记为等待批准，
不据此放行为不再提供；等待超过所设时限而仍有设备未答复时，标记为暂不可得，并记下是哪几台设备未
答复。两者都不是绝对终态：收到更高版本的设备列表且其中出现了尚未答复的设备时，
该位置应退回暂不可得并把新设备计入未答复；无论处于哪一种状态，该位置此后收到其
内容时——包括由本人其他设备同步而来的——系统都应接受并应用它，而不是按重复丢弃。
两种情形都放行应用游标、都在界面上标明原因与它所依据的设备列表版本。这类恢复用
的控制消息不占用被请求作者的消息序号，也不得排在它们要解除的缺口之后。

<!-- tao:field acceptance -->
**验收：** 被请求用户与请求方本人的其他全部未吊销设备都删除某条消息后，请求方逐一收到各设备签名可验证的
声明，该位置标记为不再提供，聊天会话继续应用其后的消息；其中一台设备长期离线
时，超过时限后该位置标记为暂不可得，聊天会话同样继续，界面标明是哪台设备未
答复；该设备随后上线并提供内容时，该位置转为已应用且不产生重复；已标记为不再
提供之后，收到一份更高版本的设备列表且其中有未答复的新设备时，该位置退回暂不
可得；已标记为不再提供的位置，其内容随后由本人另一台设备同步到达时仍被接受并
应用；伪造的、签名验证不通过的同类声明被忽略；在该消息本身尚未到达时投递这些
声明，声明仍能被处理而不是排在缺口之后。

<!-- tao:field source -->
**来源：** 消息严格按序应用且不得跳过，所以一条永远拿不到的消息会让整个聊天会话永久停在
那里。既然用户可以删除自己发出的消息，这种情况就是必然会发生的，不是异常。

由各设备用自己的设备私钥签名，而不是由用户私钥签名：用户私钥只存在于用户指定
的设备上，要求用它签名，等于让多数设备答不了对自己已删消息的重发请求。而安全
性不因此下降——要伪造放行，攻击者需要凑齐双方设备并集中全部未吊销设备的签名，而
双方设备列表分别由各自用户私钥签名。

必须同时给出收不齐时的出路，否则"等全部设备答复"本身就成了新的永久等待——
一台长期不开机的设备足以让对方的聊天会话卡死。所以超时按暂不可得放行，并且
这个放行是可逆的：那台设备终究上线时，内容应当被补上而不是被永久挡在外面。

这类控制消息还必须能越过缺口被处理。如果把它们放进同一条作者日志并占用序号，
它们就会排在自己要解除的那个缺口之后，形成一个谁也打不开的循环。
```

```{req} 删除保留消息标识并覆盖内容
:id: REQ_20260918_F9J932YWK907YPY7
:status: proposed

删除一条消息时，系统应保留该消息的标识与排序所需的信息，并覆盖其内容，使内容

<!-- tao:field acceptance -->
**验收：** 用正确的密钥打开本地数据库之后检索该消息的原文，在消息表、全文索引以及任何

<!-- tao:field source -->
**来源：** 保留内容只加一个删除标记，等于没有删——设备被取得时内容仍然在那里，而这正是

等于没有验收。
```

```{req} 删除尚未送达的消息只停止本设备的重传，须告知其边界
:id: REQ_20260918_SR68DSXCX4S5TZ3R
:status: proposed

如果用户删除一条自己发出但尚未确认送达的消息，则系统应停止从本设备重传它，
并在执行删除时说明：本设备不再提供这条消息；对方可能已经收到而只是确认丢失；
本人其他尚未同意该删除指令的设备仍可能应其请求提供它。

<!-- tao:field acceptance -->
**验收：** 在对方离线期间发送并删除一条消息，且本人其余设备均已同意该删除指令时，对方
上线后不再收到它；存在尚未同意的其他设备时，对方仍可能取得该消息，而删除确认
界面在所选范围包含未确认送达的消息时已说明这一点并给出其条数。

<!-- tao:field source -->
**来源：** 删除的直觉是"清理我这边的记录"，但对一条还没送出去的消息，它同时取消了一次尚未
完成的投递。这两种后果差别很大，用户应当在按下去之前就知道自己正在做哪一件。

但承诺只能说到这里为止。"对方永远收不到"是做不到的：删除指令要每台设备各自
同意，尚未同意的设备仍持有原文并会应重发请求提供它；而且没有收到确认并不等于
对方没有收到，确认本身也可能丢失。把一个做不到的保证写给用户，他会据此判断
敏感内容是否已经暴露，而这个判断会是错的。
```

```{req} 存储失败必须报告为失败
:id: REQ_20260918_R5JVF7M78YZQKN8H
:status: proposed

如果本地存储的读取或写入失败，则系统应把该操作报告为失败，不得以"没有数据"

<!-- tao:field acceptance -->
**验收：** 注入一次存储故障后，界面出现明确的失败提示，且未发生任何依赖该结果的后续动作——

<!-- tao:field source -->
**来源：** 本地存储是消息的唯一副本，没有中心服务可以在下一次请求时纠正一个错误的答案。
把"读不出来"说成"没有"，下游会据此创建、跳过、从零开始或删除，而这些动作往往
```

```{req} 接收、落盘与重发一律受速率与体积上限约束
:id: REQ_20260918_0FAYS8R0Z7A9WF3Q
:status: proposed

系统应对单条消息的大小、单位时间内接收的消息数量、单位时间内的落盘量、重发与
通道重建的频率，以及单个对端可占用的本地存储分别设定上限；这些上限同样适用于
已建立关系的联系人，取值应足够宽松，不影响正常聊天的速度与节奏。超出上限的
输入应被拒绝，且不得导致存储无界增长或应用不可用。当一个已建立关系的联系人
触发上限时，系统应告知用户是哪个对端、触发了哪一项上限、该聊天会话因此暂停
接收，并提供至少一种当场可执行的恢复动作；恢复之后应按序补齐被拒绝的部分，
不得把这段表现为对方沉默。

<!-- tao:field acceptance -->
**验收：** 以正常人聊天的最快节奏持续收发，不触发任何上限；以远超该水平的速率与体积持续
投递，应用保持可用、其他聊天会话不受影响，被拒绝的数量在诊断信息中可见，本地
存储与落盘量的增长受限于所设上限；让一个正常联系人的占用达到存储上限，界面
给出上述告知与至少一种恢复动作，执行该动作后被拒绝的消息按序补齐。

<!-- tao:field source -->
**来源：** 用户明确要求不得出现导致拒绝服务的实现缺陷。已建立关系的联系人同样需要受限：
他本来就能向本机投递数据，而拉黑只有在用户已经察觉之后才起作用。上限覆盖到
落盘而不只是接收，是因为真正的瓶颈通常在磁盘而不在网络；覆盖到重发与重建，
是因为这两件事本身就是可以被诱导反复触发的动作。

必须同时写明恢复路径，否则这条为防拒绝服务而设的机制会在正常使用下自己制造
一个不可自愈的停滞：被拒绝的是正常联系人的合法消息，而消息不得跳过、系统又
不得自动清理，于是应用游标永久停在缺口处，外观还与对方沉默一模一样。
```

## 待确认事项

- 草稿是否跨设备同步，未纳入当前需求。
- 各项时限与上限的具体数值：接收方等待多久才请求重发、缓冲多少条、发送方等待多久
  才兜底重发、通道重建的频率上限、告知用户之前等多久，以及单条消息大小、接收与
  落盘速率、单对端存储的上限。这些都需要在设计阶段结合实测确定；当前只承诺它们存在，
  且正常聊天不会触发。
- 各设备历史视图不一致带来的其他影响。删除指令逐设备确认意味着同一个用户在不同
  设备上看到的历史可以不同，这已经由"重发按并集提供"覆盖；但同一个搜索词在不同
  设备上会给出不同结果，是否需要让用户看出"这台设备上删除过消息"，留待有实际
  使用反馈后决定。
- 覆盖内容能做到什么程度。加密数据库的行更新未必立即抹掉旧字节（预写日志、空闲页
  可能仍持有它们），因此当前的验收只要求按内容检索不到原文，而不是承诺物理不可恢复。
  是否需要额外的清理动作、代价多大，在设计阶段核实存储层的实际行为后确定，不要
  在此之前把它说成已经做到。
- "不再提供"声明的放行细节：放行之后那段缺失在界面上如何呈现，以及它所依据的设备
  列表版本如何展示给用户。签发主体（各设备用自己的设备私钥）与版本绑定已经写进
  需求，这些是它的落实方式。
- 移动端的推送与免打扰策略留待移动端阶段确定；桌面端的未读与通知行为属于本增量，
  见[界面与通知](app-shell.md)。
- 以下数值统一在设计阶段结合实测确定：消息自称时间与本机时间相差多少算「明显
  矛盾」、等待多久才在界面上标明正在获取、收集不再提供声明等待多久后转为暂不可得、
  以及通道重建各项时限。这些时限不只是体验参数——每一个都是形式化模型里的一个
  可触发动作，它们的存在与有界性要在模型中显式表达，不能假定等待终会结束。
