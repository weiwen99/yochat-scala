# 隐私与防护

<!-- tao:section scope -->
## 目标与边界

本篇界定使用 YoChat (有聊) 时用户实际暴露了什么、系统对此承担什么告知义务，以及
系统对滥用与资源耗尽的防护。它覆盖跨能力的承诺，各能力内部的安全要求写在各自篇中。

范围内：中转设施与对端可观察到的信息；在线状态的可见性；发现信息的内容边界；陌生
对端的连接资源上限；失败响应的对外边界与失败信息的对内边界；诊断输出的内容边界；
当前连接方式的可见性。

范围外：消息内容的加密见 [聊天会话与消息](messaging.md)；本地静态加密与密钥保管见
[用户与设备](users-and-devices.md)；关系层面的过滤见 [好友与通讯录](contacts.md)。

交付边界：本篇全部需求属于首个交付增量。

<!-- tao:section terms -->

本篇使用的中转、直接连接、发现信息、用户公钥、设备公钥等术语，定义见

## 需求

```{req} 内容与参与者对中转设施不可读
:id: REQ_20260918_P7X1QGZCYA41GAQT
:status: proposed

系统应使消息内容对任何中转基础设施不可读。中转设施能够观察到的，限于**通信双方的
设备端点标识**、连接与投递发生的时间、每次投递的字节数与帧数，以及本机连接中转时
使用的网络地址、客户端支持的中转协议版本，以及设备证明自己拥有该端点的签名；除这些之外的任何信息——包括消息内容、其解密所需的任何材料，以及
**用户层的身份与聊天会话的成员名单**——均不得对中转可读。

这里可见的是**设备**端点标识，它在本产品中的定位等同于网络地址（见术语表）：中转由此
知道哪两台设备之间有流量，但不知道它们属于谁——用户公钥不在中转可见的范围内。

由实测确定的**已接受的限制**，单独记明并须如实告知：**消息条数与内容长度对中转可见**
（中转按帧计数与计字节，这是转发本身的需要）。本条承诺不再声称这两项不可读。用户于 2026-10-30 同意将协议版本与端点认证签名也作为已接受的限制；它们用于协议协商与端点认证，不包含用户公钥或消息解密材料。

<!-- tao:field acceptance -->
**验收：** 在中转路径上捕获的数据不含明文正文、不含任何解密材料，也不含用户公钥或聊天
会话的成员名单；可被观察到的字段范围与告知给用户的清单一致，不多不少；核对的对象是
中转协议解封后的字段，而不只是链路抓包。

<!-- tao:field source -->
**来源：** 这是 YoChat 承诺的核心，也是用户选择这类工具的原因。但承诺要写得住：投递本身
需要知道送到哪里，因此目的端点标识必然对中转可见，这不是内容加密能隐藏的东西。
把它写成"参与者标识不可读"，是承诺了一件所选传输机制并不提供的事。

历史本机实测补齐了原先写作"待核实"的那一半：**来源端点标识同样可见**——每个客户端
必须用自己的设备私钥向中转认证才能收发，中转的访问控制接口直接拿到该标识；字节数与帧数
同样可见。原实验已退役，固定源码出处、上游版本及当前回归覆盖边界见
[架构中的中转观察依据](../engineering/architecture.md#DOC_20260918_94F65AR6A6WAQ9QM--contracts)。
换一把临时密钥连中转不能消除投递所需的设备标识，不能以此声称隐藏通信双方。
```

```{req} 实际暴露的信息须在使用前如实告知
:id: REQ_20260918_Q0MQBNAVS1TB1PBW
:status: proposed

系统应在用户添加第一个联系人之前，一次性说明使用中实际会暴露的信息：中转服务
可以观察到连接与投递发生的时间、**通信双方的设备端点标识**（因此也知道哪两台设备之间
有往来）、每次投递的字节数与条数，以及本机连接中转时使用的网络地址；与本机建立直接
连接的对端可以得知本机的公网地址；联系人可以看到本人全部设备的设备公钥与设备别名。
说明应一并讲清这些是**设备**层的信息：中转据此不能得知设备属于谁，用户公钥不在其
可见范围内。

<!-- tao:field acceptance -->
**验收：** 首次添加联系人的流程中出现该说明；说明的每一条与实现的实际行为一致，不包含
实现未能提供的保护。

<!-- tao:field source -->
**来源：** 用户要求不得发生数据泄漏。点对点模型能保护内容，保护不了"谁在什么时候连了谁"，
也保护不了设备公钥——后者是联系人拒收已吊销设备消息所必需的，而中转要把字节送到
正确的一端，也必须读到作为地址的那个端点标识。不说清楚，用户会在错误的预期下使用
它；这条清单与隐私承诺里"中转能观察到什么"必须逐字对得上，否则那条需求的验收
无法通过。
```

```{req} 在线状态对持有设备公钥的人可见
:id: REQ_20260918_386RMXBPWJYEXT9P
:status: proposed

系统应说明：持有某台设备的设备公钥的人可以据此查询该设备的在线状态；这是点对点
寻址机制的固有性质，YoChat 不提供隐藏在线状态的选项。仅持有用户公钥不足以做到
这一点。

<!-- tao:field acceptance -->
**验收：** 该说明出现在生成邀请与首次添加联系人的流程中；系统不提供任何声称能隐藏在线
状态的开关；用户公钥本身不能被用来查询任何设备的在线状态。

<!-- tao:field source -->
**来源：** 设备通过公开的发现机制被寻址，可用的中转入口数量也很有限，因此在线与否可以被
任何持有设备公钥的人查到。把它写成一个可关闭的选项会是一个做不到的承诺。这条
与用户公钥的区分是实际的：它决定了生成邀请（必须给出设备公钥）与应答邀请（不必）
的暴露程度根本不同，用户据此判断把邀请贴到哪里、以及该由谁来发邀请。
```

```{req} 发现信息不发布直接地址
:id: REQ_20260918_QZGW3CN8BHBB0F6N
:status: proposed

系统在可被第三方查询的发现信息中不得发布本机的直接网络地址。

<!-- tao:field acceptance -->
**验收：** 以本人的标识查询发现记录，其中只含中转入口，不含本机的直接地址。

<!-- tao:field source -->
**来源：** 在线状态藏不住，网络位置则不必一并送出去。仅仅持有一个标识，不应当就能被动地
得到用户的网络位置。
```

```{req} 陌生对端的资源上限
:id: REQ_20260918_FBGYS6FJ6X3GHEQ4
:status: proposed

系统应在进行握手、分配大缓冲与任何密码学处理之前，对未建立关系的来源设置一个
全局准入预算，覆盖并发连接数、握手速率、待处理任务数与总内存；在此之上再叠加
按对端的限额。超出预算的连接应在昂贵处理发生之前被拒绝，且系统应为已建立关系
的联系人保留一份不被陌生来源挤占的容量。

<!-- tao:field acceptance -->
**验收：** 以高并发、且不断更换身份的方式从大量陌生用户持续发起连接与握手并投递畸形应答，
应用保持可用，总内存与待处理任务数受限于所设预算，已建立关系的联系人的消息
收发延迟不显著变化。

<!-- tao:field source -->
**来源：** 标识可能被泄漏或被扫描到，任何人都可以尝试连接。用户明确要求不得出现导致拒绝
服务的实现缺陷，而这是最容易被触发的一条路径。预算必须是全局的并且设在昂贵
处理之前：攻击者可以不断更换身份，使每个身份都不超过按对端的限额，而握手、
解密与验签的总开销照样把机器压垮——那时数据库一点没长，应用却已经不可用。
```

```{req} 对未获授权的请求不产生响应
:id: REQ_20260918_MXHYRG96W0VKB031
:status: proposed

系统不得对来自未建立关系的对端、已被拉黑的对端或指向不存在目标的请求产生任何
YoChat 应用层出站响应；向用户展示的失败信息不得包含密钥材料或其他联系人的标识。
这里的静默不涵盖 iroh 的传输行为：QUIC 握手、ACK、关闭等传输包仍可能存在，且
连接结果与时序可能不同。产品应明确告知这些差异，不承诺通过传输行为无法探测关系状态。

<!-- tao:field acceptance -->
**验收：** 上述三种情形均不产生 YoChat 应用层出站数据（含拒绝、送达确认和错误回执）；
结合应用层发送记录和抓包区分传输包，记录握手、ACK、关闭及其差异，核对产品告知可见；
遍历全部失败路径，展示给用户的文案不含上述内容。

<!-- tao:field source -->
**来源：** 在线状态本来就可见，因此一条可区分的拒绝响应只会额外把"你属于哪一种"这个答案
送出去，让拉黑与关系状态变成可批量探测的。应用层不回可避免额外的显式拒绝信号；
用户于 2026-11-01 选择保留 iroh，并如实告知传输层差异，不将应用层静默扩称为传输层不可区分。
```

```{req} 诊断默认不记录内容
:id: REQ_20260918_DVFN7QEAWP32QD9G
:status: proposed

系统在默认配置下不得把消息正文、联系人名称或用户公钥写入日志；提高日志级别的
入口应明确告知这些内容可能被记录。

<!-- tao:field acceptance -->
**验收：** 以默认级别完成一次完整流程，日志中不含上述内容；提高日志级别的入口带有该告知。

<!-- tao:field source -->
**来源：** 用户会把日志直接贴进问题报告。默认记录内容，等于把一条默认开启的泄漏通道交给
最愿意配合排查的那批用户。
```

```{req} 当前连接方式对用户可见
:id: REQ_20260918_377PNHQWJ8PGCN80
:status: proposed

用户应能看到每个聊天会话当前实际使用的连接方式是经中转还是直接连接，并随实际
变化更新。

<!-- tao:field acceptance -->
**验收：** 在强制经中转与允许直接连接两种条件下，界面分别显示对应的连接方式，且在连接
方式变化后的可接受时延内更新。

<!-- tao:field source -->
**来源：** 告知说明的是可能性，用户还需要知道此刻实际是哪一种，才能判断要不要在这条链路
上说某些话，或者换一个时间再联系。
```

## 用例与性质

```{uc} 陌生对端高并发下应用保持可用
:id: UC_20260918_G6816V452C2ZEFE8
:status: proposed
:verifies: REQ_20260918_FBGYS6FJ6X3GHEQ4

<!-- tao:field given -->
**给定：** 一台运行中的设备已有若干正常联系人；攻击方持有该设备的标识，并可以从任意多个陌生用户发起连接与握手。

<!-- tao:field when -->
**当：** 攻击方以远超正常水平的并发与速率持续发起连接与握手。

<!-- tao:field then -->
**则：** 应用保持可用，内存占用受限于所设上限，正常联系人的消息仍能收发；被拒绝的连接数量在诊断信息中可见。
```

```{uc} 三种未获授权的请求都得不到应用层响应
:id: UC_20260918_21V7YHFYJQNNR090
:status: proposed
:verifies: REQ_20260918_MXHYRG96W0VKB031

<!-- tao:field given -->
**给定：** 存在三种情形：目标不存在、目标存在但已拉黑发起方、目标存在但与发起方没有关系。

<!-- tao:field when -->
**当：** 发起方分别在三种情形下尝试发送消息，结合应用层发送记录与抓包区分应用数据和传输包。

<!-- tao:field then -->
**则：** 三种情形均未收到 YoChat 应用层响应，包括拒绝、送达确认和错误回执。记录实际传输包及连接结果、时序差异；产品明确告知应用层静默的边界，不宣称这些传输差异不可用于探测关系状态。
```

```{uc} 默认日志不含可识别内容
:id: UC_20260918_CVCBC3MVS9F6DYBV
:status: proposed
:verifies: REQ_20260918_DVFN7QEAWP32QD9G

<!-- tao:field given -->
**给定：** 以默认配置启动应用。

<!-- tao:field when -->
**当：** 完成一次包含添加联系人、收发消息与搜索的完整流程，并检查全部日志输出。

<!-- tao:field then -->
**则：** 日志中不含消息正文、联系人名称与用户公钥；提高日志级别的入口带有会记录这些内容的说明。
```

<!-- tao:section questions -->
## 待确认事项

- 是否提供"仅经中转、不暴露本机地址"的可选模式，取决于所选网络库是否允许在运行时
  或构建时关闭直接连接。在核实该能力确实可得之前，本篇不把它写成需求；设计阶段
  核实后再决定是纳入还是明确声明不提供。
- 是否对已建立关系但尚未通过安全码比对的联系人限制直接连接，取决于同一项核实结果。
- 具体的连接数、握手速率、内存预算与为已建立关系的联系人保留的容量，在设计阶段
  结合实测确定；连接方式变化后多久之内必须更新显示，同样归入该清单。
