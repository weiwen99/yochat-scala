# 用户与设备

<!-- tao:section scope -->
## 目标与边界

本篇界定 YoChat (有聊) 中，一个人如何在没有账号、手机号与服务器注册的前提下拥有
一个可恢复的身份，如何在自己的多台设备上使用它，以及本地数据在设备落入他人之手
时的保护。

范围内：用户的创建与恢复；用户私钥的持有范围与同步；设备的加入、吊销与设备列表；
历史向新设备的可选同步；常在线设备；设备别名与用户别名；应用锁与本地静态加密；
密钥材料的保管边界。

范围外：与他人建立关系见 [好友与通讯录](contacts.md)；消息的传递与顺序见
[聊天会话与消息](messaging.md)；网络层实际暴露的信息见
[隐私与防护](privacy-and-safety.md)。

交付边界：本篇全部需求属于首个交付增量，验收平台为 macOS、Windows、Linux。移动端
不在本增量内，但本篇不得引入任何仅桌面成立的假设。

<!-- tao:section terms -->
## 术语

本篇使用的用户、用户公钥、用户私钥、设备、设备公钥、设备列表、设备吊销、常在线
设备、应用会话、应用锁、恢复短语、历史同步、用户私钥同步、设备别名、用户别名等
术语，定义见[项目术语](../glossary.md)。

<!-- tao:section requirements -->
## 需求

```{req} 用户是本机生成的一对密钥
:id: REQ_20260918_4DYMP7NVJDKNPTKR
:status: proposed

系统应把一个用户表示为在本机生成的一对用户密钥，不要求手机号、邮箱、用户名或
任何服务器端注册。

<!-- tao:field acceptance -->
**验收：** 在断开网络的全新安装上完成用户创建并进入主界面；创建过程中不产生任何对外
网络请求。

<!-- tao:field source -->
**来源：** YoChat 没有中心服务。没有账号目录，也就没有可以被要求交出、被攻破或被封禁的
一份用户名单。
```

```{req} 恢复短语只在创建时展示并要求确认
:id: REQ_20260918_T1H63J7F3QD0WBBT
:status: proposed

当系统创建新用户时，应展示一次恢复短语，并在用户确认已记录之前不进入主界面；
此后不再主动展示，用户在设置中显式请求且通过应用锁校验后方可再次查看。

<!-- tao:field acceptance -->
**验收：** 创建流程中不确认无法继续；重启后主界面不出现短语；设置中的查看入口要求先输入
应用锁口令。

<!-- tao:field source -->
**来源：** 恢复短语是用户私钥的可书写形式。备份好它，丢掉任何一台设备都还能重新取得签发
设备条目与吊销声明的能力；只有它和全部持有用户私钥的设备一同丢失，这项能力才
真正消失。所以确认用户记下了它，是这个模型里最要紧的一步。但常驻展示会把肩窥、
截屏与录屏都变成泄漏途径。
```

```{req} 恢复短语可打开本机既有数据
:id: REQ_20260918_G2S3MXJ3J0HXYXYP
:status: proposed

当用户在一台已持有本人数据的设备上输入正确的恢复短语时，系统应解开该设备上
既有的本地数据，而不是重建一台空设备。

<!-- tao:field acceptance -->
**验收：** 设置应用锁口令后模拟忘记口令，用恢复短语进入，此前的消息与联系人仍然可读。

<!-- tao:field source -->
**来源：** 忘记口令是常见情况，而本地是消息的唯一副本。若恢复只能得到一台空设备，忘记
口令就等于永久丢失全部历史。
```

```{req} 无可解开数据时恢复为一台新设备
:id: REQ_20260918_VMJVPZMK63123DKH
:status: proposed

系统应按三种情形分别处理：设备上没有本人的既有数据时，建立一台新设备并如实
告知这是新设备而不是恢复出的原设备；有既有数据且能用该短语解开时，打开它；
有既有数据但解不开时，报告无法解开并停下，只有在用户明确选择放弃该数据之后
才建立新设备，且新设备使用独立的数据目录，不得覆盖原有目录。

<!-- tao:field acceptance -->
**验收：** 在干净设备上输入短语得到可用的空设备，界面明确说明这是新设备；在数据存在但
无法解开时（例如输错短语），系统报告无法解开并停下，原有数据目录保持不变；
用户明确选择放弃之后建立的新设备位于另一个数据目录，原目录仍然存在。

<!-- tao:field source -->
**来源：** "恢复本机数据"与"在新设备上启用这个用户"是两种不同的结果，用户对历史的预期
完全不同。把两者混为一谈，用户看到空白聊天会话时无法判断是数据丢了还是本来
就没有。而"解不开"必须单列为第三种：最常见的原因是短语输错了一个词，此时若
直接在既有数据之上建新设备，用户得到的是一个空应用，而本地是唯一的副本。
```

```{req} 设备条目由用户私钥签发，设备列表对联系人可见
:id: REQ_20260918_5A7WDB3CTV03FJTW
:status: proposed

系统应把用户的每台设备表示为一条由用户私钥签发的设备条目，全部条目构成一份
有版本的设备列表；该列表经签名后随关系同步给联系人。日常操作以人为单位：
加好友、拉黑、发消息都以用户为对象，消息寻址到用户并由系统分发到其当前设备。

<!-- tao:field acceptance -->
**验收：** 通讯录与聊天界面均以人为单位组织，不出现按设备拆分的条目；在联系人详情中可以
查看对方的设备公钥与设备别名；本方增删设备后对方无需任何操作即可继续正确收发。

<!-- tao:field source -->
**来源：** 设备公钥在点对点网络中本来就会被通信对方看到，而联系人还需要凭设备列表拒收
已吊销设备发出的消息，所以设备列表是明确公开给联系人的。隐藏它既做不到，也会
让吊销失去作用。把它放在详情里而不是主界面上，是为了让日常操作保持和普通即时
通讯软件一样以人为单位。
```

```{req} 用户私钥只存在于用户指定的设备上
:id: REQ_20260918_R1J6B5CH21YFFP32
:status: proposed

系统应使用户私钥只存在于用户明确指定的设备上。其余设备持有自己的设备密钥对
与用户公钥，足以正常收发消息，但不能把新设备签入设备列表，不能签发吊销声明，也不能
生成邀请与邀请应答（即不能加好友）。

<!-- tao:field acceptance -->
**验收：** 在一台未持有用户私钥的设备上，添加设备与吊销设备的入口不可用并说明原因；该
设备的收发、搜索与通讯录的浏览、备注、拉黑功能不受影响；添加联系人的入口不可用并说明
应在哪台设备上完成。

<!-- tao:field source -->
**来源：** 把用户私钥复制到每一台设备上，等于让任意一台设备的丢失都变成整个用户的失守。
限制在用户挑选的少数设备上，丢一台普通设备只需要吊销它。
```

```{req} 用户私钥同步须在已持有它的设备上发起
:id: REQ_20260918_ZVSZ6JT217MBK53K
:status: proposed

当用户希望另一台设备也持有用户私钥时，系统应要求在一台已持有它的设备上发起
同步，并在两端分别确认。

<!-- tao:field acceptance -->
**验收：** 目标设备上不存在任何单方面索取用户私钥的入口；同步完成后目标设备可以签发设备
条目与吊销声明，且该事件对本人其他设备可见。

<!-- tao:field source -->
**来源：** 与历史同步同样的道理：把这项能力的取得绑定到对一台已有设备的实际控制。它是
便利而不是保险——持有用户私钥的设备全部损坏时，备份好的恢复短语本身就能重新
取得这项能力，所以不需要为了冗余而让更多设备持有它，持有得越少暴露面越小。
```

```{req} 新设备加入必须让其他设备看见
:id: REQ_20260918_H0XN0536A5P1WZVG
:status: proposed

当一台新设备进入设备列表时，系统应向本人其他设备发布加入事件，包含加入时间、
设备别名与设备公钥；其他设备察觉设备列表版本变化而未收到对应加入事件时应告警。

<!-- tao:field acceptance -->
**验收：** 设备 B 加入后，设备 A 在下次连通时显示该加入记录；使用一个刻意不发布加入事件的
客户端加入时，设备 A 仍然因设备列表版本变化而告警。

<!-- tao:field source -->
**来源：** 持有恢复短语的人可以签出合法的设备条目，这在没有中心服务的前提下无法阻止——
没有第三方能拒绝一个用户私钥的合法签名。既然拦不住，就必须让本人看得见。
```

```{req} 恢复短语的真实后果须在生成时说明
:id: REQ_20260918_E6NXMN0ABVQD7NSN
:status: proposed

当系统展示恢复短语时，应同时说明：持有该短语的人可以以这个用户加入设备、收发消息、
吊销其他设备，**并可以以你的名义发出邀请与应答、与陌生人建立联系人关系**；但默认取不到
加入之前的历史，且加入行为会被其他设备看到。

<!-- tao:field acceptance -->
**验收：** 创建流程中出现该说明，其中每一条分别由本篇的默认历史范围、历史同步与加入事件
需求保证。

<!-- tao:field source -->
**来源：** 恢复短语就是用户私钥。与其宣称一道其实拦不住的批准流程，不如把它的能力与边界
如实说清楚，用户才能据此决定怎么保管它。
```

```{req} 新设备默认只能读取加入之后的消息
:id: REQ_20260918_V6NGSKDD26FWGEZ4
:status: proposed

新设备应默认只能读取其进入设备列表之后产生的消息。

<!-- tao:field acceptance -->
**验收：** 设备 A 已有若干历史；设备 B 加入后该聊天会话在 B 上为空，此后双方新消息在 A、B
上内容与顺序一致。

<!-- tao:field source -->
**来源：** 用户选择默认不搬历史。这同时把一台新设备——无论是本人添加的还是短语泄漏导致
的——能接触到的数据限制在它加入之后。
```

```{req} 历史同步必须在持有历史的设备上发起
:id: REQ_20260918_9G1QW692AHHVT4JX
:status: proposed

当用户希望某台设备取得其加入之前的历史时，系统应要求在一台已持有该历史的设备
上发起同步，并由用户选择同步的聊天会话范围。

<!-- tao:field acceptance -->
**验收：** 新设备上不存在任何单方面拉取历史的入口；在持有历史的设备上发起后，新设备收到
所选聊天会话的历史。

<!-- tao:field source -->
**来源：** 把"取得历史"绑定到对一台老设备的实际控制，使仅仅持有恢复短语不足以取得历史。
这是默认不搬历史这个选择在安全上的实际价值所在。
```

```{req} 历史同步可中断续传且不产生重复
:id: REQ_20260918_KAN0STW3H8EWZB99
:status: proposed

如果历史同步在完成前中断，则系统应在下次连通时从中断处继续；完成后目标设备上
该范围的消息内容与顺序与源设备一致，且不产生重复。

<!-- tao:field acceptance -->
**验收：** 同步一万条消息，中途断网并重启双方，恢复后目标设备该范围的消息集合与源设备
逐条一致，无重复、无缺失。

<!-- tao:field source -->
**来源：** 历史可能很大，而设备间传输不可靠。一次中断就要全部重来会让这条路径在真实数据
规模下无法使用。
```

```{req} 吊销设备使其消息被拒绝，用户公钥不受影响
:id: REQ_20260918_9YNQV83FP0G2FV42
:status: proposed

当用户吊销一台设备时，系统应由一台持有用户私钥的设备签发吊销声明，声明中携带
被吊销的设备公钥与签发时间戳，并由用户私钥签名；该声明随设备列表分发给本人其他
设备与全部联系人。收到该声明的设备应拒绝被吊销设备此后发出的消息，并使其无法
解密此后产生的消息。用户公钥不因此作废。

<!-- tao:field acceptance -->
**验收：** 吊销设备 B 之后由设备 A 发送消息，B 无法解出；以 B 的设备密钥构造的消息被已知
该吊销的设备拒绝；吊销声明的签名可用该用户的用户公钥验证，篡改其中的设备公钥
或时间戳后验证失败；本人与联系人的其余通信不受影响，安全码不变。

<!-- tao:field source -->
**来源：** 设备丢失、被盗或不再使用时，用户需要一个真正切断它的动作。让吊销作用在设备
公钥而不是用户公钥上，用户不必因为丢一台设备就重建全部关系、重新比对全部安全码。
```

```{req} 吊销的判定依据本地接收时间，不依据消息自称的时间
:id: REQ_20260918_PYQVKZPN5ZS9HWSA
:status: proposed

接收方判断一条消息是否应因设备吊销而被拒绝时，应依据该消息在本机的接收时间与
本机收到吊销声明的时间，不得依据消息自称的创建时间。收到某台设备的吊销声明
之后，系统应拒绝该设备此后到达的一切消息，无论其自称的创建时间为何；对于在
收到声明之前已经接受的、来自该设备的消息，系统应标记它们来自已吊销的设备，
且其自称时间无法核实。

<!-- tao:field acceptance -->
**验收：** 用一台被吊销设备的设备私钥构造一条自称创建时间早于吊销时间戳的消息，在接收方
已收到吊销声明之后投递，该消息被拒绝；接收方在收到声明之前已接受的该设备消息
仍然可读，但在界面上带有上述标记。

<!-- tao:field source -->
**来源：** 消息的创建时间是发送设备自己写上去的，一台已被吊销但仍持有设备私钥的机器可以
把它设成吊销之前的任何时刻，以此欺骗还没收到吊销声明的联系人。本机的接收时间
和本机收到声明的时间则是本机自己观察到的，不受对方摆布，所以判定必须建立在
这两个时间上。至于收到声明之前已经接受的那些消息，事后无法分辨真伪，唯一诚实
的做法是把这个不确定性标出来交给用户判断，而不是假装能判定。
```

```{req} 吊销不撤销该设备已持有的数据
:id: REQ_20260918_214C96FXNAE7W0G6
:status: proposed

系统应在用户执行吊销时说明：吊销不会删除该设备上已有的本地数据，也不能撤销它此前
已经解密过的消息；尚未收到吊销声明的联系人在收到之前仍会接受该设备的消息；本人其余
设备不再受理该设备签发的未过期邀请，需要重新生成，但那些邀请的一次性私钥仍在被吊销的
设备上、无法销毁，因此应撤下已经张贴出去的邀请文本。

说明还应区分两种情形：**若被吊销的设备不持有用户私钥**，吊销之后它不能再以本人名义结识
新的人；**若它持有用户私钥**，YoChat 无法阻止它继续以你的名义发出邀请与应答、也无法替你
通知任何人——那等同于恢复短语泄漏，吊销处理不了。

<!-- tao:field acceptance -->
**验收：** 吊销的确认界面包含该说明，且区分被吊销设备是否持有用户私钥两种情形；系统不提供
任何声称能远程擦除的入口；吊销之后，本人其余设备把该设备签发的未过期邀请显示为不再受理，
并提示重新生成与撤下张贴。

<!-- tao:field source -->
**来源：** 没有中心服务，也就没有远程擦除能力，吊销声明也只能随连接逐步传开。把做不到的
事写成承诺，会让用户在设备被盗这种高风险时刻做出错误判断。

连带作废那台设备签发的邀请，是因为那些邀请的一次性私钥就在它上面；而它已经不被
信任，不会配合删除。至于"被吊销的设备还能不能以本人名义去认识新的人"——**不持有用户
私钥的设备不能**，因为邀请与应答都由用户私钥签名，见[好友与通讯录](contacts.md)的设备
授权需求；**持有用户私钥的设备仍然能**，它与掌握恢复短语的人能力相同。把后一半藏起来，
用户会在设备被盗这个最高风险的时刻作出错误判断。
```

```{req} 用户私钥全部丢失时的处理
:id: REQ_20260918_P2MVJR9GAY96T95W
:status: proposed

如果用户既没有恢复短语，也不再拥有任何持有用户私钥的设备，则系统应说明：无法
再签发设备条目或吊销声明，也无法通过 YoChat 向联系人发出任何可被验证的声明，只能
通过其他渠道告知联系人。

<!-- tao:field acceptance -->
**验收：** 在该状态下相关入口不可用并给出上述说明；系统不提供任何声称能替用户通知联系人
的功能。

<!-- tao:field source -->
**来源：** 此时这个用户发出的任何声明都无法与冒充者区分，YoChat 没有能力替他通知任何人。把
这件事说清楚，用户才会明白备份恢复短语保护的究竟是什么：不只是找回历史，而是
保住对自己这个用户的控制权。
```

```{req} 本地数据静态加密
:id: REQ_20260918_ZTSEXMZQ2VHS21R6
:status: proposed

系统应把本地的消息、联系人、设备列表与密钥材料加密存储，在未通过应用锁或恢复
短语的情况下不得读出其内容。

<!-- tao:field acceptance -->
**验收：** 在未解锁状态下检查应用数据目录，不存在可直接读出消息正文、联系人名称或密钥
材料的文件。

<!-- tao:field source -->
**来源：** 设备丢失是最常见的泄漏途径。把文件放在应用目录本身不提供任何保护。
```

```{req} 应用锁是安全边界而不是界面切换
:id: REQ_20260918_B9Y4E73VMQ8RS99X
:status: proposed

当用户锁定应用或应用重新启动时，系统应要求口令。锁定动作本身应立即使当前应用
会话失效，此后返回的、属于该会话的结果一律丢弃——不论此时是否已经重新解锁。
锁定后不得残留上一个应用会话的任何数据可达。

<!-- tao:field acceptance -->
**验收：** 在一次搜索请求返回之前锁定，该结果在仍处于锁定状态时返回，不被显示也不写入
任何界面状态；重新解锁后它同样不出现；在同一台机器上切换到另一个用户或另一个
设备实例后，同样不出现上一个实例的聊天会话内容、草稿、搜索词或联系人。

<!-- tao:field source -->
**来源：** 同一台设备可能被另一个人拿到，下一个解锁的人未必是同一个人。一次异步请求从
发出到结果返回之间有一段窗口，用户可以在这段窗口里做任何事，包括锁定；结果
回来时若再去读当时的界面状态，就会把上一段时间的私密内容显示给下一个人。

失效必须发生在锁定的那一刻，而不是下一次解锁的时候。否则锁定之后、再次解锁
之前返回的那些结果，其所属会话看上去仍然有效，照样会落到界面上——而那正是
屏幕无人看管的一段时间。
```

```{req} 空闲超时自动锁定
:id: REQ_20260918_YQW27DXZJSHAR0Z0
:status: proposed

系统应在用户空闲超过可配置的时长之后自动锁定，该行为默认开启；自动锁定与用户
主动锁定走同一条路径，产生同样的效果。

<!-- tao:field acceptance -->
**验收：** 解锁后保持无操作直到超过所设时长，应用自动进入锁定状态，界面不再显示任何聊天
内容；此时返回的在途请求结果同样被丢弃；用户可以调整时长，也可以关闭该行为，
关闭时界面说明其后果。

<!-- tao:field source -->
**来源：** 本篇把"本地数据在设备落入他人之手时的保护"写进了自己的范围，而只有主动锁定与
重启两个时机，覆盖不了最常见的那一类现实泄漏——人走开五分钟。共用一台机器在
本篇里已经被当作真实使用方式，这条就更不能少。
```

```{req} 密钥材料不进入日志与崩溃报告
:id: REQ_20260918_865PCSHV46Q4X2XF
:status: proposed

系统不得把恢复短语、用户私钥、设备私钥、会话密钥或本地数据库密钥写入日志、

<!-- tao:field acceptance -->
**验收：** 以最高日志级别完成一次完整的收发流程，日志中不含上述材料；构造一次进程崩溃，

<!-- tao:field source -->
**来源：** 用户明确要求不得发生密钥泄漏。日志与崩溃报告是最容易被忽略、又最容易被原样

```

```{req} 常在线设备
:id: REQ_20260918_GBC9KZAACYZ1RHYZ
:status: proposed

系统应支持把用户自己的一台设备作为常在线设备长期运行，用于在其他设备都离线时
替本人接收消息；该职责不要求设备有界面，但应能在无人值守的情况下持续运行。
系统应在用户设置常在线设备之前一次性说明：该设备持有可解密其可见范围内全部
消息的密钥材料，因此应当部署在用户自己控制的机器上。

<!-- tao:field acceptance -->
**验收：** 该设备在其他设备全部离线期间接收并保存消息，其他设备上线后取得这些消息；有
界面与无界面两种形态都能承担该职责；部署说明与设置界面均包含上述说明。

<!-- tao:field source -->
**来源：** 用户选择用一台常在线的设备解决对方发消息时本人不在线的问题。能否解密是这条
路成立的前提，也是它真正的代价；有没有界面与这个职责无关，一台常开的电脑和
一个部署在自己机器上的无界面实例同样胜任。
```

```{req} 设备别名由持有者设置并对联系人可见
:id: REQ_20260918_VWTKG0AZG2084W8K
:status: proposed

用户应能为自己的每台设备设置别名；该别名随签名的设备列表同步给联系人。联系人
可以看到对方设备的别名与设备公钥，但不能修改它。

<!-- tao:field acceptance -->
**验收：** 在设备上改名后，本人其他设备与联系人在下次连通后看到新名字；界面不提供修改
他人设备别名的入口。

<!-- tao:field source -->
**来源：** 设备别名的用途是让人认出"这是哪一台机器"，双方看到同一个名字才有意义。给别人
的设备另起一个只有自己看得见的名字，对任何一方都没有用处。
```

```{req} 用户别名与头像是公开的，只有本人能改
:id: REQ_20260918_Z1P2TGCMD0K4W1XP
:status: proposed

用户应能为自己设置一个用户别名与一张头像，两者随关系同步给全部联系人；头像的
体积应有上限，超出上限的图片应被拒绝或在本机压缩后再使用。只有本人可以更改
这两个属性，联系人不能。当本人多台设备产生同版本、不同有效签名的公开资料时，系统应
提示冲突，由本人选择一份并签发严格更高版本后传播；不得按到达顺序或内容哈希自动选定。

<!-- tao:field acceptance -->
**验收：** 更改自己的别名或头像后，联系人在下次连通时看到新的；两者在本人全部设备间一致；
联系人界面不提供修改对方别名或头像的入口；超过体积上限的头像被拒绝并给出上限值。
两台本人设备离线产生同版本异内容、按相反顺序投递时，两侧均提示冲突；取消选择或重启
不丢失冲突。本人选用一份后，以高于当前已知版本的新签名资料解决冲突；联系人只接受
该有效的新版本，不代替本人选择或签发，迟到的旧版本不能复活冲突。

<!-- tao:field source -->
**来源：** 用户需要一个自己能决定、并且所有联系人都能看到的称呼与形象。两者都是公开的，
用户在设置时应当据此判断要写什么、放什么。头像要有上限，否则它就成了一条可以
向全部联系人推送任意大小数据的通道。
```

```{req} 同一台机器可并存多个用户与多个设备实例
:id: REQ_20260918_RCMJA190DC6RY6DW
:status: proposed

系统应允许在同一台机器上并存多个用户，也应允许同一个用户在同一台机器上并存
多个设备实例。每个实例的消息、联系人、密钥材料与应用锁应完全隔离，任一实例
在未解锁的状态下不得读出其他实例的任何数据。

<!-- tao:field acceptance -->
**验收：** 在一台机器上建立两个用户与同一用户的两个设备实例；从一个已解锁的实例无法解出
另一个实例的任何消息、联系人或密钥材料，各实例使用不同的数据库密钥；解锁其中
一个不使其他任何实例变为已解锁；在实例之间切换时要求重新通过应用锁。

<!-- tao:field source -->
**来源：** 家庭成员可能共用一台机器，这是真实的使用方式。同一个用户的多个设备实例则主要
服务于开发与调试——它让一台机器就能演练多设备同步、历史同步与吊销，而这些行为
没有第二台设备根本无法验证。两者在实现上是同一件事：按实例隔离全部状态。既然
并存是被允许的，实例之间的切换就必须和锁定一样是一道边界，否则隔离只是目录
上的分开。
```

## 待确认事项

- 新设备加入时用什么方式把用户公钥与设备条目带过去（扫码、短码、还是直接输入恢复
  短语），属于交互方案，在设计阶段随可用能力一并确定；本篇只约束结果与告知义务。
- 吊销声明的传播依赖连接，而在联系人收到它之前，被吊销的设备仍然可以冒充。是否
  需要给吊销声明一条独立于聊天的、更积极的传播路径（例如由本人其他设备主动向全部
  联系人推送，或让联系人定期重取设备列表），在设计阶段确定。当前需求只保证收到
  之后的判定是可靠的。
- 头像体积上限的具体数值，以及是否在本机统一压缩到固定尺寸，在设计阶段确定。
- 同一机器上多实例的切换交互（各自独立的窗口，还是一个窗口内切换），以及实例列表
  本身是否需要保护——能看到有哪些实例存在，本身就泄漏了这台机器上有几个人在用。
- **分期决定（用户，2026-09-24）：** 第一期由长期运行的桌面进程承担常在线职责；无界面形态
  （NAS容器、系统服务）及无系统钥匙串时的解锁方式延后。本篇“有界面与无界面两种形态都能承担”
  的需求保留，实施范围与当前结果见[主计划](../plans/2026-09/20260918-yochat-f2f-messenger.md#DOC_20260918_BFV4FCXTMM9MQRDD--verification)。
