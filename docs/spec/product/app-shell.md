# 界面与通知

<!-- tao:section scope -->
## 目标与边界

本篇界定 YoChat (有聊) 桌面端界面的可判定基线：主界面布局、键盘可达性、外观、
大量历史下的可用性，以及用户如何得知有新消息。

本篇只固定能被核对的部分，不规定审美——观感由设计与实现承担，但"做到什么程度算
做到了"必须在这里有据可依。

范围内：主界面布局与键盘可达；浅色与深色外观；十万条量级历史下的可用性；未读计数
与聊天会话排序；桌面系统通知及其内容边界。

范围外：消息本身见 [聊天会话与消息](messaging.md)；移动端的推送与免打扰留待移动端
阶段。

交付边界：本篇全部需求属于首个交付增量，验收平台为 macOS、Windows、Linux。

<!-- tao:section terms -->
## 术语

本篇使用的聊天会话、送达状态等术语，定义见[项目术语](../glossary.md)。

## 需求

```{req} 主界面布局与可达性基线
:id: REQ_20260918_3AEMNVEGME49ZT2R
:status: proposed

应用应提供主流即时通讯软件的布局：聊天会话列表、会话视图与输入区并置，并可打开
联系人与设备的详情。主要操作应可仅用键盘完成；应用应提供浅色与深色两套外观并
跟随系统设置。

<!-- tao:field acceptance -->
**验收：** 逐项核对：从启动到发出一条消息、切换聊天会话、打开联系人详情、发起搜索，全程
不使用指针设备即可完成；切换系统外观后应用随之变化；文字与背景的对比度满足下述可读性基线。

**可读性基线取 WCAG 2.2 AA**：正文与界面文字对背景不低于 4.5:1，大号文字（粗体 18.66px 以上
或常规 24px 以上）与图标、输入框边框一类的非文字界面元素不低于 3:1；深浅两套外观各测一遍。
取这一版而不是自拟一个数：它是各处无障碍法规实际引用的那一版，工具链现成，判定不取决于谁来测。
键盘焦点指示本身也按非文字元素算，同样不低于 3:1——焦点看不见时「可仅用键盘完成」是句空话。

<!-- tao:field source -->
**来源：** 界面质量是用户对本产品最直接的要求之一，而它此前没有任何可判定的承诺——设计
已经据此做了选型，规格里却没有对应条目，等于把一个会被实现阶段悄悄缩水的东西
留在了空中。这里只固定可核对的基线，不规定审美。
```

```{req} 大量历史下仍然可用
:id: REQ_20260918_3TK81N30WS2S6JWB
:status: proposed

在十万条量级的本地历史下，聊天会话的滚动、跨会话搜索与联系人检索应保持可用。

<!-- tao:field acceptance -->
**验收：** 以十万条消息的本地库测量：打开一个聊天会话到首屏可读不超过 500 毫秒；连续滚动时
单帧卡顿不超过 100 毫秒；一次跨全部会话的搜索不超过 1 秒；且内存占用不随滚动持续增长。

<!-- tao:field source -->
**来源：** 本地是消息的唯一副本且默认永久保存，所以历史只增不减，规模问题是必然而不是
极端情况。三个时延阈值取交互响应常用的体验目标，**独立于实测值给出**（未找到同规模客户端的
公开基线）；用户 2026-09-24 确定，实测之后再看是否调整。
```

```{req} 未读与会话列表排序
:id: REQ_20260918_2AD55GM4Z0PTAJXX
:status: proposed

系统应为每个聊天会话维护未读计数，并按最近活动排序聊天会话列表。未读状态应在
用户的全部设备之间同步。

<!-- tao:field acceptance -->
**验收：** 在一台设备上收到消息后，该聊天会话出现未读计数并升到列表前列；在另一台设备上
读过之后，两台设备的未读状态一致。

<!-- tao:field source -->
**来源：** 没有未读标记，用户每次都得逐个点开才知道哪里有新消息。它必须跨设备同步，否则
在手机上读过的消息在电脑上仍然显示为未读，用户会重复检查。
```

```{req} 桌面通知及其内容边界
:id: REQ_20260918_G3JQAH0SXEXVDATA
:status: proposed

系统应在应用未处于前台时，为新消息发出系统通知；用户可以逐个聊天会话地关闭它。
通知是否包含消息正文应由用户选择，默认不包含，仅显示来自谁。

<!-- tao:field acceptance -->
**验收：** 应用最小化时收到消息，系统通知出现并可点击跳转到对应聊天会话；默认设置下通知
文本不含消息正文；关闭某个聊天会话的通知后不再为它发出通知。

<!-- tao:field source -->
**来源：** 一个不打开就不知道有消息的即时通讯软件不成立，而本篇其他需求已经在把通知当作
既有事物使用。默认不含正文与诊断输出默认不记录内容是同一条理由：通知会出现在
锁屏上、会被投屏看到，而用户往往意识不到。
```

## 用例与性质

```{uc} 从通知进入的是消息所属的聊天会话
:id: UC_20260918_KZACP3YFJW0WRWBK
:status: proposed
:verifies: REQ_20260918_G3JQAH0SXEXVDATA, REQ_20260918_DK8P5E0K5GES1T0C

<!-- tao:field given -->
**给定：** 用户打开着聊天会话 X；来自聊天会话 Y 的一条消息触发了系统通知。

<!-- tao:field when -->
**当：** 用户点击该通知。

<!-- tao:field then -->
**则：** 应用切换到聊天会话 Y 并定位到该消息；X 的草稿与滚动位置保持不变。
```

## 实现与验收边界

通知点击、搜索结果及引用跳转按目标消息所属会话打开，不借用此刻选中的会话；
各会话的草稿、引用及视口状态独立。异步打开结束前不能把“已选中”当作内容加载完成，
旧读取/发送回调也不能清空后来编辑的草稿（{need}`UC_20260918_KZACP3YFJW0WRWBK`、
{need}`TASK_20261102_SDC8EBR3BCEG24TQ`）。

规模验收分开观察DOM就绪和真实绘帧。窗口被遮挡、显示器关闭或系统锁屏时，
`requestAnimationFrame`可能停止；未绘帧不能算首屏绘制或连续滚动通过。应用进程RSS
不包含独立WebContent进程；已落盘历史的窗口/搜索结果不能外推网络恢复成本
（{need}`TASK_20260919_0R84ESC1SZ2Y0FEM`）。

macOS键盘焦点是否移动还受系统“全键盘访问”影响。CSS焦点合同、渲染对比度、
真实原生按键及OS前台焦点是不同观察，不能用JS `.focus()`或合成按键替代原生旅程。
系统通知记录器不证明实际系统投递/点击，单机通过也不替代其他平台验收
（{need}`TASK_20260919_0R2EC1M6896HVHT7`、{need}`TASK_20260919_84943YC4AF86ZET8`）。
