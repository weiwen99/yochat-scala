# 发送队列类型化与冻结原件调度

<!-- tao:section scope -->
## 范围与依据

2026-11-20用户要求实现此前讨论的合理目标：发送调度读取结构化的消息类型、候选、目标及状态；最终网络原件只编码一次，在SQLite持久化后原样发送与重试；不为检查队列而反复解析、验签；分类标签不能替代密码认证或当前授权。大原件保持不可变共享，不因新增类型信息复制大对象。

实施起点为`28578dd18db0986c3a2130ca023ae2043dcb1bc9`。该提交仅在无待办反向公告时跳过元数据读取，并未消除未确认期间的反解析。本计划先完成真实生产与恢复路径的类型化切换，再执行[原万条原生验收](20261114-native-acceptance-fixes.md)，不重新打开已完成的[上一轮状态运行时重构](20261117-typed-state-runtime.md)，也不提前开展约定在当前任务之后的[全量SQL审计](20261120-sql-query-efficiency.md)。

<!-- tao:section design -->
## 实现约束

类型事实必须从真实构造、验签后的接收或SQLite恢复边界取得，随同精确原件、候选身份和发送目标原子持久化。调度、重试、重连及反向预密钥维护不得为识别自身队列消息类型而重新解析网络字节。需要兼容的旧持久数据在明确的恢复／迁移边界处理，不能永久保留未分类回退或每次调度补解析；迁移须有界、可重启，失败不能发布部分状态或提前发送。

状态、密钥推进、不可变原件与待发任务仍同事务提交，成功后才出站；相同重试复用相同字节。结构化分类只负责筛选，不能通过伪造类型、候选、目标或旧序号绕过当前同意、设备吊销、引用授权、删除、到期、配额和固定截止。Core继续不依赖具体加密库，不改变线上格式，不引入无界缓存。

按所有权并行实施：Core存储与类型、Protocol真实生产端及消费者、应用调度、模型及验证分别分配文件；共享契约先固定，应用集成只有一个所有者。不并行启动需要独占桌面的原生测试。

## 实际结果与限制

四项实现与定向验证已完成。现有发送任务已经持有目标、授权及共享不可变原件，正文、历史和原生转发分别已有类型化所有者；本次补齐缺失的首次Bootstrap Create关联，不为所有Effect再添加重复枚举。Store格式为64，支持60—63原子升级：精确关联只保存300字节调度事实，恢复标记48字节，不额外复制网络原件。

首次Create的反向公告屏障和类型关联使用同一个收件人选择函数，覆盖普通创建与已认证私有发现两条真实生产入口；原件、队列、关联及恢复完成标记同事务发布。首次集成确实检出了私有发现入口漏记的问题，现已修正生产端，五项原有“ACK前不得发送Create”消费者断言全部通过，没有放宽等待边界。

维护现在只读精确候选、目标及序号，不读取待发JSON或密码状态，更不解析、验签网络帧。旧数据只在一次性恢复边界检查当前会话的单个来源原件；恢复使用固定五秒且受父截止约束的SQL/CPU共同期限、版本CAS及原子完成标记，失败不发布半成品。来源投影只返回固定大小字段，不构造完整缓冲原件或应用消息清单。取消、替换、原件删除／拒绝及来源退役清理关联；分类不授予认证或当前授权。
