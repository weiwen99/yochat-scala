# 项目术语

<!-- tao:section terms -->
## 术语

```{term} YoChat

本产品的名称，中文名是「有聊」。文档与界面以 YoChat 指称它。中文名单独出现时
写成「有聊」，与 YoChat 一起出现时写成 YoChat (有聊)。加标记是必要的：这两个字
在汉语里本身是一个普通词组，不加标记会被读成一句话而不是一个名字。
```

```{term} 用户
:english: User
:avoid: ["身份"]

一个人在 YoChat 中的存在，由一对用户密钥表示，在本机生成，不在任何地方注册。日常操作
都以用户为对象：加好友、拉黑、发消息针对的都是人，而不是他的某一台设备。
```

```{term} 用户私钥
:english: User Private Key

定义一个用户的私钥，恢复短语是它的可书写形式。它只存在于用户明确指定的设备上，
不是每台设备都持有。持有它才能把新设备签入设备列表、签发设备吊销声明、生成邀请与邀请应答（即加好友）。它与恢复
短语一同丢失，就再也无法做这两件事，也无法通过 YoChat 向联系人发出任何可被验证的声明。
```

```{term} 用户公钥
:english: User Public Key

一个用户的公开标识，用来指称这个人、验证其签名、计算安全码。它不是网络地址：
单独持有它连不上任何机器，也查不到任何设备的在线状态，那需要设备公钥。
```

```{term} 设备
:english: Device

一个用户的一台机器。每台设备一定持有自己的设备密钥对与本人的用户公钥，这足以
正常收发消息；是否同时持有用户私钥由用户决定——不持有用户私钥的设备不能生成邀请与
邀请应答，也就不能加好友。
```

```{term} 设备公钥
:english: Device Public Key

一台设备在点对点网络中的地址，作用相当于传统网络里的 IP 地址：持有它就能寻址
到这台设备、查到它的在线状态并尝试连接它。通信对方必然会看到它，联系人也需要它
来判断一条消息来自哪台设备、该设备是否已被吊销。它出现在邀请里，是为了让关系建立之后对方能
投递第一条操作与后续消息——应答不经网络投递，而是由人经渠道复制粘贴回传。
```

```{term} 设备列表
:english: Device List

一个用户当前全部设备条目的有版本集合，由用户私钥签名，随关系同步给联系人。消息
寻址到用户，由系统分发到该列表中的设备；它的版本变化本身就是一个可被观察到的事件。
```

```{term} 设备吊销
:english: Device Revocation

由持有用户私钥的设备签发的一条声明，使某台设备的设备公钥不再被接受。用户公钥不
因此作废，安全码也不变。收到该声明的设备会拒绝被吊销设备此后发出的消息；尚未收到
它的联系人在收到之前仍会接受。
```

```{term} 设备别名
:english: Device Name

设备持有者为自己的设备设置的名字，随签名的设备列表同步给联系人。它的用途是让人
认出这是哪一台机器，因此双方看到同一个名字；联系人不能修改它。
```

```{term} 用户别名
:english: Display Name

用户为自己设置、同步给全部联系人的名字。它和用户头像一样是公开的，只有本人可以
更改，联系人不能。它可以随时改，也可能与别人重名或被冒用——这正是好友别名存在的
原因。
```

```{term} 用户头像
:english: Avatar

用户为自己设置的一张图片，与用户别名一样公开、一样只有本人可以更改。它有体积
上限，否则就成了一条能向全部联系人推送任意大小数据的通道。
```

```{term} 好友别名
:english: Contact Alias

用户给某个联系人另起的、用来代替对方自设的用户别名显示的名字。它是私有的，不
发送给对方，可以随时改，并在本人全部设备之间同步。它存在的理由是对方的名字由
对方说了算，而用户需要一个自己说了算的称呼才能稳定地找到人。
```

```{term} 好友备注
:english: Contact Note

用户为某个联系人写的一段较长的说明，与好友别名一样私有、可改、在本人设备间同步。
它是记录这个人是谁、通过哪个渠道以什么身份加上的最自然的地方。与好友别名分开是
因为一个要短到能当称呼显示，另一个要能写长句。
```

```{term} 联系人分组
:english: Contact Group

用户对联系人的私有分组，一个联系人可以属于多个分组。分组及其成员关系不发送给
任何联系人，只在本人设备之间同步。它也是文件共享设定可见范围时的单位。
```

```{term} 常在线设备
:english: Always-On Device
:avoid: ["个人节点"]

用户自己的一台长期保持在线、解锁且能自动接收的完整设备，用于在本人其他设备都离线
时保存消息。它持有解密其可见范围内全部消息的密钥，不是只转存密文的中转。
当前部署方式及后台/应用锁边界见[常在线设备指南](guides/always-on-device.md#DOC_20260925_PQ6XSG67M650ARTX--scope)。
```

```{term} 应用会话
:english: App Session
:avoid: ["会话"]

从一次解锁到下一次锁定之间的时段。锁定是安全边界而不是界面切换：下一个解锁的人
可能是另一个人。不要用不加限定的"会话"指代它。
```

```{term} 聊天会话
:english: Conversation
:avoid: ["会话"]

与一个联系人之间、或用户与自己之间的全部消息构成的有序序列，也是这些消息唯一
存在的地方。与自己的聊天会话不是特例，它和其他聊天会话使用同一套机制。
```

```{term} 联系人
:english: Contact

与本人建立了双向关系的另一个用户。关系由两轮交换建立，双方各自在自己的设备上
确认，任何一方单独的动作都不足以建立它。
```

```{term} 邀请
:english: Invitation

用户生成的、用于让别人加自己为好友的文本，由发起方的**用户私钥**签名。它携带
发起方的用户公钥、发起方所依据的渠道标签与其在该渠道上的权威账号、一个设备公钥（即签发它的那台设备，用于关系
建立之后接收对方的操作，不用于接收应答）、有效期、本份邀请专用的一次性公钥，以及
可选的一段备注；这把一次性公钥同时就是邀请标识。邀请不携带用户别名。定向邀请
额外携带被邀请方在该渠道上的权威账号；不定向邀请不指定接收者，因此可以贴在群里
被多个人分别应答。它真正的代价是那个设备公钥与那个渠道账号：贴到公开场合，在场
所有人都能据此查到对应设备的在线状态，也知道了发起方在那个渠道上的账号。
```

```{term} 邀请标识
:english: Invitation Id

一份邀请的唯一标识，取值就是该邀请的一次性公钥，公开出现在邀请里，也出现在应答
的密文之外，使发起方不必逐份试解就能定位是哪一份。它让发起方区分同时存在的多份
邀请、分别作废；而"不能被重放到另一份邀请上"由应答签名覆盖整份邀请的摘要来保证，
不是由标识本身保证。它不是安全码——安全码由双方用户公钥导出，而生成邀请时还不知道
应答方是谁，算不出来。
```

```{term} 一次性公钥
:english: Ephemeral Public Key

专为某份邀请生成的公钥，应答用它加密，它同时是该邀请的标识。对应私钥仅留在签发
设备，不同步到本人其他设备，过期或作废后删除并拒绝使用。它避免长期用户私钥承担
解密职责，但不承诺擦除备份、日志、空闲页或已被他人复制的材料；逻辑删除不等于物理
不可恢复（{need}`TASK_20260919_GWD9N0YMH757CHCV`）。
```

```{term} 邀请应答
:english: Invitation Reply

对一份邀请的回应，携带应答方的用户公钥、其所依据的渠道标签与在该渠道上的权威
账号、用于本次交换的一台设备公钥，以及可选的一段备注；由应答方的**用户私钥**
签名，并用邀请所带的一次性公钥加密，只有该邀请的发起方能解开。它不携带用户别名，
别名与头像在关系建立之后才同步。加密使应答方不必向发起方之外的任何人公开自己的
标识，所以发邀请和应答邀请的暴露程度并不对称。它的签名覆盖规范编码后整份邀请的
摘要，以及应答方自己声明的全部内容，因此不能被改换作者，也不能被重放到另一份
邀请上。
```

```{term} 超时动作
:english: Timeout Action

形式化模型里对"等够了"的显式建模：每一处等待都对应一个可以在任意时刻、任意多次
触发的动作，不假定等待终会结束。它与术语"等待"不是一回事——那一条指的是由乱序
造成、会自行结束的那种；等收齐声明、等用户批准这类等待不会自行结束，只能由超时
动作推进。
```

```{term} 中转
:english: Relay

双方无法直接连接时代为转发字节的第三方设施。它可见通信双方设备端点标识、连接/
投递时间、字节数/帧数、本机网络地址、中转协议版本及设备认证签名；内容与用户层
身份仍受端到端保护。设备标识可见不等于用户名单可读，协议本身也不把设备标识映射
成用户身份。具体边界见[隐私与防护](product/privacy-and-safety.md)。
```

```{term} 直接连接
:english: Direct Connection

两台设备之间不经中转、直接建立的连接。它比经中转少一个可观察方，代价是与本机直接
连接的对端可以得知本机的公网地址。
```

```{term} 发现信息
:english: Discovery Record

为让别人找到一台设备而发布到网络上的记录。本项目要求它只含**中转入口**——即一台中转设施的可连接地址，
经它可以把数据转交给目标设备——而不发布目标设备自己的直接地址。这条要以所选网络库实测
核实，结论未出之前按待核实处理。
```

```{term} 渠道身份
:english: Channel Identity

一对（渠道标签，本方在该渠道上的权威账号）。它是本地私有数据，在本人设备之间同步，
仅在用户为某一份邀请或应答选用时才进入那份产物；整份列表不发送给任何联系人。
```

```{term} 渠道绑定
:english: Channel Binding

借助双方已经在用的另一个渠道，把一个 YoChat 用户公钥与对方在那个渠道上的账号对应
起来的确认过程。邀请与应答都必须携带本方的**渠道标签与该渠道上的权威账号**——权威
指那个渠道自己用来标识账号、不由用户随手改动的那一个（例如微信号而不是昵称）；
对应本身由人完成：用户回到那个渠道，核对这条邀请或应答确实出自那个账号本人。
它依赖的是那个渠道对"这条消息是谁发的"的保证，因此强度不超过那个渠道——账号可能
被盗、可以转让，有的渠道还允许改动账号本身——也不能替代安全码比对。用户若不回到
渠道核对，这条绑定就等于没有。
```

```{term} 安全码
:english: Safety Number

一个可供双方人工比对的值，存在中间人时两边看到的值相同的概率不高于设计写明的上界。它只解决建立关系那一刻
"我不知道对方公钥本该是什么"的问题；此后对方的一切声明都由签名验证，不再需要它。
它由对方的用户身份决定，不随其增删设备而变，因此比对一次长期有效。

它必须通过一条独立于传递邀请所用渠道的途径比对，否则控制那条渠道的人可以连安全码
一起替换掉——这是它唯一的依赖，也是它全部价值所在。比对时双方各念一半、各自核对
收到的那一半，是为了逼双方都真的动手算和看，而不是一方念完另一方敷衍地说对上了。

"知道安全码"不证明任何身份：同时看得到双方公钥的人算得出它，而中间人正是如此。
把它换成只有双方算得出的共享秘密也不会更安全，因为中间人是他那两条腿各自合法的
参与者，双方各自会看到什么他都算得出来。真正能换来好处的是先承诺后揭示——它让
安全码可以短到人真的愿意念，代价是不可重算。具体取哪种做法是设计阶段的事。
```

```{term} 设备吊销时间戳
:english: Revocation Timestamp

吊销声明中由签发设备写入并一并签名的时间。它与本机收到该声明的时间一起构成判定
依据；消息自称的创建时间不参与判定，因为一台已被吊销但仍持有设备私钥的机器可以
把它写成吊销之前的任何时刻。
```

```{term} 等待
:english: Waiting
:avoid: ["停滞"]

聊天会话中某条消息尚未到达，其后的消息因此暂不呈现的状态。它由乱序造成，会在
缺失的消息到达后自行结束，不需要用户做任何事，也不应当被呈现成需要处理的问题。
```

```{term} 通道重建
:english: Channel Re-establishment

当一方无法解开对方的消息时，由接收方发起、双方自动重新建立加密通道并重传尚未
确认送达的消息的过程。它不需要用户参与，也不丢失任何已经落盘的消息，因为每条
消息在发出之前已经在发送方本地存在。只有在长时间无法完成、或重建次数达到上限时才告知用户。
```

```{term} 重发
:english: Resend

把一条已经发出过的消息再送一次。它有两个触发方：接收方察觉缺失并等够了自己设定
的时限之后主动请求；发送方长时间收不到送达确认时兜底发起——后者是必要的，因为
一条完全没有到达且是最新的消息，接收方看不出任何异常。两者都自动完成，不打扰
用户。请求要问遍被请求用户的全部设备，因为各设备的历史可以不一致。
```

```{term} 消息删除
:english: Message Deletion

用户在自己设备上移除一条消息内容的操作，对自己发出的与对方发来的消息同样适用。
它保留消息标识与排序信息并覆盖内容：覆盖是为了设备被取得时内容不在那里，保留
标识是为了这条消息不会被重新同步回来、也不会被当作缺失而使聊天会话永久等待。
它不是撤回——它不要求对方删掉他那一份；删除一条尚未送达的消息只使本设备停止提供
它，并不保证对方收不到：本人其他设备在各自同意那条删除指令之前仍持有原文并仍会
应请求提供，而未收到送达确认也不等于对方确实没收到。删除在本机立即生效，传播到
本人其他设备的只是一条删除指令，须由那台设备上的用户各自同意才执行。
```

```{term} 删除指令
:english: Deletion Request

一台设备把自己执行的删除传播给本人其他设备时发出的提议。它到达后进入待确认列表，
在那台设备上的用户同意之前不执行，相关消息保持可读；用户也可以拒绝它。每台设备
的历史因此由该设备自己说了算，代价是同一个用户不同设备上的历史可以不一致——所以
重发请求要按这些设备的并集来问。
```

```{term} 日志位置
:english: Log Position
:avoid: ["消息序号", "序号"]

一次**操作**在某台设备某条只增日志上的位置，由日志层给出，连续无空洞，每条操作各占
一个——正文、送达确认与加密协议自己的控制消息都在内。它是传输层的坐标：缺失检测、
乱序缓冲、等待、重发请求与放行都按它，因为补齐要取回的是一次操作。它**不是**消息的
身份：通道重建后重传的同一条消息会占一个新的位置。
```

```{term} 消息标识
:english: Message Id
:avoid: ["消息序号", "序号"]

一条**消息**在（聊天会话，作者设备）内的编号，由发送方给出、随内容一同加密。它是产品层
的身份：呈现、去重、墓碑、删除指令、送达确认的目标与引用都按它，重新加密与重传都不改变
它。它**不是**传输坐标：缺了一条时，本机手上有的是日志位置，不是它。
```

```{term} 应用游标
:english: Apply Cursor

某个聊天会话中、某一台作者设备的下一个将被处理的日志位置——每个（聊天会话，作者
设备）对各有一个，因此一个作者的缺失不会连带阻塞另一个作者的消息。它是一个承诺
而不是一个位置：只有当一条操作的全部持久化效果都已提交之后，它才越过这条操作。
```

```{term} 送达状态
:english: Delivery State

一条已发送消息当前的可见状态，至少区分已写入本地与对方已收到。它描述的是事实
而不是预期，因此"对方已收到"必须以对方确实收下为前提；粒度是对方**任一未吊销设备
已落盘**，不是全部设备。它不表示人已经看到——数据到达与人看见是两件事。
```

```{term} 历史同步
:english: History Sync

把一台设备上已有的聊天历史传给同一用户的另一台设备。它必须在持有历史的设备上
发起，这使得仅仅持有恢复短语不足以取得历史。
```

```{term} 用户私钥同步
:english: User Key Sync

把用户私钥从一台已持有它的设备传给同一用户的另一台设备，由持有方发起并在两端
确认。它是便利而不是冗余：持有它的设备全部损坏时，备份好的恢复短语本身就能重新
取得这项能力，因此不需要为了保险而让更多设备持有它——持有得越少，暴露面越小。
```

```{term} 应用锁
:english: App Lock

进入已解锁状态所需的口令校验。它保护的是本地数据的访问，与用户私钥的持有是两件
事：忘记口令时可以用恢复短语打开本机既有数据。
```

```{term} 恢复短语
:english: Recovery Phrase

用户私钥的可书写形式。持有它的人可以以这个用户加入设备、收发消息、吊销其他设备，
并可以以该用户的名义发出邀请与应答、与陌生人建立联系人关系；但默认取不到加入之前的
历史，且加入行为会被本人其他设备看到。
```

```{term} 共享
:english: Share

把本机的一个文件或目录标记为可被指定范围的联系人下载。YoChat 默认不复制文件，记录
的是本地位置与内容指纹，因此源文件被修改或删除后该项共享会被标记为不可用。发送
文件是它的一种形式：带有默认七天的有效期，并且会出现在聊天会话里。
```

```{term} 共享根
:english: Share Root

一次共享所对应的本地文件或目录。对方能看到的相对路径都在它之下，共享根以上的
任何路径成分都不离开本机；其中指向共享根之外的符号链接会被拒绝而不是跟随。
```

```{term} 内容指纹
:english: Content Digest

一份内容按分块计算出的校验值。它使接收方能够逐块验证取得的数据，因而既能发现
传输损坏与篡改，也使同一份内容可以安全地从多个来源并发取得。
```

## 缩写

- E2EE：端到端加密（end-to-end encryption），指只有聊天会话参与方的设备能解密。
- P2P：点对点（peer-to-peer），指设备之间直接通信，不经过持有内容的服务端。
- BIP39：一种把密钥编码为一组助记词的公开规范，恢复短语采用的形式。
