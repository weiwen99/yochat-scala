# 测试规格等价 T1、性能硬门与膨胀预算

**状态**: accepted (2026-11-20)

## 背景

用户要求：重新实现的功能采用原项目相同的测试规格，并保证通过；不能通过时必须说明是测试不合理还是与真实需求冲突，由人裁决。

复盘同时显示：旧测试在依赖升级后集体变红，说明不少测试测的是实现细节；20 多轮 review 没有收敛；性能与文件大小只写在文档里。

## 决策

### 测试规格等价（T1）

- 只对 KEEP 功能做等价；被砍功能的测试不移植。
- Quint：S1 只对 KEEP 协议面重建 5 个模型（Q1–Q5）；旧模型/性质逐条 KEEP/DROP 映射见 `test-parity.md`，未签字不得 DROP。Rust 属性/状态机测试按同生成器、同性质、同参考模型移植为 Scala 测试；E2E 按同场景、同 DOM 断言移植；单元测试按新结构重写。
- 每个旧测试在 `test-parity.md` 有一行：旧测试、功能、层、新测试、状态、省略理由、人签字。
- Kani 这类无 Scala 等价物的层登记为缺口，用属性测试补足或人工裁决。
- 任何失败必须写「测试本身不合理」或「与真实需求冲突」，由人裁决；不得静默删除、跳过或放宽。

### 性能硬门

- 1,000 条端到端 <5s（S1 数据与进程拓扑）。
- 冷启动 p50 ≤2s / p95 ≤4s（JVM + Electron；首个 spike 后校准一次，写回 ADR）。
- 空闲内存 ≤800MB。
- 指标进 `./check.sh`，回执存数值、命令、版本、输入哈希与判词。文档里的数字不是门。

### 膨胀预算

- 生产源码文件 ≤2,000 行（用户裁决，覆盖复盘建议的 800）。
- 模块 ≤8,000 行；v1 生产代码 ≤30,000 行、测试 ≤15,000 行。
- 每加一个功能，同一提交删掉等量死代码。
- 超限必须拆或砍；不接受「先写着，以后再拆」。

### 评审停止规则

- 7 轮硬上限。
- 第 3 轮问题数不降就停，查范围/gate/对象，不加轮次。
- 评审前冻结 diff；修完是新的一轮。

### 文档出口

- 每个计划结项声明取代了哪份旧文档。
- 评审发现必须关闭或撤回；不允许无出口的 append-only。

## 后果

- 移植测试的工作量真实存在；T1 把它限制在行为契约与领域不变量上，避免把旧架构焊死。
- 2,000 行文件上限仍允许较大的文件；模块与总量上限、删代码预算、风险分级评审承担剩余约束。
- 性能门需要稳定的测量环境；首个 spike 校准一次冷启动阈值，之后不得因为一次坏跑而放宽。
