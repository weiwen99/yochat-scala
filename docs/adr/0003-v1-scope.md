# v1 范围 S1：两端各一台设备的加好友与单聊

**状态**: accepted (2026-11-20)

## 背景

旧实现把一句话需求「加好友，单聊」细化成 93 条需求、144 个 Quint 模型、205 个任务、约 25 万行代码，最后仍停在加好友与单聊。复盘的第一条建议是把自用场景砍到两台设备、在线单聊、消息落盘、重启不丢、断网重连。

用户的原则：只实现产品本身合理、可行的功能；不为发布级需求做自用工具。

## 决策

v1 是 **S1**：

- 一个用户 + 一个联系人，各一台设备；
- 通过邀请与应答加好友；
- 单聊；
- 先落盘再发送；
- 重启不丢消息；
- 断网后重连并继续；
- 本地密钥与数据库有最低限度的解锁保护；具体形态（系统钥匙串或口令）由 spike 决定，不做多用户切换。

## 非目标（v1）

- 多设备同步、新设备历史同步、设备吊销传播；
- 群聊、文件传输；
- 恢复短语、四设备迁移接管；
- 陌生人准入预算、公开隐私告知页；
- WCAG 2.2 AA 完整审计、十万条首屏 500ms；
- 完全 p2p / NAT 打洞（v1 是 relay-only，见 ADR-0002）；
- 发布级安装包矩阵与自动更新。

## 后续

- S2（自用多设备）：同一用户 2 台设备、新设备只读加入后消息、吊销；仍无群聊/文件。
- S3（发布级 MVP）：从旧 93 条需求中重新论证的子集。
- S2/S3 各自立计划，不塞进 0001。

## 取舍判据

一条需求如果删掉之后，明天仍然能发一条消息，就删或推迟。新增功能必须回答：

1. 它服务 S1 的哪个验收场景？
2. 它需要新的表、协议状态或组件吗？
3. 它的测试与性能代价是多少？

答不上来就不进 v1。

## 后果

- v1 的产品面很小，但它是真的 friend-to-friend：两个用户、两台设备、一条可恢复的消息路径。
- 旧产品文档中与本 ADR 冲突的部分，以本 ADR 为准；旧文档仍是后续版本的输入。
- 中继是 v1 的已知依赖；没有中继时，两台设备无法跨网通信。这是已知约束，不是待补的洞。
