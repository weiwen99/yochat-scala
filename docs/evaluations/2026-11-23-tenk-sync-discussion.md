# 10k 历史同步与存储口径讨论（2026-11-23）

- 对象：2026-11-23 11:39–12:03（Asia/Shanghai）`AI体验营` 群里的 10k 测试讨论。参与者为本人与 D。起点是本仓 10k 存储基准的截图，随后转到 D 旧实现的 1 万条端到端测试和 sol 的实现。
- 目的：把几条都叫「10k」的数字分开记，留下 D 对慢因的清单、批量提交与签名粒度的取舍，以及它们与本仓性能门的关系。
- 本文只新增文档，不改产品代码，不改门禁。

## 结论

1. 4.34–4.51s 是单进程 store 写入 10,000 条的耗时，不是 10k 两进程 E2E，也不是 10k 协议回放。按 60s 门算占 7.2%–7.5%。`server.bench` 已在 `30ebc76` 固化：两次回执为 4,343 ms 与 4,507 ms，p50 约 0.41–0.42 ms/条，p95 约 0.60–0.61 ms/条；更早的一次性测量是 5,104 ms，只作历史观测，不并入这个区间。
2. 1k 门更紧。ADR-0007 G7 的 1,000 次插入+点查实测 1.55–1.56s（上限 2s）；放进 1k 两进程 <5s 门，store 已占约三成，剩约 3.4s 给加密、transport、runtime 与 UI。
3. D 的「1w 条历史消息同步半小时」是旧实现的端到端数字，且受 600 frame/min 限流约束。单限流下限就是 10,000 ÷ 10/s ≈ 16.7 分钟，半小时是该下限的约 1.8 倍。它不能当存储基准，也不能和本仓 4.34–4.51s 的 store 数字直接比较。
4. D 指出的慢因是队列设计、定时器驱动而非网络事件驱动、大对象复制与反复反序列化、SQLite 索引与表结构。他明确说本机两进程直连，加解密也不是主因。这些是旧实现的自述，不是对本仓的实测。
5. 批量事务提交不是「不能做」。D 说历史同步可以批量提交，他后来就是这么优化的；本次讨论里「不能批量」的判断出自 sol，被 D 否掉。
6. 每条签名与每批签名是协议与存储取舍。旧实现按条存签名，是为了离线转发时证明原作者；加密原本为共同好友转发准备，现已去掉，只保留同一用户的多设备转发。本仓 v1 没有多设备与历史转发，`wire` 按条存是因为「先落盘再发」要原样重发同一帧；改签名粒度应另立 ADR，不能当性能微调。
7. 不建议为了压低 4.34–4.51s 改批量提交。写路径只占 10k 门约 7%，改了会动「先落盘再发」与崩溃语义。下一步仍是 M5 的两进程 1k/10k E2E。

### 限流算术

旧实现的限流是「一分钟接收不超过 600 frame」，即 10/s；30 秒 ACK 等待与它互相打架（`124164`）。10,000 条按 10/s 至少 1,000 秒，约 16.7 分钟。半小时是该下限的 1.8 倍，说明限流至少吃掉一半以上时间，差额不能全算到存储或反序列化。这是按已给阈值的算术推断，不是对旧实现的复测。

## D 的慢因清单

D 在 `128790` 列了五项：队列设计不合理；定时器驱动而不是网络事件驱动；大对象复制；反复反序列化；SQLite 索引与表结构不合理。`128798` 补了 sol 的膨胀数字，`128801` 给端到端时长，`128827` 排除了网络，`128830` 排除了加解密。

这些与 2026-11-20 的两份复盘一致：旧实现的失败形状不是「插入慢」，而是 20,001 条待发效果、1,733 块历史任务（约 20 分钟）、9,901 个重复日志位置，以及 6,940 次补发与限流互撞（`124838`）。本仓已用有界窗口、ACK/缺口与单条落盘替换这类形状：`MaxInFlight=32`、出站上限 1,024、重试有界。4.34–4.51s 的 store 回执不覆盖这些运行时路径。

## 批量提交

D 在 `128825` 说，sol 的分析里「历史同步不能批量」是错的：历史同步可以批量事务提交，他后来做了这个优化。这条只针对历史同步的批量写入，不改「单条消息先落盘再发」的语义。两者不是同一件事：实时发送要求每条先落盘，历史回填可以按批提交。

## 签名与加密

D 在 `128840` 问本仓存储是否存加密、签名信息，并说他的优化是「去掉每条签名，改成每批」。他在 `128842` 给了理由：存储要有签名，是因为离线转发要证明原作者；`128850` 补了加密的由来：原本想共同好友转发，现在去掉了，只让同一用户自己的多设备转发。

本仓的现状：`messages` 表每条存 `wire` 与 `body` 两列。`wire` 是完整帧（头 + 密文 + Ed25519 签名），`body` 是明文正文用 store key 逐条 AEAD 封存。签名粒度是协议的一部分，不是存储的可调参数；v1 又不做多设备与历史转发，所以这条讨论对 v1 的直接结论只有一句：不要为了省字节改帧格式，改它要另立 ADR。

## 本仓每条开销

按字段长度相加：

| 列 | 组成 | 字节数 |
| --- | --- | ---: |
| `wire` | `MessageHeader.canonical`（version 1 + kind 1 + sessionId 32 + devicePub 32 + dhPub 32 + pn 8 + n 8 + seq 8 + nonce 12）+ 密文（正文 + 16 字节 AEAD tag）+ Ed25519 签名 64 | 正文 + 214 |
| `body` | store key 封存的明文：nonce 12 + 正文 + tag 16 | 正文 + 28 |

一条消息的总量约为 `2 × 正文 + 242` 字节，正文在 `wire` 的密文与 `body` 的封存明文里各出现一次。17 字节正文约 276 字节，尚未计 SQLite 行头、两个索引与页填充。这是结构推算，不是实测文件大小；但它足以说明本仓的每条常数开销在数百字节量级，不是 sol 的 32KB。

代码位置：`core/src/yochat/core/WireFrame.scala`、`MessageHeader.scala`、`Signature.scala`；`store/src/yochat/store/MessageRepository.scala`（`seal` 与 `wire` 同一条插入）、`Schema.scala`、`Store.scala`（`synchronous=FULL`）。

## 证据边界

- 微信群内容是参与者自述；D 对旧实现与 sol 的判断没有在本仓复核。
- 5,104 ms 与 108 ms 来自一次性临时基准，现由 `server.bench` 的 4,343–4,507 ms 与恢复 p50 55–56 ms 取代；两者都只覆盖 store，不覆盖 transport/runtime/UI。
