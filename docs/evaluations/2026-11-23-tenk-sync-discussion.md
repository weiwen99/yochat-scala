# 10k 历史同步与存储口径讨论（2026-11-23）

- 对象：2026-11-23 的 `AI体验营` 群讨论。11:39–12:03 的回合从本仓 10k 存储基准截图起，转到 D 旧实现的 1 万条测试和 sol 的实现；13:54 本文发到群里，14:41 D 回复更正与目标，本文据以修订。参与者为本人与 D。
- 目的：把几条都叫「10k」的数字分开记，留下 D 对慢因的清单、批量提交与签名粒度的取舍，以及它们与本仓性能门的关系。
- 本文只新增文档，不改产品代码，不改门禁。

## 结论

1. 4.34–4.51s 是单进程 store 写入 10,000 条的耗时，不是 10k 两进程 E2E，也不是 10k 协议回放。按 60s 门算占 7.2%–7.5%。`server.bench` 已在 `30ebc76` 固化：两次回执为 4,343 ms 与 4,507 ms，p50 约 0.41–0.42 ms/条，p95 约 0.60–0.61 ms/条；更早的一次性测量是 5,104 ms，只作历史观测，不并入这个区间。
2. 1k 门更紧。ADR-0007 G7 的 1,000 次插入+点查，最新回执是 1.83–1.85s，离 2s 上限只剩 7%–8% 的余量；放进 1k 两进程 <5s 门，store 已占 37%，剩约 3.2s 给加密、transport、runtime 与 UI。
3. D 在 14:41 更正：那半小时包含 10k 消息生成与其它测试，不是纯传输时间。先前据此推的「限流至少吃掉一半时间」作废，本文不再用它估算任何速率。
4. D 指出的慢因是队列设计、定时器驱动而非网络事件驱动、大对象复制与反复反序列化、SQLite 索引与表结构。他明确说本机两进程直连，加解密也不是主因。这些是旧实现的自述，不是对本仓的实测。
5. 批量事务提交不是「不能做」。D 说历史同步可以批量提交，他后来就是这么优化的；本次讨论里「不能批量」的判断出自 sol，被 D 否掉。
6. 每条签名与每批签名是协议与存储取舍。旧实现按条存签名，是为了离线转发时证明原作者；加密原本为共同好友转发准备，现已去掉，只保留同一用户的多设备转发。本仓 v1 没有多设备与历史转发，`wire` 按条存是因为「先落盘再发」要原样重发同一帧；改签名粒度应另立 ADR，不能当性能微调。
7. 实时路径不建议为了压低 4.34–4.51s 改批量提交；写路径只占 10k 门约 7%，改了会动「先落盘再发」与崩溃语义。历史同步是另一条路径，批量提交可以接受，D 自己就是这么优化的。
8. D 给的速率 bar 是同步超过 1,000 条/秒。本仓最接近的口径是 10k 协议回放 811–869 条/秒，低于 bar 13%–19%，而且这条口径还没有 SQLite 与网络。存储与加解密单跑都在 bar 以上，合起来不够；回放的组合开销没有单独计时。
9. D 的两条预算 wire overhead ≤200%、storage overhead ≤10%，按真实消息长度分布算，当前帧与两列存储都不满足。群聊正文 p50 只有 37 字节，214 字节的固定开销是它的 5.8 倍。
10. 历史同步属于多设备，ADR-0003 把它排在 v1 之外。这组数字要变成门，得先定是否改 v1 范围、以及百分比的分母，本文只记依据与算式，不做裁决。

### 限流算术（作废）

本文先前用「一分钟 600 frame」推算 10,000 条至少要 16.7 分钟，据此说半小时里限流占了一半以上。D 在 14:41 更正：那半小时包含 10k 消息生成与其它测试，不是纯传输。原推算的分子分母都不成立，整段结论删除，仅保留 600 frame/min 与 30 秒 ACK 互相打架这条事实（`124164`）。

## 1,000 条/秒的口径对照

三条可直接比较的本仓回执：

| 口径 | 规模 | 耗时 | 折算 | 含什么 |
| --- | --- | --- | --- | --- |
| A-first spike（ADR-0005） | 1,000 条 | 107 ms | 9,346 条/秒 | 真实加解密 + harness 中继；无持久化、无 UI |
| store 追加（`server.bench`） | 10,000 条 | 4.343 / 4.507 s | 2,302 / 2,219 条/秒 | 真实 SQLite、逐条事务；夹具预生成，不含加解密 |
| 协议回放（`TenKReplaySpec`） | 10,000 条 | 11.5 / 11.9 / 12.3 s | 869 / 842 / 811 条/秒 | 真实 `Application.step`（含签名、验签、ACK）；无 SQLite、无网络 |

D 的 bar 是 1,000 条/秒，折成每条约 1 ms。最接近完整链路的是第三行，它比 bar 慢 13%–19%，而且还没有数据库与网络。

两条单跑都够快：加解密与中继 9,346 条/秒，存储 2,219–2,302 条/秒，各自都在 bar 以上两倍有余。合起来的回放却只有 811–869 条/秒。回放里每条消息要走发送与接收两侧的 step、还带 ACK，这部分组合开销没有单独计时，不能直接把两个单跑数字相除解释，但可以确定缺口不在存储单侧。按 1 ms 预算拆，store 追加 p50 已占 0.41 ms（41%），p95 占 0.60 ms（60%）；剩下 0.4–0.6 ms 要给验签、解密、状态推进与 ACK。

还有一层口径差别：协议回放是单线程顺序处理，没有批量提交，也没有并发。历史同步若按 D 的做法改成批量事务与流水线，这条回放不代表它的上限。批量路径要单独测，本文不给结论。

## D 的慢因清单

D 在 `128790` 列了五项：队列设计不合理；定时器驱动而不是网络事件驱动；大对象复制；反复反序列化；SQLite 索引与表结构不合理。`128798` 补了 sol 的膨胀数字，`128801` 给端到端时长，`128827` 排除了网络，`128830` 排除了加解密。

这些与 2026-11-20 的两份复盘一致：旧实现复盘记录到的失败形状是 20,001 条待发效果、1,733 块历史任务（约 20 分钟）、9,901 个重复日志位置，以及 6,940 次补发与限流互撞（`124838`）；这些是队列与运行时问题。本仓已用有界窗口、ACK/缺口与单条落盘替换这类形状：`MaxInFlight=32`、出站上限 1,024、重试有界。4.34–4.51s 的 store 回执不覆盖这些运行时路径。

## 批量提交

D 在 `128825` 说，sol 的分析里「历史同步不能批量」是错的：历史同步可以批量事务提交，他后来做了这个优化。这条只针对历史同步的批量写入，不改「单条消息先落盘再发」的语义。两者不是同一件事：实时发送要求每条先落盘，历史回填可以按批提交。

## 签名与加密

D 在 `128840` 问本仓存储是否存加密、签名信息，并说他的优化是「去掉每条签名，改成每批」。他在 `128842` 给了理由：存储要有签名，是因为离线转发要证明原作者；`128850` 补了加密的由来：原本想共同好友转发，现在去掉了，只让同一用户自己的多设备转发。

本仓的现状：`messages` 表每条存 `wire` 与 `body` 两列。`wire` 是完整帧（头 + 密文 + Ed25519 签名），按 ADR-0007 为了重发时逐字节原样使用；`body` 是明文正文用 store key 逐条 AEAD 封存，其 AAD 绑定 `SHA-256(wire)`。签名粒度是协议的一部分，不是存储的可调参数；v1 又不做多设备与历史转发，所以这条讨论对 v1 的直接结论只有一句：不要为了省字节改帧格式，改它要另立 ADR。

## 本仓每条开销

按字段长度相加：

| 列 | 组成 | 字节数 |
| --- | --- | ---: |
| `wire` | `MessageHeader.canonical`（version 1 + kind 1 + sessionId 32 + devicePub 32 + dhPub 32 + pn 8 + n 8 + seq 8 + nonce 12）+ 密文（正文 + 16 字节 AEAD tag）+ Ed25519 签名 64 | 正文 + 214 |
| `body` | store key 封存的明文：nonce 12 + 正文 + tag 16 | 正文 + 28 |

一条消息的总量约为 `2 × 正文 + 242` 字节，正文在 `wire` 的密文与 `body` 的封存明文里各出现一次。17 字节正文约 276 字节，尚未计 SQLite 行头、两个索引与页填充。这是结构推算，不是实测文件大小；但它足以说明本仓的每条常数开销在数百字节量级，不是 sol 的 32KB。

代码位置：`core/src/yochat/core/WireFrame.scala`、`MessageHeader.scala`、`Signature.scala`；`store/src/yochat/store/MessageRepository.scala`（`seal` 与 `wire` 同一条插入）、`Schema.scala`、`Store.scala`（`synchronous=FULL`）。

## 两条 overhead 预算

D 的两条预算需要先定分母，否则同一份代码能算出几个结论。本文按两种常见读法各算一遍。

读法一：overhead =（帧或存储字节 − 正文字节）÷ 正文字节。

另一种更严的读法：总量不超过正文的两倍，即 wire ≤ 2× 正文。此时门槛从 107 字节抬到 214 字节。

本仓当前每条固定开销：`wire` = 正文 + 214，`body` = 正文 + 28，两列合计 2×正文 + 242。

对单条消息的边界：

| 目标 | 需要的正文字节 |
| --- | ---: |
| wire overhead 200%（多出部分不超过正文两倍） | ≥107 |
| wire ≤ 2× 正文（更严的一种读法） | ≥214 |
| storage overhead 10%（相对正文） | ≥2,420 |
| storage overhead 10%（相对 wire） | 无解；两列的最小比值约 13%，随正文增大趋近 100% |

真实消息长度分布（0x1 镜像，2026-11-23 查询）：

| 类型 | 条数 | p50 | p90 | 均值 | ≥107 字节占比 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 群聊 | 91,111 | 37 | 99 | 55.3 | 8.6% |
| 私聊 | 16,132 | 24 | 69 | 40.0 | 4.0% |
| 公众号等 | 126 | 288 | 537 | 284.7 | 65.9% |

按总量加权：

| 类型 | wire ÷ 正文 | storage ÷ wire |
| --- | ---: | ---: |
| 群聊 | 4.87 倍（overhead 387%） | 1.31 倍（+31%） |
| 私聊 | 6.35 倍（overhead 535%） | 1.27 倍（+27%） |
| 公众号等 | 1.75 倍（overhead 75%） | 1.63 倍（+63%） |

结论：按读法一，群聊与私聊的 wire overhead 是 387% 与 535%，都超过 200%；只有长文（公众号）达标。存储相对 wire 多出 27%–31%，超过 10%；公众号类多出 63%，更远。

口径说明：镜像里 44% 的群聊消息带「发送者 wxid + 换行」前缀，长 17–21 字节，上表已剥掉；不剥的话群聊均值会虚高到 64.6 字节、overhead 显得低一些。

两个可行的杠杆，代价不同：

- 去掉每条签名、改每批签名，是 D 自己在做的方向。它省掉 64 字节，但在 47 字节的群聊 p50 上仍救不回 200%，因为 134 字节的帧头还在。要真正压到 200% 以下，得让帧头按会话或批次摊销，属于协议格式改动。
- 存储侧要满足 10%，只有一条便宜路径：投递完成后丢掉 `wire`，只留 `body` 与 `wireHash`（32 字节）。按真实分布，这样存的是 wire 的 0.39–0.69 倍，稳定满足 10%。代价是交付后再也不能原样重发，而 ADR-0007 的 G3 行绑定靠 `wireHash` 仍可成立；但 `body` 的 AAD 绑定的是 `SHA-256(wire)`，删列前要确认哈希列的位置与迁移。这属于 ADR 级改动，不是性能微调。

两者都只解决一部分：前者管传输，后者管落盘。任何一项进代码前都要先定分母与是否进入 S1 范围。

6. 若采纳两条 overhead 预算，先定分母（相对正文还是相对 wire、单条还是总量），再决定改帧格式还是改存储列。

## 待裁决

下面三项本记录不自行决定，需要人给口径：

1. 1,000 条/秒是否进入 S1 门。它比现有 1k 门隐含的 200 条/秒、10k 门的 167 条/秒都严，等于收紧五倍；而且历史同步本身不在 v1。
2. wire overhead 的分母：相对正文（200% 即帧不超过正文三倍）还是总量不超过正文两倍。两种读法的门槛相差一倍。
3. storage overhead 的分母：相对正文还是相对 wire。相对正文时，10% 在真实聊天长度上要求至少 2,420 字节，等于不可达；相对 wire 时，只要不再存第二份就能满足。

## 证据边界

- 微信群内容是参与者自述；D 对旧实现与 sol 的判断没有在本仓复核。D 的 1,000 条/秒与两条百分比是对方自述的设计目标，不是对本仓的验收。
- 5,104 ms 与 108 ms 来自一次性临时基准，现由 `server.bench` 的 4,343–4,507 ms 与恢复 p50 55–56 ms 取代；两者都只覆盖 store，不覆盖 transport/runtime/UI。
- 消息长度分布取自 0x1 微信镜像的文本消息，只含本人账号可见的会话（群聊 91,111、私聊 16,132、公众号等 126），不是任意 IM 流量的代表样本。图片、语音、文件、表情消息没有计入，它们的正文长度分布不同。
- overhead 表里的 mean 是字节平均，wire ÷ 正文 与 storage ÷ wire 都是按总量加权，不是把单条比值取平均；两者在数学上不同，正文短的条目权重更大。
- S1 的服务层功能 E2E #1–#7 已在 `da4b8d6` 上 7/7 通过（32.22s，见 Plan 0003 的 impl.md），但那是功能契约，不是吞吐；E2E#8 的 1k/10k 吞吐、冷启动、空闲内存仍未跑。任何「S1 性能已达标」的说法都不成立。
- 每条开销是字段长度推算；没有实测数据库文件大小，也没有把索引与页填充算进去。
- 本文没有改代码，也没有重跑 `./check.sh`；两次 `server.bench` 的回执在文末。

消息长度与开销分布（只输出聚合值，不取正文）：

```sql
with m as (
  select c.kind,
         case when m.text ~ '^wxid_[a-z0-9]+:\n'
              then octet_length(regexp_replace(m.text, '^wxid_[a-z0-9]+:\n', ''))
              else octet_length(m.text) end as b
  from wechat_message m
  join wechat_conversation c using (account_wxid, conversation_id)
  where m.text is not null and m.parse_state = 'ok' and length(m.text) > 0
), a as (
  select kind, count(*) n, sum(b) s from m group by kind
)
select kind, n,
       round((s + 214.0 * n) / s, 3) as wire_x_payload,
       round(100.0 * 214.0 * n / s, 1) as wire_overhead_pct,
       round(100.0 * ((2.0 * s + 242.0 * n) / (s + 214.0 * n) - 1), 1) as storage_over_wire_pct
from a order by n desc;
```
